# MVP 모의 로그의 근거 보존·AI 전달

이 문서는 #350의 **MVP 모의 입력에 한정한 구현 방식**이다. 운영 로그 수집 계약의
확정본이 아니며, 실제 수집을 도입할 때 원천·수집 지연·누락·보존 방식과 함께 재검토한다.
위험 판정·자동 대응 정책·Action Whitelist는 기존 구현을 따른다.

## 준비부터 전달까지

`검증된 모의 로그 테스트 자료 → 집계·발췌를 첨부한 모의 관측 파일 → 기존 MockThreatConsumer →
receive_threat → Incident + THREAT 근거 저장 → Dispatcher → 그래프 요청`

새 공개 접수 API는 만들지 않는다. 기존 요약 관측 파일도 계속 접수하며, 이 경우
로그 첨부는 `null`로 남는다. N01/N02 수락 대조 자료는 위협으로 주입하지 않는다.

```powershell
uv run --no-sync python scripts/secops_log_corpus.py prepare --case C01 --inbox <앱의-모의-inbox> --target-arn <명시할-EC2-ARN>
# 필요할 때 창 끝점을 옮긴다. 모든 원천/수신 시각에 같은 초 단위 차이를 적용한다.
uv run --no-sync python scripts/secops_log_corpus.py prepare --case C01 --inbox <앱의-모의-inbox> --target-arn <명시할-EC2-ARN> --occurred-at 2026-09-17T00:00:00Z
```

준비 명령은 파일만 쓰며 DB·AWS·모델을 호출하지 않는다. 앱 소비자가 실행 중인
inbox에 쓰면 이후 앱의 기존 처리 흐름이 시작되므로, 실행 환경을 정한 뒤 사용한다.
공급 파일의 64 KiB 상한은 유지한다.

## Incident에 남기는 자료

기존 THREAT `content.event`를 유지하고 선택적 `content.context`를 더한다.
기존 JSONB Evidence 저장을 사용하므로 새 테이블·ENUM·마이그레이션은 없다.
공개 API에는 기존처럼 Evidence ID만 보이며 새 원문 조회 API는 만들지 않는다.

| 자료 | 저장 내용과 의미 |
| --- | --- |
| 위협 | 정규화 이벤트와 기존 초기 판정. 로그 집계·출발지·창 끝점·대상과 일치 확인 |
| 모의 로그 | 생성 fixture 전체의 실패·수락·보조 행 수, 원천·선택 정책, 전체 원문 지문, 최대 12행 발췌 |
| 대상 자산 | 접수 때 사용 가능한 수집 자산의 `DetectionAssetSnapshot`. 수집 회차·관측 시각 포함 |
| 관계 자산 | EC2의 직접 `SECURED_BY` SG와 `PROTECTED_BY` NACL만 선택. 각 자산 사본·수집 회차 보존 |
| 선택 누락 | 연결 대상 미수집·소멸·회차 누락·원본 관계 회차 불일치·유형/계정/리전 불일치 사유 |
| 고정 시점 | `captured_at`. 과거 모의 사건 발생 시점의 실제 인프라 상태라고 해석하지 않음 |

로그 발췌는 원천 시각 순 처음 6행과 마지막 6행이며 전체가 12행 이하면 전부다.
발췌 자체에서 전체 실패 횟수를 다시 세지 않는다. 집계는 검증된 모의 공급자가 전체
테스트 자료에서 계산한다. 이 입력 경로가 임의 운영 로그를 검증하는 탐지기는 아니다.
생성된 모의 로그 전체는 버전 관리되는 테스트 자료에 남고, DB에는 지문과 선택된 발췌를 보존한다.

`corpus_fingerprint`는 시각 이동 전 전체 JSON 레코드의 정규화 지문이다.
`time_shift_seconds`와 `explicit_mock_target`으로 재생 변환을 표시한다. 지문은 내용
동일성 비교용이며 실제 공격 발생·원천 진위의 증명이 아니다. 합성 수락 0건도 실제
인증 성공 부재를 의미하지 않는다. NCP 대조 자료를 AWS 관측으로 옮기지 않는다.

대상·직접 관계·연결 자산은 DB의 한 조회 문장으로 읽는다. 원본 관계의 회차가
대상 자산 회차와 다르면 해당 관계를 제외하고 사유를 남긴다. 연결 자산은 자신의
수집 회차를 그대로 표시하므로 모든 자료가 같은 관측 시점이라고 주장하지 않는다.
최대 64개의 직접 SG/NACL 관계를 지원하며 초과는 입력 거부로 처리한다.
NACL 사본의 현재 DTO에는 개별 rule entry가 없어 차단 효과·rule 가용성은 판단할 수 없다.

## 저장분에서 AI 입력 만들기

Dispatcher는 새 Inventory를 조회하지 않고 THREAT 안의 대상 사본을 `asset_context`로
복원한다. SG/NACL 사본과 로그 집계·발췌는 위협 근거로 전달한다. 모델 요청에서는
대상 자산 본문의 중복을 제거하고 수집 회차는 남긴다. 입력 계약은 최상위 자산과
저장 사본의 일치를 확인한다.

선차단 등의 실행 결과는 Incident 생성 이후 생기므로 기존 Execution 조회로 별도
연결한다. 가드레일·실행 직전 현재 AWS 상태 확인은 그대로이며 과거 사본이 실행
가능성을 보장하지 않는다. 모델에 보낼 문자열은 기존 전송 마스킹을 거친다.

중복 관측 재전달은 기존 Incident와 근거를 그대로 반환한다. 이후 Inventory 갱신이나
관계 제거가 저장 근거를 바꾸지 않는다. 근거 저장 실패는 Incident·이벤트 저장과 함께
롤백하고, 저장소 장애는 기존 파일 소비자의 재시도 경로를 따른다.

## 부족한 자료와 기존 Incident

- 로그 첨부 없음은 `null`이다. 관측 실패 0건으로 바꾸지 않는다. 기존 요약 관측에
  근거를 꾸며 넣지 않으며 현재 모의 접수 호환성을 유지한다.
- 대상 미수집·소멸·수집 회차 누락은 해당 상태와 위협 근거를 보존한다. Incident 생성과
  초기 위험도는 유지하지만 대상 사본이 없으므로 기존 분석 실패 처리를 따른다.
- 일부 관계를 선택할 수 없으면 사유와 남은 관계를 보존한다. 수집 완전성을 주장하지 않는다.
- NACL 존재를 근거 스키마의 필수 조건으로 만들지 않는다. 다만 기존 Dispatcher는
  조치 메뉴가 비면 모델을 호출하지 않고 실패 처리한다. 이 정책의 변경은 이번 범위 밖이다.
- 구 Incident의 `context`가 없으면 조회는 가능하다. 최신 Inventory로 과거 근거를
  보충하지 않으며 분석 시 기존 실패 경로를 따른다. 자동 backfill·수집 대기·수동 재개
  API는 추가하지 않는다.
- DB 조회 실패는 정상 빈 결과로 기록하지 않는다. 접수 트랜잭션을 실패시키고 재시도한다.

## 검증 범위

`tests/test_secops_log_corpus.py`는 원천 집계·재생성을, `apps/core-api/tests/test_secops_context.py`는
파일 공급·실제 PostgreSQL 저장/조회·Inventory 갱신 뒤 사본 유지·모델 요청 조립을 검증한다.
모델은 FakeAIModelClient이므로 실제 모델의 판단 품질을 증명하지 않는다.

[2026-09-17 서비스 실행 결과 요약](OBSERVATION_SUMMARY.md)에서는 별도로 C01~C07을
실제 모델에 각 1회 전달하고, 저장 근거와 실제 모델 입력의 일치·화면 승인·가드레일·
LocalStack NACL 변경·완료 표시를 확인했다. N01/N02는 위협 입력을 만들지 않았다.
같은 응답의 품질도 평가했다. 구조화 기대값은 5건 통과·2건 조치 필요성 미확정이고,
문장 품질은 7건 모두 최소 한 항목이 미달했다. 기준·결함·한계는 실행 결과 요약에 함께 남겼다.
#324에서는 이 판정을 바탕으로 입력·기대 답을 보강하고 품질을 개선한다.

## #324 인계

이번 변경은 머지 후 #324의 입력·기대 답 재검토와 품질 개선을 시작할 수 있는 기반을 제공한다.
GitHub에는 [서비스 실행 결과 요약](OBSERVATION_SUMMARY.md)으로 조건·결과·한계와 개선 후보를
공유한다. 실제 저장 근거·그래프 입력·모델 요청과 응답·DB/API·실행 상세 기록은 담당자 로컬에만
보관하며 #324에서 재검토한다.

#324에서는 이 저장 입력에 평가 입력을 맞추고, 판단 목표별 필요한 근거·허용 답·금지 단정을
정리한다. 이어 로그·기대 답·채점 기준·프롬프트를 보강하고 같은 조건으로 개선 전후를
비교한다. 이 품질 작업을 #350 머지의 선행 조건으로 두지 않으며, 유료 측정은 라운드별
대상·호출 수·예상 비용·시간을 확인하고 승인받아 진행한다.

FinOps·#347의 기존 근거·입력·후보·절감 예상 경로는 전체 회귀 검증에 포함했다.
해당 경로의 재설계를 #324 착수 조건으로 추가하지 않는다.
