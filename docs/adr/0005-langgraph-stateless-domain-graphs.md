# ADR-0005: LangGraph를 상태를 보관하지 않는 도메인별 두 그래프로 구성한다

- **Status**: Accepted
- **Date**: 2026-08-18
- **Amended**: 2026-11-05(1차 — 설계 원칙 5항 "근거 선행" 신설, SecOps 그래프 순서 복귀·위험 재평가 노드 제거, 요약 호출 입력 규칙, 실행 계획 단계의 대체 불가). 하단 "개정 이력" 참조, **핵심 결정 불변**
- **Deciders**: 안성일(AI/Guardrail) 제안, 김세혁(PM/Infra) 승인 / 1차 개정 — 안성일 제안·김세혁 승인(PR #584)

## Context (배경)

LangGraph 도입 여부는 [ADR-0001](0001-mvp-monorepo-structure.md)·[ADR-0002](0002-runbook-whitelist-mvp-scope.md)가 후속 결정 후보로 남겼던 항목이며, 2026-08-13 팀장 결정으로 도입이 확정됐다(`docs/PROJECT_STATUS.md` 결정 로그). 그래프 설계는 안성일 주관. 입출력 계약은 `packages/schemas/agents.py`에 정의 완료(#49) — 도메인별 입력, 공통 출력, 불변식 9항. **그래프 내부는 미정.**

구현 전 결정 대상:

- FinOps·SecOps 그래프 분리 여부
- 상태 원천 — 그래프 Checkpointer vs 외부 DB
- Guardrail·DB 저장·AWS 실행의 그래프 내외 배치와 LLM 호출 경계
- 판단 근거의 보존 형태 — AWS를 실제로 변경하므로 사후 설명·검증이 가능해야 함

## Decision (결정)

**FinOps·SecOps 두 그래프로 나누고, 상태 보관·승인 대기·AWS 실행·Guardrail 검증을 모두 그래프 밖에 둔다. 판단 근거는 검증 가능한 구조화 필드로만 남긴다.**

```text
FinOps : summarize_evidence(근거 3줄 + decision) → propose_candidates(실행 계획 전사) → validate_output_contract
SecOps : summarize_evidence(근거 3줄 + decision) → (실행 계획: 코드 조립) → validate_output_contract
```

`validate_output_contract`는 출력 스키마와 #49 불변식만 검사한다 — 4단계 Guardrail 검증이 아니며 그래프 밖에서 별도로 수행된다.

- **SecOps `reassess_risk`는 두지 않는다.** 이 노드는 등급만 내는 호출로, 서버가 이미 집계한 입력에 서버 자신의 산술 규칙(`apps/core-api/security/risk_evaluator.py`와 공유하는 횟수·빈도 문턱)을 다시 적용했다. 2026-11-05 모델 비교에서 이 노드의 출력이 서버의 `initial_risk_level`과 달랐던 것은 167회 중 6회이며, 6회 모두 규칙 위반이었다.
- **SecOps 출력의 `reviewed_risk_level`은 null로 둔다.** 서버 값을 복사하지 않는다(아래 "대안과 기각 이유" 1). 출력 계약은 FAILED 밖에서도 이 필드의 null을 허용한다(`packages/schemas/agents.py` `AgentGraphOutput`). Workflow 검사(`apps/core-api/agent_dispatcher.py` `_contract_violation`)의 SECOPS 분기는 FINOPS 분기와 같은 모양으로 바꿔, 값이 실려 있으면 `REVIEWED_RISK_MISMATCH`로 거절한다 — 이렇게 해야 "SecOps는 null로 낸다"가 검사되는 규칙이 된다. AI 재평가 값이 담긴 과거 행은 그대로 둔다. 이 필드가 다시 의미를 갖는 것은 자기 입력과 평가셋을 가진 맥락 보정 노드가 생길 때이며, 그 도입은 이 개정의 범위 밖인 후속 결정이다. 자동 선제 차단은 `initial_risk_level`이 구동하므로 영향이 없다.
- **두 그래프 모두 "분석 먼저" 순서다.** 이는 이 ADR의 원래 순서로의 복귀다. 2026-09-21 변경(#324, commit `dd22cda`)은 SecOps 그래프에서 요약을 후보 생성 뒤로 옮겨 요약 문장이 실제 후보를 설명하게 했다. 이 개정은 요약을 사후 설명으로 만드는 대신 **구조화된 `decision` 필드와 코드의 decision↔후보 대응**으로 같은 목표를 달성한다(설계 원칙 5, "대안과 기각 이유" 2).
- **SecOps 실행 계획은 코드가 조립한다.** 출발지 CIDR은 타입 입력의 Evidence에서(근거 3줄 문장을 파싱하지 않는다), NACL 대상은 자산 맥락에서, protocol은 TCP 전체, rule number는 서버가 정한다 — 서버 rule number는 #570으로 이미 충족된 선행 조건이다. 이 단계에 모델 호출은 없다. 조립의 세부 규칙은 구현 이슈(#583)에서 정한다.
- **FinOps는 AI 소관 파라미터를 위해 실행 계획 단계의 모델 호출을 유지한다.** 규칙에서 도출 가능한 값은 코드로 옮긴다는 방향을 유지한다(#251 선례, #237에서 흔들린 필드는 파라미터뿐이었다).
- **호출 수는 비규범이다.** 초기 구현은 SecOps 1회, FinOps 2회다. 어떤 값을 모델이 채우고 어떤 값을 코드가 정하는지는 규칙이 있느냐로 정하며, 호출 수는 그 결과이지 목표가 아니다.

**설계 원칙 5항**:

1. **도메인별 분리** — 단일 그래프에 조건 Edge를 두면 합집합 State가 필요해 한쪽 전용 필드가 nullable로 혼입된다. 두 그래프로 나눠 출력 불변식을 그래프 단위로 강제한다. (`domain`은 Workflow가 설정하며 그래프 노드가 이를 바꿀 수 없다 — #49 불변식 2) SecOps 전용 `reviewed_risk_level`은 초기 위험도를 덮어쓰지 않는다 — 1차 개정 이후 SecOps 그래프는 맥락 보정 노드가 생기기 전까지 이 값을 null로 낸다(위 결정 참조).
2. **상태 비보관** — Checkpointer를 두지 않고 업무 상태는 PostgreSQL 단일 원천으로 둔다. 승인 중단점도 없다 — 그래프는 한 번 호출되면 Terminal 결과 반환 후 종료한다. 중복 호출은 Incident의 AI 호출 상태를 PostgreSQL 트랜잭션 안에서 원자적으로 선점(Claim)해 막는다 — 프로세스 수와 무관하게 성립한다. (상태 이원화와 서버 타이머·그래프 수명의 결합 회피)
3. **책임 한정** — 그래프는 분석·후보 생성까지만 담당하고 Guardrail·DB 저장·AWS 실행·승인은 밖에 둔다. 모델 호출은 이 ADR에서 도입하는 `AIModelClient` 경계를 통해서만 수행해 SDK 타입·자격증명·예외가 `AIModelClient` 구현 밖의 그래프·도메인 코드로 새지 않게 한다. (테스트 주입용 경계이며 Provider 교체·배포 방식의 확정이 아님)
4. **근거는 구조화 필드로** — 판단 근거는 `Incident`의 요약 3줄·`initial_risk_reason_codes`·`reviewed_risk_level`(1차 개정 전 행에 한함 — 이후 SecOps 그래프는 null), `RunbookCandidate.evidence_ids`, `GuardrailEvaluation` 4단계 결과에 남긴다. 호출 메타는 구조화 로그로 출력하되 업무·감사 데이터의 기준은 PostgreSQL이며 운영 로그는 감사 근거가 아니다. `evidence_ids`가 가리키는 Evidence는 생성 후 변경하지 않는다 — 근거가 바뀌면 판단 설명이 성립하지 않는다. (`RiskReasonCode` 값 목록은 2026-08-31 확정 — PR #206, `packages/schemas/events.py`)
5. **근거 선행** — 모델이 결정을 내는 호출에서는 근거가 결정에 선행한다. (1차 개정 신설)
   - **"결정"의 범위** — 이 원칙에서 결정은 조치/무조치의 선택, 곧 사람에게 제시할 선택지의 선택이다. 실행 계획 단계에서 파라미터를 채우는 것은 결정이 아니라 전사다.
   - **`decision`의 의미와 형태** — `decision`은 모델이 사람에게 제시하기를 권하는 메뉴 조치 목적의 **집합**이다. 0개는 제시 없음, 보통은 1개이며, 2개 이상은 대상이 서로 다르거나 함께 실행해야 할 때뿐이다 — 이 기준은 현 FinOps 후보 프롬프트에 있던 것이며, 개정 후에는 `decision`을 내는 요약 호출이 적용하고 실행 계획 단계는 그 집합을 전사만 한다("대안과 기각 이유" 3). 뜻은 "선택지를 사람에게 제시한다"이며 "지금 실행한다"가 아니다 — 선택지를 권하면서 적용 보류를 조언하는 것도 조치를 결정한 것이다(SecOps 기준선 C06: 후보와 현재 적용 보류가 공존 가능). 값은 산문이 아니라 닫힌 값으로 받는다 — 인코딩과 지문(fingerprint) 반영 방식은 구현 이슈(#583)에서 정한다.
   - **도메인별 허용 값** — SecOps는 조치 0개 또는 1개다. FinOps에서 메뉴가 비어 있지 않을 때 "제시 없음"을 허용할지는 구현 이슈(#583)에서 정한다 — #243 실측에서 요약이 판정을 유보하자 NO_PROPOSAL 도피가 나왔다(A7 4/60). 허용하려면 FinOps 정답지가 케이스마다 기대 decision을 가져야 한다.

   원칙 5는 세 가지 차원으로 확인한다. ①②는 구조가 보장하고 코드가 검사하며, ③은 구조가 보장하지 못해 평가로 측정한다.

   - **보장 ① 요청 스키마의 순서** — 결정을 싣는 호출이 요청하는 JSON Schema의 속성 순서에서 근거 3줄(observation → diagnosis → rationale)이 `decision`보다 먼저 온다. 확인은 스키마 순서 테스트로 한다 — 키를 정렬하는 승인 지문으로는 순서를 확인할 수 없다. 실제 생성 순서는 Provider에 따라 다르며 구현에서 검증한다. 필드 순서는 보이는 출력의 순서만 정하며, 숨은 추론에 대해서는 아무것도 말하지 않는다.
   - **보장 ② decision↔후보 대응** — 코드가 결정된 조치 목적마다 그 Runbook을 대응시킨다. 자산 메뉴 안에서 목적↔Runbook은 1:1이므로 다른 조치로의 대체는 금지 대상이 아니라 불가능하다. 후보 수는 결정된 조치 수와 같다. 코드가 대상을 1:1로 정할 수 있는 곳(SecOps의 NACL, FinOps의 대상 자산)은 코드가 정하고, 실행 계획 단계에 남는 대상·근거 선택의 재량은 아래 반복 안정성 제약에 묶인다. 불일치·실현 불가는 실패 사유다 — 새 사유 코드는 `AnalysisFailureReason`(`apps/core-api/ai/agent.py` — 운영 로그 분류 코드이며 공개 계약이 아니다)에 정의하며, 이름은 구현 이슈(#583)에서 정한다(제안: `DECISION_MISMATCH`). 검사는 응답 모델 밖의 그래프 코드에서 하고, 출력 재시도 대상으로 두지 않으며, 항상 로그로 남긴다.
   - **보장 ③ 근거가 결정을 뒷받침하는가** — 구조로 보장되지 않는다. 평가에서 채점 항목("rationale이 decision을 뒷받침한다")과 반복 실행 간 decision 뒤집힘 비율로 측정한다.
   - **반복 안정성** — 두 도메인 모두의 제약이다. 설정을 고정한 반복 실행에서 결정된 집합과 `runbook_id`·`target_arn`·`evidence_ids`·후보 수가 달라지지 않아야 한다. 후보↔NO_PROPOSAL 전환은 결정된 집합과 후보 수의 변화이므로 흔들림이다. 실행별 허용(SecOps `EITHER`)은 반복 안정성과 별개이며 둘 다 보고한다. 반복 횟수와 측정 절차는 기준선 문서(`apps/core-api/ai/evaluation/summary/baseline.md`, `apps/core-api/ai/evaluation/secops/baseline.md`)가 정한다.
   - **근거와 설명의 구분** — 결정 뒤에 생성된 텍스트는 설명이며 근거라 부르지 않는다. 근거 3줄은 사람 승인자를 위한 근거 사실이고, 의미 있는 결정은 사람의 승인이다(원칙 3 불변).
   - **보존** — `decision`은 그래프 안에서만 쓰이고 사라진다. 요약 3줄과 후보는 계약대로 저장되지만, `decision` 자체와 FAILED로 거절된 출력에서 남는 것은 `agent_analysis_failed` 로그의 실패 사유 코드뿐이다 — 감사 공백으로 인정한다. `decision`을 `AgentGraphOutput`이나 DB로 옮기는 것은 공개 계약·마이그레이션 변경이라 이 개정과 구현 이슈(#583)의 범위 밖이며 후속 결정이다. 교차 검증 분류기를 두면 그 불일치는 진단 메타데이터(분류 라벨과 확률)로만 기록하고, 모델 텍스트와 거절된 출력은 보존하지 않는다(미보존 대상 불변).
   - **이유** — 요약 3줄은 사람 개입 승인(human-in-the-loop)을 위한 "CoT 3줄" 구상에서 출발했다. CoT는 보여 줄 수 없으므로 3줄은 근거 줄이 됐다. 결정보다 먼저 생성된 근거는 결정의 조건이 될 수 있지만, 결정 뒤에 생성된 텍스트는 이미 내려진 결정을 설명할 뿐이다. 2026-11-05 모델 비교(후보 12개 × SecOps 7케이스, SecOps 167회 실행)의 위험도 규칙 위반 6건이 그 사례다. 등급은 등급만 내는 호출에서 나왔다(`RiskReassessmentOutput`의 필드는 `reviewed_risk_level` 하나뿐). rationale 줄은 그 뒤의 요약 호출이 썼고, 그 호출은 주어진 등급을 유지하도록 지시돼 있다(`_SECOPS_SUMMARY_PROMPT`). 요약은 사실("한 조건만 충족")을 바르게 적으면서 틀린 등급을 그대로 옮겼다. 이 실험이 보여 주는 것은 둘이다 — (a) 등급만 내는 모델 호출이 167회 중 6회 산술을 어겼다. (b) 설명 호출은 틀린 결정을 바른 사실로 충실히 설명했다 — 사후 설명의 문제 그 자체다. 6건을 모두 잡았을 것은 등급이 모델에서 나오지 않는 것(또는 reviewed==initial 검사)이지 decision↔후보 대응 검사가 아니다. 그래서 이 개정은 등급을 모델 호출에서 빼고(위 결정), 결정을 근거 뒤에 둔다.

### 요약 호출의 입력

근거 호출(`summarize_evidence`)이 받는 것과 받지 않는 것:

- **역할** — 3줄은 승인하거나 차단하는 관제자를 위한 것이다.
- **판정은 사실로** — FinOps `verdict`와 SecOps `initial_risk_level`은 서버가 낸 사실로 주어진다. 모델은 이를 다시 판정하지 않는다.
- **사실** — 집계된 횟수, 관측 창, evidences, 자산 상태. SecOps는 여기에 `isolation_execution`(선행 격리 상태와 영향 범위)과 관측 창·근거 출처·사본 시점을 받는다.
- **FinOps `skip_reason_code`는 싣지 않는다** — 인시던트가 되는 것은 COST_CANDIDATE·UNUSED뿐이고(`packages/schemas/intake.py`), `RuleEvaluationResult`는 SKIP이 아니면 사유를 금지하므로 인시던트에서는 항상 null이다.
- **메뉴는 목적 문구만** — `available_actions`는 이 자산에 대한 capability의 목적 문구(Vigilantis가 여기서 실행할 수 있는 것)다. Runbook ID, 파라미터 명세, 대상 ARN 목록은 싣지 않는다 — 이것들은 실행 계획 단계에만 간다. 근거는 #243 실측이다(기록: `apps/core-api/ai/agent.py` 머리 주석). 메뉴 없이 쓴 rationale의 31/60이 카드에 없는 조치를 권했다. Runbook 이름을 주자 요약이 메뉴를 열거해 후보 노드가 언급된 Runbook을 전부 담았고(후보 2건 35/60), 목적 문구만 싣는 것으로 고쳤다 — 이 35/60은 이름 노출의 결과이며 후보 2건이 결함이라는 근거가 아니다. #243이 보여 준 것은 메뉴 밖 조치의 감소이지 제안 편향이 없다는 것이 아니다 — 메뉴가 비어 있지 않은 상태에서의 타당한 무제안이 평가셋에 있어야 한다.
- **제품 설명 없음** — Vigilantis 자체에 대한 설명은 싣지 않는다.

### 실행 계획 단계

- 실행 계획 단계(FinOps는 모델 호출, SecOps는 코드)는 근거 3줄 + `decision` + 전체 capabilities(ID, 파라미터 명세, 허용 대상)와 원래의 타입 입력(evidence ID, 자산 맥락)을 받아 `decision`을 `runbook_id` · `target_arn` · `evidence_ids` · `parameters`로 전사한다. 근거 3줄만 받는 것이 아니다.
- **다른 조치로 대체할 수 없다** — 보장 ②의 대응 규칙이 대체를 불가능하게 한다. 이는 #324의 불일치(요약은 A, 후보는 B)에 대한 구조적 해결이다.
- **결과 판정**:

  | 실행 계획의 결과 | `invocation_status` | 출력 |
  | --- | --- | --- |
  | 결정된 조치가 실현됨 | SUCCEEDED | 근거 3줄 + 후보(결정된 조치 수만큼) |
  | 조치 없음으로 결정 | NO_PROPOSAL | 근거 3줄 + 빈 후보 |
  | 실현 불가 또는 대응 불일치 | FAILED | 현 계약대로 빈 요약·빈 후보·`reviewed_risk_level` null(`AgentGraphOutput`) |

  FAILED에서는 근거 3줄이 사라진다. 지금은 받아들이는 비용이며, 근거 3줄을 보존하는 실패 상태는 계약 변경이 필요한 후속 결정이다.
- **"실현 불가"는 코드의 결과다** — 모델이 쓰는 판정이 아니다. 기존 사유 코드(`TARGET_NOT_ALLOWED`, `SERVER_PARAMETER_UNAVAILABLE`, `CANDIDATE_CONTRACT_VIOLATION`)를 쓰며, SecOps 조립 경계 사례의 사유 코드는 구현 이슈(#583)에서 정한다.
- **출력 전체를 거절한다** — 후보 하나만 떨어뜨리지 않는다.
- **재시도는 결정을 다시 고르지 않는다** — 실행 계획 단계를 재시도하는 동안 받아들인 근거와 `decision`은 고정된다. 다른 조치를 얻으려고 선택을 다시 돌리지 않는다.
- 가드레일·승인·실행은 그래프 밖에 남는다(원칙 3 불변). 근거 호출에 주는 메뉴는 제안이지 실행 허용의 보장이 아니다. 가드레일 ④는 범위가 한정된 사전 검사(DryRun·전제 조건 — [ADR-0007](0007-guardrail-dryrun-executor-precheck-contract.md))이며 실행 성공이나 모든 IAM 권한을 확정하지 않는다. 4단계 전부와 그 실패 처리는 바뀌지 않는다.

### 원칙 5가 정하지 않는 것

다음은 원칙 5 아래의 구현 선택이며 이 ADR이 정하지 않는다.

- 호출 수 — 위 "호출 수는 비규범이다" 참조
- 모델 선택
- 선택적 독립 교차 검증 — 같은 제시/무제시 질문에 답하는 폐쇄형 분류기. 권고용이다 — 불일치는 진단 메타데이터(라벨과 확률)로 기록할 뿐 거부권이나 상태 변경이 되지 않는다(위 "보존"). 분류기가 받는 입력(같은 사실만, 또는 근거 3줄까지)은 구현 이슈(#583)에서 정하며, 독립성은 이 선택에 달려 있다
- 선택적 설명·비평 단계

노드명은 계속 비규범적이다.

미보존 대상:

| 항목 | 이유 |
| --- | --- |
| Prompt 전문·원본 응답 | 재호출마다 변동하는 텍스트는 감사 근거로 부적합 — 로그 레벨과 무관하게 저장·출력하지 않는다 |
| 모델의 내부 추론 텍스트 | 검증·재현 불가 — 후보 정당성은 `evidence_ids` 참조 검증으로 대체. 팀 문서가 "CoT 3줄 요약"이라 부르는 최종 요약(`Incident.summary_lines`)은 저장·노출 대상이며 여기서 말하는 미보존 대상이 아니다 |
| 단가·계산된 비용 | 토큰 수는 사용량 집계용이며 청구 비용의 근거가 아니다(캐싱·할인·요금제 차이) |

노드 분할과 호출 수명주기 상세는 구현 단계에서 정한다.

## 대안과 기각 이유 (1차 개정)

| # | 대안 | 기각 이유 | 근거 |
| --- | --- | --- | --- |
| 1 | `reviewed_risk_level`에 서버 `initial_risk_level` 값을 복사 | 서버 값을 AI "정밀 평가"로 보이게 해 사실과 다르다 | 출력 계약은 null을 허용한다(`AgentGraphOutput`). 웹 앱의 카드·종료 대화상자는 값이 없으면 초기 등급으로 대체 표시하고, 상세 화면의 재평가 행은 "정밀평가 없음"을 보인다 — 그 표기는 개정과 함께 바꾼다(Consequences) |
| 2 | SecOps 요약을 후보 뒤에 두는 현행 순서 유지 | 요약이 실제 후보를 설명하긴 하지만 결정의 조건이 되지 못한다. 요약↔후보 일치라는 같은 목표는 `decision` 필드와 코드 대응으로 달성된다 | 2026-11-05 비교에서 설명 호출이 틀린 등급을 바른 사실로 충실히 설명했다(설계 원칙 5 "이유") |
| 3 | `decision`을 정확히 하나로 제한 | 대상이 서로 다르거나 함께 실행해야 하는 조치를 표현할 수 없다 | #243의 후보 2건 35/60은 Runbook 이름 노출의 결과이지 2건이 결함이라는 근거가 아니다. 현 FinOps 후보 프롬프트가 그 경우를 허용한다 |
| 4 | 모델이 "실현 불가"를 출력 | 검증할 수 없는 도피구가 된다 — #243이 막은 NO_PROPOSAL 도피와 같은 종류다 | 코드가 기존 사유 코드로 판정할 수 있다("실행 계획 단계") |

## Consequences (결과·트레이드오프)

**장점**

- 도메인별 출력 불변식을 그래프 단위로 강제 → 계약 위반 조기 노출
- 업무 상태 원천이 PostgreSQL 단일 → 재시작 복구 경로 단일화
- `FakeAIModelClient` 주입으로 실제 API 없이 두 경로 검증 가능
- 후보가 참조한 근거를 계약으로 검증 가능 → 판단 경위 설명 가능
- (1차 개정) 세 확인 차원이 분리된다 — 요청 스키마의 속성 순서는 스키마 순서 테스트로, decision↔후보 대응은 코드의 대응 규칙과 실패 사유로, 근거의 뒷받침은 평가 측정으로 확인한다
- (1차 개정) SecOps 위험 등급이 모델 호출에서 나오지 않는다 — 2026-11-05 비교의 규칙 위반 6건이 생긴 경로가 없어진다

**바뀌는 것(1차 개정)**

- SecOps 정상 경로 모델 호출은 3회에서 1회가 된다. FinOps는 2회다. 호출 수는 비규범이다(Decision 참조)
- SecOps 출력의 `reviewed_risk_level`은 null이 된다. 과거 행의 AI 재평가 값은 그대로 남는다

**비용/유의**

- 호출 중 프로세스 종료 시 남은 Claim을 회수한 뒤 처음부터 재호출 — 부분 재개 미지원. 회수·재시도 규칙은 호출 수명주기 결정에서 정한다
- Prompt 미보존으로 과거 판단을 그대로 재현할 수 없음 — 입력 snapshot 재호출 시 결과 상이 가능
- 공통 노드 미추출 시 두 그래프에 중복 발생
- 그래프 내부 State를 `packages/schemas` 계약과 분리해 별도 정의 필요
- 그래프 호출 중복은 DB Claim으로 막지만 Scheduler·Dispatcher의 인메모리 상태는 별개 문제 — 다중 worker·replica 실행 토폴로지는 **별도 결정 대상**
- LLM 운영비 지표는 **MVP 제품 기능 제외** — 필요 시 로그의 토큰 사용량을 집계해 오프라인으로 추정
- 노드명과 세부 분할은 비규범적이라 개정 대상이 아님. 다만 도메인 분리·영속성·부수효과(노드의 DB·AWS 접근)·감사 경계를 바꾸는 변경은 **이 ADR의 개정 대상**
- (1차 개정) 그래프 내부 모델 `EvidenceSummaryOutput`(외부 계약이 아니다)에 `decision` 필드가 추가되고, 운영 로그 분류 `AnalysisFailureReason`에 새 실패 사유가 생긴다(이름은 구현 이슈(#583)에서 정한다, 제안: `DECISION_MISMATCH`). 공개 출력 계약 `AgentGraphOutput`은 이 개정으로 바뀌지 않는다
- (1차 개정) `decision` 미보존에 따른 감사 공백과, 실현 불가·대응 불일치 FAILED에서의 근거 3줄 손실을 받아들인다 — 둘 다 해소하려면 계약 변경이 필요한 후속 결정이다
- (1차 개정) 요약 출력 스키마가 두 도메인에 공유되므로 FinOps·SecOps 모두 기준선을 다시 잡아야 하며, 과거 품질 수치는 이력으로만 남고 이어지지 않는다
- (1차 개정) `reviewed_risk_level`의 웹 앱 "정밀 평가" 표기와, 이 값이 null이 아니어야 통과하는 평가·테스트는 함께 바뀌어야 한다
