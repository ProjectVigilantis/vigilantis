# ADR-0013: 플랫폼 활동 로그 — 고칠 수 없는 한 테이블, 계약으로 정한 행동, 두 가지 쓰기 규칙

- **Status**: Proposed (2026-11-24 — 리뷰에서 승인되면 Accepted 로 바꾼다)
- **Date**: 2026-11-24
- **Deciders**: 김세혁(PM — 2026-11-06 회의에서 범위와 담당 결정) / 김승철(계약 · 테이블 · 기록 함수 · 조회 API) / 안성일(기록 호출 분담 동의, 2026-11-11)

## Context (배경)

2026-11-02 기준으로 플랫폼에서 일어난 일을 한곳에서 볼 수 없었다.

- **기록이 네 곳에 흩어져 있었다.** 조치 승인과 종료 판단은 `audit_events`, 사용자 · 직원 관리는 `user_admin_events`, 문의는 `inquiry_events`, 도입 신청 판단은 `signup_request_decisions` 에 남았고 모양이 제각각이었다.
- **아예 남지 않는 일이 있었다.** 고객사 등록 · 수정 · 정지 · 재개 · 연결 확인의 행위자, 로그인 실패와 MFA 실패, 권한 거절(403 · 범위 밖 404), 접속지 주소와 브라우저 정보.
- **ISMS 보고서와 사고 조사 페이지가 읽을 근거 로그가 필요했다**(#488 · #622 · #623). 그 원천은 일어난 사실만 담아야 한다.

기존 테이블에 칸을 더하는 길은 택하지 않았다. 네 테이블은 각자 업무 외래키와 제약을 갖고 있어, 로그인 실패나 권한 거절처럼 업무 행이 없는 일을 담을 자리가 없다.

## Decision (결정)

**플랫폼 활동은 새 테이블 `platform_events` 한 곳에 한 건 한 행으로 남긴다.** 기존 기록 테이블은 없애지 않고 그대로 쓴다. 같은 일은 두 곳에 남는다.

### 1. 테이블 — 추가만 된다

- DB 트리거(`platform_events_append_only`)가 UPDATE 와 DELETE 를 거절한다. `audit_events` · `user_admin_events` · `inquiry_events` · `signup_request_decisions` 와 같은 방식이고, 이로써 수정 · 삭제를 막는 테이블은 다섯이다.
- 행위자(`actor_user_id`)만 외래키를 둔다. 고객사(`tenant_id`) · 세션 · 대상(`target_id`)에는 외래키를 두지 않는다. 대상이 지워져도 「그 일이 있었다」는 행이 남아야 하기 때문이다.
- 행위자의 계정 종류와 플랫폼 등급은 **기록 시점의 값**을 행에 복사한다. 뒤에 등급이 바뀌어도 그때 값이 남는다.
- 넣지 않는 것: 비밀번호 · 토큰 · 세션 원문 · TOTP 비밀 · ExternalId · AWS 자격. 이메일 같은 개인정보는 복사하지 않고 `actor_user_id` 로 잇는다. 없는 계정으로 로그인을 시도하면 입력한 이메일은 남기지 않고 `ANONYMOUS` · 사유 코드 · 접속지만 남긴다(#589 Q5).

### 2. 행동은 계약이 정한다

- `action` 칸은 DB enum 이 아니라 문자열이다(#589 Q2). 행동이 기능마다 늘어나는데 enum 이면 값마다 마이그레이션이 든다.
- 대신 `packages/schemas/platform_events.py` 의 `ACTION_SPECS` 가 단일 원천이다. 행동마다 분류 · 허용 결과 · 허용 행위자 · 대상 종류 · `details` 모델이 하나씩 정해져 있고, 목록 밖 행동이나 맞지 않는 `details` 는 기록 함수가 거절한다.
- 행동 이름에 성공 · 실패를 넣지 않는다. 결과는 `outcome`(`SUCCEEDED` · `DENIED` · `FAILED`) 칸이 말한다.
- 기준 커밋의 계약은 **9분류 44행동**이다.

| 분류 | 행동 수 | 분류 | 행동 수 |
| --- | --- | --- | --- |
| `TENANT_ADMIN` | 10 | `ACTION` | 5 |
| `USER_ADMIN` | 8 | `SUPPORT` | 5 |
| `INCIDENT` | 7 | `ACCESS` | 2 |
| `AUTH` | 5 | `COLLECTION` · `NOTIFICATION` | 각 1 |

- 새 행동이나 `details` 변경이 필요한 PR 은 그 PR 에서 계약 파일을 함께 고치고 계약 담당이 리뷰한다(2026-11-11 합의).
- FE 타입(`apps/web/src/types/api.ts`)과의 일치는 테스트가 CI 에서 견준다(PR #658).

### 3. 쓰기 규칙 둘

| 경우 | 방식 | 함수 | 실패하면 |
| --- | --- | --- | --- |
| 상태가 바뀌는 일 | 그 변경과 **같은 트랜잭션** | `platform_events_repo.record_platform_event` | 변경도 함께 되돌린다 |
| 거절 · 실패 | **따로 짧은 트랜잭션** | `platform_event_log.record_detached` | 응답은 그대로 나가고 앱 로그에만 남는다 |

- 거절 · 실패를 따로 쓰는 이유는 요청 트랜잭션이 되돌려져도 「거절됐다」가 남아야 하기 때문이다.
- 기록은 이 두 함수로만 한다. 요청 문맥(세션 · 요청 ID · 접속지 · 브라우저 정보)은 함수가 채우고, 기능 코드는 행동 · 대상 · `details` 만 넘긴다.
- 멱등 재요청(같은 키의 200 재생)은 새 행을 만들지 않는다.
- 시스템 루프는 회차 · 건 단위로 남긴다. 자산 하나하나는 남기지 않는다. 수집은 (고객사, 리전)의 직전 회차와 상태가 달라질 때만 한 행을 남긴다. 5분마다 도는 수집이 로그를 덮지 않게 하려는 것이다.

### 4. 권한 거절

- 403 은 공통 오류 처리기가 한 자리에서 남긴다(`ACCESS_FORBIDDEN`). 싣는 것은 메서드와 경로뿐이고 질의 문자열과 본문은 싣지 않는다.
- 범위 밖 404(`ACCESS_OUT_OF_SCOPE`)는 「있는데 범위 밖」인 것만 남긴다. 없는 ID 를 연 것은 남기지 않는다(#589 2026-11-12 코멘트의 방식). 오타나 무작위 ID 로 행이 불어나지 않고, 이 행의 뜻이 「남의 것을 열려 했다」로 유지된다.
- 범위 밖 404 의 행은 **응답을 보낸 뒤에** 쓴다. 응답 전에 쓰면 범위 밖일 때만 쓰기가 끼어 응답 시간으로 그 ID 가 있다는 것이 드러난다. 그 사이 프로세스가 내려가면 행은 빠진다.

### 5. 접속지

- 앱은 `X-Forwarded-For` 를 읽지 않는다. 앞부분을 클라이언트가 꾸밀 수 있다.
- 운영 배포에서는 CloudFront 가 오리진 요청에 싣는 `CloudFront-Viewer-Address` 헤더만 읽는다(#589 Q3, 설정 `CLIENT_ADDRESS_SOURCE=cloudfront-viewer-address`). 기본값은 소켓 주소다.
- 이 설정은 **ALB 가 CloudFront 를 거친 요청만 받는 배포에서만** 켠다(ADR-0010). 헤더가 없거나 둘 이상이거나 형식이 맞지 않으면 접속지는 비워 두고 소켓 주소로 물러서지 않는다.

### 6. 조회

- `GET /api/v1/platform-events`. 필터는 기간 · 분류 · 행동 · 결과 · 행위자 · 고객사 · 대상이고 최신순 커서 페이지다.
- 중앙 관리자는 전부 본다. 고객 담당자는 담당 그룹 고객사의 행과, 고객사 없는 행 가운데 본인 행만 본다(#589 Q4). 범위는 요청마다 `tenant_scope_ids` 로 다시 정한다.
- 본인 행은 내가 한 일의 행과 **내 계정이 대상인 인증(`AUTH`) 행**이다. 로그인 · MFA · 비밀번호 재설정 시도는 행위자가 `ANONYMOUS` 라서, 행위자로만 고르면 내 계정에 일어난 인증 시도가 빠진다.
- **범위 밖 404(`ACCESS_OUT_OF_SCOPE`) 행은 중앙 관리자만 읽는다**(#589 2026-11-13 · 2026-11-16 코멘트). 담당자 조회에서는 담당 고객사의 행과 본인 행 두 갈래 모두에서 빠지고, `action` 필터로 골라도 나오지 않는다. 행이 있다는 것만으로 그 ID 가 있다는 답이 되므로, 낸 사람과 그 고객사의 담당자에게도 보이면 안 된다. §4 가 응답 시간을 막은 것과 같은 목적이다. 2차에 고객사 계정의 조회를 열 때도 이 조건을 유지한다.
- 범위 밖이거나 형식이 어긋난 필터 값은 404 가 아니라 빈 목록이다. 존재를 알리지 않는다.
- 고객사 계정은 403 이다(2차 범위).

## Consequences (결과)

**얻은 것**

- 로그인 실패 · 권한 거절 · 고객사 관리처럼 남지 않던 일이 남는다. 접속지는 2026-11-20 실 플랫폼에서 실제 클라이언트 주소로 남는 것을 확인했다.
- ISMS 보고서 · 사고 조사 · 신고 초안이 한 테이블을 근거로 읽는다.

**치르는 것과 남은 한계**

- **같은 일이 두 테이블에 남는다.** 기존 기록 테이블과 `platform_events` 가 어긋날 수 있는 자리가 생긴다. 같은 트랜잭션에 쓰는 것으로 막는다.
- **「행동마다 호출이 있다」와 「상태가 바뀌는 자리마다 호출이 있다」는 다르다.** 수용 기준을 행동 단위로 세었을 때 구독 흐름의 정지 두 자리(이용 중단 · 권리 만료)가 빠진 것을 가리지 못했다. PR #678 이 메웠다. 새 상태 변경 경로를 더할 때는 행동이 아니라 자리를 센다.
- **따로 쓰는 행은 빠질 수 있다.** DB 오류나 프로세스 종료로 거절 · 실패 행이 빠지면 앱 로그에만 남는다.
- **범위 밖 404 가운데 두 자리는 시도한 고객사가 행에 남지 않는다.** 유형별 비용은 고객사 ID 를 질의 문자열로, 초대는 본문으로 받는데 질의 문자열과 본문은 싣지 않는다(§4). 1차에서는 조사의 한계로 받아들였다(#589 2026-11-13 · 2026-11-16 코멘트). 남기려면 계약에 검증한 대상 칸을 더해야 한다.
- **의도한 예외**: 로그아웃과 비밀번호 재설정은 같은 트랜잭션이 아니다. 수집의 실패 회차는 그 리전의 별도 트랜잭션에 남는다. 세션 회수와 근거 내보내기는 요청마다 한 행이다.
- **확인하지 않은 것**: 꾸민 헤더와 IPv6 접속지는 실 플랫폼에서 시험하지 않았다.
- **하지 않은 것(2차)**: 보존 기간 규칙 · 보관소 이전 · CSV 내보내기, 고객사 계정의 자기 고객사 로그 조회, 개인정보 조회 기록(사용자 목록 · 상세 열람), 운영 알림 읽음 처리의 범위 밖 기록.
