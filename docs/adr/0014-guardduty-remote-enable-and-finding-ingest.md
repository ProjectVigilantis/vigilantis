# ADR-0014: GuardDuty — 고객 계정에서 원격으로 켜고, 탐지 결과를 주기 조회로 읽고, 자동 대응은 걸지 않는다

## Context (배경)

2026-11-02 기준으로 위협은 전부 모의였다. 위협 유형은 `OPEN_IP` 와 `SSH_BRUTE_FORCE` 둘이고 둘 다 모의 관측이다. 실제 고객 계정에서 생긴 위협을 받는 원천이 하나도 없었다.

GuardDuty 를 원천으로 쓰려면 일이 둘이다. 고객 계정에서 **켜는 일**과, 탐지 결과를 **읽어 인시던트로 잇는 일**이다. 읽는 일은 어느 쪽이든 플랫폼이 고객 역할로 한다. 갈리는 것은 누가 켜느냐였다.

| 안 | 방법 | 걸리는 점 |
| --- | --- | --- |
| A. 온보딩 템플릿이 켠다 | 템플릿 안의 사용자 지정 자원이 리전마다 없을 때만 탐지기를 만든다 | 템플릿이 복잡해진다. 플랫폼 권한은 늘지 않는다 |
| B. 플랫폼이 원격으로 켠다 | 고객 역할에 켜는 권한을 더하고 연결 확인 때 켠다 | 고객 역할에 IAM 쓰기(서비스 연결 역할 생성)가 들어간다 |
| C. 꺼져 있으면 막고 안내한다 | 연결 확인에 검사만 더하고 고객이 직접 켠다 | 고객 쪽 일이 는다 |

조사 단계의 권고는 A 와 C 였다. 2026-11-06 회의는 B 를 택했다.

## Decision (결정)

**플랫폼이 고객 역할로 GuardDuty 를 원격에서 켠다(B). 켤 수 없는 계정은 막고 안내한다(C 를 겸한다). 탐지 결과는 주기 조회로 읽고, 자동 대응은 걸지 않는다.**

### 1. 권한 — 켜고 읽는 것만, 끄는 것은 없다

고객 역할(`vigilantis-access`)의 온보딩 템플릿 정책에 다음만 넣는다.

| 작업 | 쓰는 곳 |
| --- | --- |
| `guardduty:ListDetectors` · `guardduty:GetDetector` | 탐지기 확인 |
| `guardduty:CreateDetector` | 켜기 |
| `guardduty:ListFindings` · `guardduty:GetFindings` | 결과 읽기 |
| `iam:CreateServiceLinkedRole` | 처음 켤 때 생기는 서비스 연결 역할 하나 |

- **끄는 권한은 넣지 않는다**(`DeleteDetector` · `UpdateDetector`). GuardDuty 를 끄면 기존 탐지 결과가 지워지고 되돌릴 수 없다.
- `iam:CreateServiceLinkedRole` 은 대상을 `AWSServiceRoleForAmazonGuardDuty` 역할 하나로, 조건을 서비스 이름 `guardduty.amazonaws.com` 으로 묶는다. 이 모듈은 IAM 을 직접 부르지 않는다. GuardDuty 가 처음 켤 때 호출자에게 이 권한을 요구한다.
- **ADR-0009 와의 관계**: ADR-0009 §4 는 앱 키에 `iam:CreateServiceLinkedRole` 을 주지 않는다고 적는다. 그 서술은 스모크 환경의 Auto Scaling 서비스 연결 역할에 대한 것이고 그대로다. 고객 역할에는 GuardDuty 의 역할 하나에 한해 이 권한을 연다(#588 Q5).
- 고객 템플릿의 GuardDuty 문장에는 리전 조건을 두지 않는다. 관제 리전은 고객사마다 다르고 뒤에 바뀐다. 스모크 환경의 정책에는 리전 울타리가 있다. 두 정책의 작업 목록은 테스트가 코드 호출과 두 방향으로 맞춘다.

### 2. 켜기 — 연결 확인에 묶는다

- 켜는 자리는 연결 확인(`verify` · `resume`) 하나다. 수집 주기에서는 켜지 않는다.
- 관제 리전마다 탐지기를 본다. 없으면 `CreateDetector(Enable=True)` 로 만들고, 있으면 건드리지 않는다.
- **만들 때 부가 보호 기능 8종을 모두 끈 채로 넘긴다.** 생략하면 꺼진 채 남지 않고 대부분이 켜진다. 켜진 기능은 고객 요금으로 나가는데 플랫폼에는 끄는 권한이 없다.
- **정지된 탐지기는 다시 켜지 않는다**(#588 Q1). 고객이 일부러 정지했을 수 있고, 켜려면 쓰기 권한이 더 든다.
- 한 리전이라도 켜지 못하면 연결 확인은 `GUARDDUTY_DISABLED` 로 답하고 고객사를 `ACTIVE` 로 올리지 않는다. 관제 리전을 끝까지 돌아 켜지 못한 리전과 리전별 사유를 전부 싣는다(`guardduty_failures`). 안내 화면이 고객이 켜야 할 리전을 한 번에 보인다.
- 이미 `ACTIVE` 인 고객사는 연결 확인이 실패해도 자동으로 정지하지 않는다. 정지는 사람의 판단이다.
- GuardDuty 요금은 고객 계정에 부과된다. 온보딩 화면과 안내 화면에 그 사실과 30일 무료 체험을 적는다(PR #624).

### 3. 읽기 — 주기 조회와 커서

- 수집 주기(기본 300초)마다 고객 역할로 리전별로 읽는다. EventBridge 로 받지 않는다. 고객 계정에 규칙과 대상 자원이 더 생기기 때문이다.
- `ListFindings` 는 갱신 시각이 커서 이상이고, 이 계정의 것이고, 보관 처리되지 않은 탐지를 갱신 시각 오름차순으로 읽는다. `GetFindings` 는 50건씩 부른다.
- 커서는 (고객사, 읽은 리전)마다 하나다(`guardduty_finding_cursors`).

| 값 | 기본 | 이유 |
| --- | --- | --- |
| 처음 읽는 리전의 거슬러 읽기 | 1일 | 과거 90일치 탐지가 한꺼번에 인시던트가 되지 않게 한다 |
| 한 회차 한도 | 500건 | 넘으면 다음 회차가 같은 조건으로 이어 읽는다 |
| 커서 여유 | 5분 | 플랫폼 시계와 GuardDuty 시계의 차이, 갱신이 목록에 보이기까지의 지연을 덮는다 |

- 커서와 같은 시각의 탐지는 다시 읽는다. 중복은 탐지 ID 로 접는다. 같은 탐지가 갱신돼 다시 들어와도 위협 이벤트는 한 번만 생긴다.
- 계정 조건은 위임 관리자 계정이 멤버 계정의 탐지까지 돌려주는 것을 막는다. 정규화 단계가 계정을 한 번 더 본다. 계정이 다르거나 필수 칸이 없는 탐지는 건별로 거절한다.
- GuardDuty 읽기의 실패는 자산 수집과 따로 기록한다. 읽기가 실패해도 그 리전의 자산 수집은 그대로 간다.
- 저장하는 것은 요약 8칸(탐지 ID · 탐지 분류 · 심각도 · 자원 유형 · 읽은 리전 · 탐지에 표시된 리전 · 최초 · 최근 관측 시각)과 활동 사실 5칸(자원의 역할 · 활동 종류 · 연결 방향 · 상대 IP · 차단 여부)이다. 활동 사실은 칸마다 읽힘 상태를 함께 남긴다(PR #651).

### 4. 위험도와 대응 — 인시던트까지만

| 심각도 | 위험도 | 처리 |
| --- | --- | --- |
| 7.0 이상 | `HIGH` | 인시던트를 만든다 |
| 4.0 이상 7.0 미만 | `MEDIUM` | 인시던트를 만든다 |
| 4.0 미만 | `LOW` | 위협 이벤트만 남긴다 |

- GuardDuty 의 High 와 Critical 은 `HIGH` 하나로 접는다.
- **자동 선차단과 자동 격리를 걸지 않는다**(#588 Q2, 2026-11-09). GuardDuty 탐지는 관측 신호이지 침해 확정이 아니다. ADR-0011 도 GuardDuty 탐지를 자동 대응에서 제외한다.
- AI 조치 메뉴가 없다. 메뉴는 모의 위협 `SSH_BRUTE_FORCE` 에만 정의돼 있어, GuardDuty 인시던트는 모델을 부르지 않고 분석을 `FAILED` 로 마친다.
- 그 사유는 둘로 갈린다. 대상이 수집된 자산이면 「가능한 조치 없음」(`NO_ACTION_AVAILABLE`)이다. 수집된 자산이 아니면(IAM 등 EC2 가 아닌 자원, 수집 범위 밖 인스턴스) 조치 메뉴를 보기 전에 「입력 불가」(`GRAPH_INPUT_UNAVAILABLE`)로 닫힌다. 어느 쪽이든 관제자가 근거를 보고 종료한다.
- 예외 하나: 보호 태그가 붙은 EC2 가 대상이면 서버가 승인 전용 격리 후보를 만든다(#598 · PR #651). 그 밖의 대상은 관제자가 근거를 보고 수동으로 종결한다.

### 5. 샘플 탐지

- **샘플 탐지도 실제 탐지와 똑같이 처리한다.** 수집에는 샘플을 거르는 조건이 없다. 샘플은 탐지 원문의 `additionalInfo` 에 표시될 뿐이다.
- 샘플은 실제 계정 ID 를 쓴다. 그래서 계정 조건에 걸리지 않고 그대로 읽힌다(§6).
- 샘플을 다시 만들면 새 탐지가 생기지 않고 같은 탐지가 갱신된다. 중복 억제로 접힌다(§6).
- 고객이 콘솔에서 유형을 지정하지 않고 샘플을 만들면 지원하는 모든 유형이 하나씩 생겨, 인시던트와 알림이 한꺼번에 나간다.

### 6. 실 계정 확인 (2026-11-24)

학원 계정을 고객으로 연결한 팀 플랫폼(`vigilantis.dev`)에서 확인했다. 단계별 시각과 수치는 #588 의 [2026-11-24 코멘트](https://github.com/ProjectVigilantis/vigilantis/issues/588#issuecomment-7124758415)에 있다.

| 확인한 것 | 결과 |
| --- | --- |
| 이미 켜진 리전(서울) | 연결 확인 때 나간 호출은 조회 둘(`ListDetectors` · `GetDetector`)뿐이다 |
| 꺼진 리전(도쿄) | `CreateDetector` 가 한 번 나가 탐지기가 켜졌다. 다시 확인하면 조회만 나간다 |
| 부가 보호 기능 | 도쿄 탐지기의 부가 기능이 전부 꺼진 채 만들어졌다 |
| 탐지 0건 읽기 | 두 리전 모두 읽기 정상, 0건. 조회 조건(갱신 시각 · 계정 · 보관 여부)을 실 API 가 받는다 |
| 샘플 3건(심각도 2.0 · 5.0 · 8.0) | 위협 이벤트 3건, 인시던트 2건(MEDIUM · HIGH). Low 는 이벤트만 남았다 |
| 자동 대응 | HIGH 인시던트에도 실행과 추천 후보가 없었다 |
| 중복 | 이어진 29주기와 샘플을 다시 만든 뒤에도 새 이벤트 · 인시던트가 생기지 않았다 |

- 두 샘플 인시던트의 분석은 「입력 불가」로 끝났다(§4). 샘플의 대상이 수집된 자산이 아니기 때문이다.
- 도쿄는 확인을 위해 관제 리전에 넣었다가 뺐다. 고객 템플릿에 리전 조건이 없어 도쿄에서도 거절되지 않았다(§1). 그래서 켜지 못하는 경우(`GUARDDUTY_DISABLED`)는 실 계정에서 보지 못했다.

## Consequences (결과)

**얻은 것**

- 실제 고객 계정의 위협을 받는 원천이 하나 생겼다. 고객이 GuardDuty 를 따로 켜지 않아도 연결 확인 한 번으로 켜진다.
- 켤 수 없는 계정(조직 관리 · 권한 상한 정책 · 정지된 탐지기)은 연결 단계에서 드러난다.

**치르는 것과 남은 한계**

- **고객 역할에 IAM 쓰기가 하나 들어간다.** 대상과 조건으로 좁혔지만 A 안에는 없던 권한이다.
- **플랫폼은 끌 수 없다.** 켠 탐지기를 지우거나 정지하는 일은 고객이 한다. 관제 리전에서 뺀 리전의 탐지기도 남는다.
- **탐지에 대응하는 길이 좁다.** 보호 태그 EC2 를 빼면 실행 후보가 없어, 관제자가 할 수 있는 일은 근거 확인과 수동 종결이다.
- **IAM 유형 탐지의 사실은 거의 읽지 않는다.** 사용자 · 액세스 키 · 호출 IP · 호출 API 는 저장하지 않는다. API 호출로 생긴 탐지에는 네트워크 연결 정보가 없어 활동 사실 5칸 가운데 셋이 비어 남는다. 읽으려면 계약에 칸을 더해야 하고, 사용자 이름과 액세스 키 ID 를 어디까지 남길지 먼저 정해야 한다.
- **같은 탐지의 갱신분은 저장하지 않는다.** 탐지가 다시 관측돼 갱신 시각과 발생 횟수가 바뀌어도 처음 저장한 위협 이벤트는 그대로다.
- **마지막 탐지와 같은 시각의 탐지는 주기마다 다시 읽힌다.** 커서가 「이상」 조건이라서다. 실 계정에서 29주기 동안 같은 3건을 매번 다시 읽고 중복으로 접었다.
- **실 계정에서 확인하지 못한 것**: 서비스 연결 역할이 처음 생기는 경로(학원 계정에는 역할이 이미 있다), 켜지 못하는 경우의 응답과 안내 화면, 500건 한도를 넘는 이어 읽기, 글로벌 서비스 탐지의 리전 표기(IAM 유형 샘플도 서울로 왔다), `LOW` 로 남은 탐지가 뒤에 `HIGH` 가 되는 빈도, 수집된 EC2 가 대상인 탐지의 「가능한 조치 없음」 경로.
- **하지 않은 것**: 실시간 수신(EventBridge), 부가 보호 기능 켜기, 탐지에 대한 자동 대응, 「GuardDuty 를 켰다」를 활동 로그의 별도 행동으로 남기는 일(연결 확인 행으로만 남는다).
