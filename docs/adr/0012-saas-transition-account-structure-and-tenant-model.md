## Context (배경)

확정 결정은 아직 **「AWS 단일 계정」**이다(SSOT §MVP 확정 범위 · 결정 로그 2026-10-12 「MVP는 단일 계정 그대로, Post-MVP는 SaaS로 전환」). [ADR-0009](0009-real-aws-smoke-environment.md)는 「새 전용 계정은 만들지 않는다 · 대상 계정은 학원 제공 계정」을, [ADR-0010](0010-platform-deployment-saas-shape.md)은 **「단일 계정이지만 SaaS 모양으로」**를 전제로 썼고, 둘 다 테넌트 분리 · 원격 회수 · 고객별 역할은 **「후속 SaaS 설계에서 정한다」**로 비워 뒀다. 그 후속 설계가 이 ADR이다.

이 결정 없이 Post-MVP 11주차 카드가 이미 움직이고 있다.

- **T-4 고객 계정 연결**(#485 · PR #489 계약 머지 10/19, PR #506 테넌트 테이블 머지 10/21)은 「ADR이 다르게 정하면 고친다」는 조건으로 먼저 들어갔다.
- **T-8 플랫폼 이전**(#494 · 김세혁)은 플랫폼을 어느 계정에 둘지가 전제다.
- **T-1 로그인 · 역할**(#492 · 안성일)은 「누가 어느 테넌트를 보는가」를 이 ADR의 테넌트 모델 위에서 정한다.

바탕이 되는 사실 셋.

1. **계정 구조는 2026-10-16 PM이 정했고, 조직을 넘는 연결은 같은 날 실측으로 통과했다**(#438 §C-1). 학원 계정에 신뢰 정책(개인 계정 + `ExternalId`)만 있는 시험 역할을 만들어 개인 계정에서 assume에 성공했고, `ExternalId` 없이는 `AccessDenied`였다. 학원 조직의 상위 정책은 조직 밖 AssumeRole을 막지 않는다.
2. **지금 앱은 「프로세스 하나에 역할 하나」다.** 운영 진입점(`apps/core-api/serve.py`)이 기동 때 접근 역할 프로필 하나를 잡고, `services/aws/client.py`의 `aws_client`가 그 자격을 그대로 쓴다(세션 기본 900초). 테넌트 개념은 PR #506 전까지 코드에 없었다.
3. **시연 고객은 실계정 1개(학원)다.** 두 번째 고객 계정은 확보 근거가 없다. 그래서 「고객이 여럿이어도 섞이지 않는다」는 주장은 **T-5 테넌트 격리 회귀 테스트**(목록 · 상세 · 실행 세 경로)가 유일한 근거다(#479 §1-2).

## Decision (결정)

**플랫폼과 고객을 서로 다른 AWS 계정으로 가르고, 플랫폼은 고객이 내준 역할에 AssumeRole + ExternalId로만 들어간다. 테넌트 하나 = 고객 AWS 계정 하나이며, 원격 회수는 「그 계정에 더 들어가지 않는 것」이다. 데이터는 뿌리 테이블의 `tenant_id`로 테넌트에 묶는다.**

### 1. 계정 구조 — 관리 · 플랫폼 · 고객 셋

| 계정 | 소속 조직 | 역할 |
| --- | --- | --- |
| 김세혁 개인 관리 계정 | 개인 조직(관리 계정) | Organizations 관리만. **워크로드를 두지 않는다**(관리 계정이 뚫리면 조직 전체가 넘어간다) |
| 플랫폼 멤버 계정(신설 · T-8 #494) | 개인 조직 | core-api · DB · 웹. 고객 계정에 들어가는 주체인 ECS 태스크 역할 `vigilantis-platform`이 여기 있다 |
| 고객 계정(시연 = 학원 계정) | 고객 조직(별개) | 관제 · 조치 대상. 고객이 내주는 역할 `vigilantis-access`만 둔다 |

- 플랫폼을 멤버 계정으로 따로 두는 이유는 둘이다 — 그 계정의 청구액이 곧 플랫폼 비용이 되어 **학원 청구 근거가 정확해지고**, 개인 조직의 다른 워크로드와 **피해 범위가 갈린다**(#438 §C-1).
- 수집 · 판정 · 실행 기록은 전부 팀 소유다. 고객 계정에서 나가는 API 호출(CloudWatch 조회 등)은 assume한 자격으로 나가므로 **고객 계정에 과금**된다.
- **AWS Marketplace 결제는 보류다**(#438 §B · 법인 · 세금 · 심사 요건). 구독 상태는 **운영자가 수동으로** 관리한다(T-16 · 계약의 `subscription` 칸).

### 2. 고객 접근 — 역할 전환만, 테넌트 문맥 없이는 나가지 않는다

- **장기 키는 받지 않는다.** 플랫폼 태스크 역할이 고객 계정의 `vigilantis-access`에 `sts:AssumeRole` + 고객별 `ExternalId`로 들어간다. 고객이 `ExternalId`를 바꾸지 않으며, 플랫폼이 테넌트를 만들 때 한 번 정한다.
- 고객 역할의 **권한은 Action Whitelist 거울 정책**이다 — 코드가 부르는 AWS 작업만 허용한다(ADR-0010 §3의 「빌려 붙인다」를 고객 쪽에 두는 것). 정책은 CloudFormation 템플릿 하나로 고객 계정에 만든다(온보딩 · 구현은 T-4 카드).
- **AWS 호출은 반드시 테넌트 문맥 안에서 나간다.** 수집 · 분석 · 실행 루프와 요청 처리는 「지금 어느 테넌트인가」를 먼저 세우고, `aws_client`는 그 테넌트의 자격을 쓴다. **문맥 없이 부르면 실패해야 한다** — 조용히 플랫폼 자격이나 다른 테넌트 자격으로 나가는 것이 가장 위험한 실패다(김승철 Q2 · 호출부가 50여 곳이라 인자로 넘기는 방식은 누락이 조용하다). 구현 방식(contextvar 등)은 카드 몫이다.
- **세션 상한은 900초(15분)를 유지한다**(ADR-0010 §3). 이 값이 §3 원격 회수의 「이미 발급된 자격의 노출 상한」이다. 자격 캐시 · 갱신 시점(Q3)은 이 상한 안에서 구현이 정한다.
- **가드레일 ③ ARN Match에 「대상 ARN의 계정 = 이 테넌트의 계정」 조건을 더한다.** 테넌트 A의 승인으로 테넌트 B의 자원을 바꾸는 길을 가드레일이 막아야 한다.

### 3. 원격 회수 — `SUSPENDED` = 더 들어가지 않는다

원격 회수는 **플랫폼이 그 고객 계정에 더 들어가지 않는 것**이다. 고객 계정의 역할은 고객 소유라 플랫폼이 지울 수 없다(계약 머리말). 세 겹으로 건다.

| 겹 | 무엇 | 효과 |
| --- | --- | --- |
| ① 앱 | 테넌트 상태를 `SUSPENDED`로(사유 필수) | **즉시** — 루프는 매 회차 상태를 다시 읽는다. 새 수집 · 새 AI 분석 · 새 실행 접수(`POST /actions/execute` → `TENANT_SUSPENDED` 409)를 막는다 |
| ② IAM | 플랫폼 역할의 `sts:AssumeRole` 허용 대상에서 그 고객 역할 ARN을 뺀다 | 새 세션을 못 만든다(앱에 결함이 있어도) |
| ③ 상한 | 이미 발급된 세션은 끊을 수 없다 | 900초가 지나면 끝난다 — §2의 세션 상한이 곧 노출 상한 |

- **진행 중인 실행과 자동 원복은 끝까지 돌린다**(Q4). 중간에 멈추면 고객 자산이 반쯤 바뀐 채 남는다 — 원격 회수의 목적(더 손대지 않기)과 반대다. 막는 것은 **새로 시작하는 것**뿐이다.
- **정지 중에는 연결 확인(`verify`)도 받지 않는다** — 그것도 고객 계정에 들어가는 일이다. 정지 테넌트에 들어가는 길은 **재개(`resume`) 하나**이고, 재개는 연결 확인이 먼저 성공해야 `ACTIVE`가 된다(정지 사이에 고객이 역할을 지웠을 수 있다).
- **기존 기록은 남고 읽을 수 있다.** 고객사 사용자도 **로그인하고 조회 전용으로** 자기 테넌트 기록을 본다 — 원격 회수는 고객 계정 접근을 끊는 것이지 고객이 자기 기록을 못 보게 하는 것이 아니다. 승인 · 실행 · 종료 같은 상태 변경은 거절한다(PR #504가 T-17로 넘긴 물음 1).
- 고객이 해지하면 스택(역할) 삭제를 **안내**한다. 고객이 역할을 지우면 다음 연결 확인이 실패로 남는다.

### 4. 테넌트 모델 — 테넌트 하나 = 고객 계정 하나

- **`tenants` 테이블 하나**가 테넌트의 원천이다. 상태는 `PENDING_CONNECTION` → (연결 확인 성공) → `ACTIVE` ⇄ `SUSPENDED` 셋이고, 연결 확인 결과는 「지금 연결된다」가 아니라 **그 시각에 확인한 결과**로 남긴다(계약 원칙). 칸의 정의와 불변식은 계약(`packages/schemas/api/tenants.py`)과 마이그레이션(PR #506)이 원천이며 여기 복제하지 않는다.
- **계정 ID는 유일하다** — 같은 계정을 두 테넌트로 두면 같은 자산을 두 번 수집 · 조치한다. 계정 · 역할을 바꾸는 길은 없다 — 다른 계정이면 다른 테넌트다. 오입력은 **연결된 적 없는 테넌트를 지우고 새로 만드는 것**으로 고친다.
- **`external_id`는 DB에 평문으로 둔다**(Q5). AWS가 비밀값으로 다루지 않고 목적이 혼동된 대리인(confused deputy) 방지이기 때문이다. 다만 내보내는 자리는 **생성 응답 · 연결 전 온보딩 링크 · 재발급 경로** 셋뿐이고 상세 응답에는 없다.
- **데이터의 소속은 뿌리 테이블 5개의 `tenant_id`로 묶는다** — `collection_runs` · `assets` · `threat_events` · `incidents` · `action_executions`. 나머지는 FK로 따라온다(Q1). **기존 행은 `NULL`로 두고, `NULL` = MVP 단일 계정 기록이다.** 마이그레이션이 기본 테넌트를 지어내지 않는다 — 그 시점에는 계정 ID · 역할 · `ExternalId`가 없어 「연결 확인 없는 `ACTIVE`」라는 거짓 기록이 되기 때문이다(PR #506 리뷰 포인트 1). 학원 테넌트가 관리자 API로 생성 · 연결 확인을 마친 뒤 그 테넌트로 채우고 `NOT NULL`로 바꾼다(뒤 카드).
- **사용자의 소속은 `app_users.tenant_id` 하나**다 — 한 사용자 = 테넌트 하나, 소속은 만들 때 정하고 옮기지 않는다(옮기면 남의 기록을 보게 된다). **`NULL`은 「소속 없음」이지 권한이 아니다** — 누가 플랫폼 운영자인지는 T-1(#492)이 따로 표시한다(PR #504 정정 · PR #506). 고객사 사용자는 **테넌트가 `ACTIVE`가 된 뒤에만 초대한다** — 연결 전 테넌트는 지울 수 있어야 하는데 사용자가 있으면 FK가 삭제를 막는다(PR #504가 넘긴 물음 2).
- **모든 조회와 실시간 이벤트는 테넌트 범위다.** 목록 · 상세 · 실행 세 경로(T-5)에 더해 WebSocket도 **범위 밖 이벤트를 보내지 않는다**(지금은 큐 하나로 모든 연결에 같은 이벤트가 간다 — 네 번째 누출 경로). 범위를 요청에 싣는 방법은 T-1이 정한다. 플랫폼 운영자는 전부 본다.
- **수집 범위는 테넌트 칸(`regions` · `collect_vpc_ids`)이 원천이다.** 플랫폼이 별도 계정으로 가면 ADR-0010 §6 `COLLECT_VPC_IDS`의 원래 이유(단일 계정에서 플랫폼 자원을 수집에서 빼기)는 사라진다 — 전역 값은 학원 테넌트가 연결되면 그 칸으로 옮긴 뒤 **지운다**(둘이 남으면 어느 쪽이 이기는지가 문제가 된다). 보호 태그 · 판정 임계치는 이번엔 전역 그대로다(T-7 이후).

| ADR-0010 §3 권한표 「후속 SaaS 설계 후보」 열 | 후보 | **확정** — `vigilantis-platform`의 AssumeRole 대상은 고객별 역할 ARN 목록, `vigilantis-access`는 고객이 CloudFormation으로 만드는 역할. 원격 회수 방식과 노출 상한은 §3 | 같은 2차 개정 |
| ADR-0010 §6 「`COLLECT_VPC_IDS` 존치 여부는 후속 설계에서」 | 미정 | **테넌트 칸으로 옮기고 전역은 폐기**(§4) | 같은 2차 개정 |

ADR-0009 · ADR-0010의 본문 개정은 **플랫폼 이전(T-8)이 실제로 끝난 뒤** 그 결과로 쓴다 — 이전 전에 「옮겼다」고 적으면 문서가 코드보다 앞서 간다.

### 6. #485 계약과의 대조

**계약과 다르게 정한 것은 없다.** 계약이 비워 둔 두 물음(PR #504)을 §3·§4에서 정했다 — 정지된 테넌트의 고객사 사용자는 **로그인 · 조회 전용**, 고객사 사용자 초대는 **`ACTIVE` 뒤**. 계약이 이 둘과 어긋나면 계약을 고친다(#485 수용 기준 마지막 항목).

## Consequences (결과 · 트레이드오프)

**얻는 것**

- 「AWS 단일 계정」이라는 확정 결정과 코드(PR #489 · #506)의 어긋남이 사라진다. T-4 구현 카드 · T-8 이전 · T-1 범위가 **같은 전제** 위에 선다.
- 원격 회수가 세 겹이라 한 겹(앱 상태)에 결함이 있어도 IAM과 세션 상한이 남는다.
- 테넌트 문맥 강제로 「어느 고객 자격으로 나갔는지 모르는 호출」이 구조적으로 생기지 않는다.

**비용 · 유의**

- **기존 기록의 `tenant_id`가 `NULL`인 구간**이 생긴다 — 학원 테넌트 연결 전까지 대시보드는 「소속 없는 기록」을 보여 준다. 채우기 · `NOT NULL` 전환 카드가 닫혀야 T-5가 뜻 있는 테스트가 된다.
- **고객 분리의 근거는 테스트뿐**이다(시연 고객 1개). T-5가 세 경로 + WebSocket을 전부 덮지 못하면 「섞이지 않는다」를 증명하지 못한다.
- ADR-0009 · ADR-0010의 본문 개정이 T-8 뒤로 밀리므로, 그때까지 두 문서의 「단일 계정」 서술과 이 ADR이 **같이 살아 있다.** 읽는 사람은 이 ADR §5를 기준으로 읽는다.
- 세션 900초는 ADR-0011의 선차단 3초 목표와 무관하지만, 테넌트별 세션이 늘면 STS 호출 한도 · 비용을 아직 재지 않았다(김승철 §7). 시연은 고객 1개라 지금은 문제가 아니다.
- 플랫폼 운영자 표시(T-1) · 조회 범위를 요청에 싣는 방법 · 온보딩 템플릿 호스팅은 **이 ADR이 정하지 않는다.** 구현 카드가 정하고, 16주차 상세 ADR이 그 결과를 적는다.
