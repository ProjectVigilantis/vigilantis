## Context (배경)

확정 결정은 아직 **「AWS 단일 계정」**이다(SSOT §MVP 확정 범위 · 결정 로그 2026-10-12 「MVP는 단일 계정 그대로, Post-MVP는 SaaS로 전환」). [ADR-0009](0009-real-aws-smoke-environment.md)는 「새 전용 계정은 만들지 않는다 · 대상 계정은 학원 제공 계정」을, [ADR-0010](0010-platform-deployment-saas-shape.md)은 **「단일 계정이지만 SaaS 모양으로」**를 전제로 썼고, 둘 다 테넌트 분리 · 원격 회수 · 고객별 역할은 **「후속 SaaS 설계에서 정한다」**로 비워 뒀다. 그 후속 설계가 이 ADR이다.

이 결정 없이 Post-MVP 11주차 카드가 이미 움직이고 있다.

- **T-4 고객 계정 연결**(#485 · PR #489 계약 머지 10/19, PR #506 테넌트 테이블 머지 10/21)은 「ADR이 다르게 정하면 고친다」는 조건으로 먼저 들어갔다.
- **T-8 플랫폼 이전**(#494 · 김세혁)은 플랫폼을 어느 계정에 둘지가 전제다.
- **T-1 로그인 · 역할**(#492 · 안성일)은 「누가 어느 테넌트를 보는가」를 이 ADR의 테넌트 모델 위에서 정한다.

바탕이 되는 사실 셋.

1. **계정 구조는 2026-10-16 PM이 정했고, 조직을 넘는 연결은 같은 날 실측으로 통과했다**(#438 §C-1). 학원 계정에 신뢰 정책(개인 계정 + `ExternalId`)만 있는 시험 역할을 만들어 개인 계정에서 assume에 성공했고, `ExternalId` 없이는 `AccessDenied`였다. 학원 조직의 상위 정책은 조직 밖 AssumeRole을 막지 않는다.
2. **지금 앱은 「프로세스 하나에 역할 하나」다.** 운영 진입점(`apps/core-api/serve.py`)이 기동 때 접근 역할 프로필 하나를 잡고, `services/aws/client.py`의 `aws_client`가 그 자격을 그대로 쓴다(세션 기본 900초). 테넌트 개념은 PR #506 전까지 코드에 없었다.
3. **시연 고객은 실계정 1개(학원)다.** 두 번째 고객 계정은 확보 근거가 없다. 그래서 「고객이 여럿이어도 섞이지 않는다」는 주장은 **T-5 테넌트 격리 회귀 테스트**(목록 · 상세 · 실행 세 경로)가 유일한 근거다(#479 §1-2).

## Decision (결정)

**플랫폼과 고객을 서로 다른 AWS 계정으로 가르고, 플랫폼은 고객이 내준 역할에 AssumeRole + ExternalId로만 들어간다. 테넌트 하나 = 고객 AWS 계정 하나이며, 원격 회수는 「그 계정에 더 들어가지 않는 것」이다. 데이터는 뿌리 테이블의 `tenant_id`로 테넌트에 묶는다.**

### 1. 계정 구조 — 관리 · 플랫폼 · 고객 셋

| 계정 | 소속 조직 | 역할 |
| --- | --- | --- |
| 김세혁 개인 관리 계정 | 개인 조직(관리 계정) | Organizations 관리만. **워크로드를 두지 않는다**(관리 계정이 뚫리면 조직 전체가 넘어간다) |
| 플랫폼 멤버 계정(신설 · T-8 #494) | 개인 조직 | core-api · DB · 웹. 고객 계정에 들어가는 주체인 ECS 태스크 역할 `vigilantis-platform`이 여기 있다 |
| 고객 계정(시연 = 학원 계정) | 고객 조직(별개) | 관제 · 조치 대상. 고객이 내주는 역할 `vigilantis-access`만 둔다 |

- 플랫폼을 멤버 계정으로 따로 두는 이유는 둘이다 — 그 계정의 청구액이 곧 플랫폼 비용이 되어 **학원 청구 근거가 정확해지고**, 개인 조직의 다른 워크로드와 **피해 범위가 갈린다**(#438 §C-1).
- 수집 · 판정 · 실행 기록은 전부 팀 소유다. 고객 계정에서 나가는 API 호출(CloudWatch 조회 등)은 assume한 자격으로 나가므로 **고객 계정에 과금**된다.
- **구독은 Marketplace SaaS 계약 모양의 모의 흐름으로 처리한다**(T-16 · #528 · AWS 문서 [SaaS 계약](https://docs.aws.amazon.com/marketplace/latest/userguide/saas-contracts.html) · [구매 뒤 고객 설정](https://docs.aws.amazon.com/marketplace/latest/userguide/saas-product-customer-setup.html)). 모의 참조값은 실제 AWS 식별자와 헷갈리지 않게 구별한다. **2차 개정(2026-11-06): 실제 Marketplace 연동의 구조를 만들고, 상품은 올리지 않는다.** 등록 랜딩(`ResolveCustomer`), 권리 조회(`GetEntitlements`), 계약 변경 알림 수신 코드와 그에 필요한 플랫폼 권한까지 구현한다. 판매자 등록 · 상품 등록 · 실제 청구는 하지 않는다. Marketplace에는 샌드박스가 없고 등록 토큰 · 상품 코드 · 알림 토픽은 상품을 등록해야 생기는데, 상품 등록에는 1차 개정이 실제 연동을 접은 이유인 판매자 등록 · 세금 · 정산 · 심사 요건(#438 §B)이 그대로 걸린다. 상품을 등록하기 전까지는 모의 계약이 권리의 원천이다. **AI 사용료는 Marketplace로 받지 않는다**(2차 개정). 플랫폼이 고객 역할로 고객 계정의 Amazon Bedrock을 불러 모델 사용료가 고객 AWS 요금으로 나가게 한다. 목표 구조는 고객이 플랫폼 이용료(Marketplace)와 AI 사용료(Bedrock)를 AWS 청구 한 곳에서 내는 것이며, 플랫폼 이용료가 실제로 청구되는 것은 상품 등록 뒤다. 청구서가 한 장으로 합쳐지는지는 계정 · 청구 조건에 따른다. 쓸 모델과 처리 리전(글로벌 교차 리전 추론이면 국외에서 처리될 수 있다)은 구현이 확인한다.
- **이 프로젝트의 구현 범위는 네 작업의 제공자 직접 API 경로다**(3차 개정). 대상은 SecOps 분석 · FinOps 분석 · 절감 단가 조회 · 신고 초안 작성의 네 작업이며, 플랫폼이 관리하는 제공자 자격으로 호출하고 고객 역할을 거치지 않는다. 위 2차 개정의 고객 계정 Bedrock 호출과 고객 AWS 요금 과금은 설계로 두고, 이 프로젝트의 코드는 이 구현 범위를 따른다. 제공자 · 모델 선정과 네 작업의 연결 · 운영 설정 · 운영 확인은 #648이 맡는다.
- **직접 API 경로의 호출은 제공자가 국외에서 처리하는 것을 전제로 다룬다**(3차 개정). 개인정보 처리방침의 위탁 · 국외 이전 항목은 실제 호출 경로의 제공자 · 국가 · 목적 · 보관과 맞춘다. 운영 호출의 보관 · 캐시 조건은 #648 「선정 결과의 운영 적용」 3. 「직접 API 경로의 운영 조건」을 따른다 — 제공자 측 출력 저장과 프롬프트 캐시는 쓰지 않고, 요청으로 끌 수 없는 제공자의 남용 감시용 보관은 개인정보 처리방침에 공개한다.
- **유료 권리의 원천은 모의 Marketplace 계약이고, 앱의 구독은 그 투영이다** — 앱이 권리를 스스로 만들지 않아야 계약과 구독이 갈리지 않는다. 구매 요청은 서버가 모의 확정을 마친 뒤에 권리가 된다. 계약은 월 단위로 자동 갱신되고, 갱신을 끄면 그 기간 끝까지 권리를 유지한다. **계약이 만료되어 남은 유료 권리가 없거나 미납이면 그 테넌트를 §3의 정지(`SUSPENDED`)로 멈춘다**(2차 개정. 무료 요금제는 없고, 1차 개정의 "Free로 전환한다"를 대체한다). 모의 계약이 없는 기존 수동 구독은 이 자동 정지 대상이 아니다. 모의 계약은 테넌트당 월 단위 등급형 계약 하나이고, 등급은 기존 플랜 이름을 쓴다. 요금 · 혜택 · SLA는 이 결정에서 정하지 않는다.
- **계약을 맺는 구매자 계정과 관제 대상 고객 계정(§4의 테넌트)은 다른 개념이다.** 모의는 둘을 실제 AWS 신원으로 잇지 않는다.
- 고객사 중앙계정(`ADMIN`)과 고객사 직원계정(`OPERATOR` · `VIEWER`)이 모두 자기 구독을 보고, 구매 · 갱신 끄기는 고객사 중앙계정만 한다(계정 이름은 #577 · #572). 중앙 관리계정과 관리자 직원계정(배정된 고객사만)은 수동 구독 관리(계약의 `subscription` 칸)를 그대로 쓰되 **모의 계약이 정한 사실은 덮어쓰지 못한다.** 이 두 계정의 화면은 구독 조회용으로 둔다. 기존 테넌트 기록 · 이력과 이전의 수동 구독은 그대로 보존하고, 모의 구매로 소급 전환하지 않는다.
- **만료 · 미납 정지는 §3의 정지 규칙을 그대로 따른다**(2차 개정). 새 관제 · 조치를 막고 기존 기록은 남는다. 미납 상태 값 추가, 90일 안에 납부하면 그대로 복구, 90일이 지나면 삭제하는 것은 SSOT 2026-11-02 결정의 방향이며, 그중 이번에 구현할 범위는 SSOT가 관리한다.

### 2. 고객 접근 — 역할 전환만, 테넌트 문맥 없이는 나가지 않는다

- **장기 키는 받지 않는다.** 플랫폼 태스크 역할이 고객 계정의 `vigilantis-access`에 `sts:AssumeRole` + 고객별 `ExternalId`로 들어간다. 고객이 `ExternalId`를 바꾸지 않으며, 플랫폼이 테넌트를 만들 때 한 번 정한다.
- 고객 역할의 **권한은 Action Whitelist 거울 정책**이다 — 코드가 부르는 AWS 작업만 허용한다(ADR-0010 §3의 「빌려 붙인다」를 고객 쪽에 두는 것). 정책은 CloudFormation 템플릿 하나로 고객 계정에 만든다(온보딩 · 구현은 T-4 카드). **2차 개정(2026-11-06): 런북 밖의 작업이라도 코드가 부르면 들어간다.** 대상은 GuardDuty를 켜는 작업(`CreateDetector` · 서비스 연결 역할 생성)과 탐지 결과 조회(`ListFindings` · `GetFindings`)다(T-14 · #588). GuardDuty를 끄는 작업은 넣지 않는다. 고객 계정 Bedrock 모델 호출(`bedrock:InvokeModel`)도 들어가며, 과금되는 권한이라 쓰는 모델 · 추론 프로필 ARN으로 좁힌다(§1). 이 권한만으로는 첫 호출이 되지 않는다. 고객 계정에서 그 모델을 처음 부르기 전에 모델 활성화(Marketplace 구독, Anthropic 모델은 계정당 1회 사용 사례 양식, 계정의 결제 수단)가 있어야 하고, 양식과 결제 수단은 CloudFormation 템플릿이 대신할 수 없으므로 고객 온보딩에 넣는다(AWS 문서 [모델 접근](https://docs.aws.amazon.com/bedrock/latest/userguide/model-access.html)). 역할에 Marketplace 구독 권한을 넣을지, 고객이 한 번 활성화할지는 구현이 정한다. 기준은 그대로 "코드가 부르는 작업만"이다.
- **3차 개정(2026-11-20): 이 프로젝트의 AI 모델 호출은 플랫폼 자격의 직접 API라 고객 역할을 거치지 않는다(§1).** 그래서 현재 고객 역할 정책과 고객 온보딩에는 모델 호출 권한도, 모델 활성화 단계도 없으며, 이는 "코드가 부르는 작업만" 기준과 맞는다.
- **고객 계정으로 나가는 AWS 호출은 반드시 테넌트 문맥 안에서 나간다.** 수집 · 분석 · 실행 루프와 요청 처리는 「지금 어느 테넌트인가」를 먼저 세우고, `aws_client`는 그 테넌트의 자격을 쓴다. **문맥 없이 부르면 실패해야 한다** — 조용히 플랫폼 자격이나 다른 테넌트 자격으로 나가는 것이 가장 위험한 실패다(김승철 Q2 · 호출부가 50여 곳이라 인자로 넘기는 방식은 누락이 조용하다). 구현 방식(contextvar 등)은 카드 몫이다. **플랫폼 자체 자원을 부르는 호출**(알림 SNS 등 — 지금은 `platform_sns_client`가 플랫폼 자격으로 나간다)은 이 규칙 밖이며, 거꾸로 고객 자격으로 나가면 안 된다.
- **세션은 900초(15분)로 요청한다**(ADR-0010 §3 유지). 다만 앱이 요청하는 값과 **앱과 무관하게 보장되는 상한은 다르다** — 역할의 최대 세션 길이(`MaxSessionDuration`)는 AWS가 1시간 아래로 못 내리고, 태스크 역할 자격으로 다시 역할을 넘는 역할 연쇄도 1시간에 묶인다. 그래서 §3 원격 회수의 「이미 발급된 자격의 노출 상한」은 **1시간**이다(AWS 문서 기준 · 학원 계정에서 재지 않았다). 자격 캐시 · 갱신 시점(Q3)은 900초 안에서 구현이 정한다.
- **가드레일 ③ ARN Match에 「대상 ARN의 계정 = 이 테넌트의 계정」 조건을 더한다.** 테넌트 A의 승인으로 테넌트 B의 자원을 바꾸는 길을 가드레일이 막아야 한다.

### 3. 원격 회수 — `SUSPENDED` = 더 들어가지 않는다

플랫폼은 앱에서 그 고객의 새 작업을 막는다. 고객 역할이 플랫폼을 계속 신뢰하는 동안에는 AWS에서 새 역할 전환이 가능하다. 고객은 스택을 삭제하거나 신뢰 정책을 바꿔 새 역할 전환을 막을 수 있다. 이미 발급된 세션은 고객이 발급 시각을 기준으로 접근을 거부하지 않으면 만료될 때까지 유효하다.

| 겹 | 무엇 | 효과 |
| --- | --- | --- |
| ① 앱 | 테넌트 상태를 `SUSPENDED`로(사유 필수) | **즉시** — 루프는 매 회차 상태를 다시 읽는다. 새 수집 · 새 AI 분석 · 새 실행 접수(`POST /actions/execute` → `TENANT_SUSPENDED` 409)를 막는다 |
| ② 고객 쪽 회수 | 고객은 스택을 삭제하거나 역할의 신뢰 정책에서 플랫폼의 접근을 거두어 새 역할 전환을 막는다. | 이미 발급된 세션의 접근은 고객이 역할 정책에서 발급 시각(`aws:TokenIssueTime`)을 기준으로 거부할 수 있다. |
| ③ 상한 | 이미 발급된 세션은 플랫폼이 끊을 수 없다 | 요청한 900초, 앱에 결함이 있으면 최대 1시간(§2)이 지나면 끝난다 |

- **진행 중인 실행과 자동 원복은 끝까지 돌린다**(Q4). 중간에 멈추면 고객 자산이 반쯤 바뀐 채 남는다 — 원격 회수의 목적(더 손대지 않기)과 반대다. 종료 판정은 고객 계정을 조회하고 자동 원복은 고객 계정을 바꾸므로, **이것이 「더 들어가지 않는다」의 유일한 예외**다. 막는 것은 **새로 시작하는 것**뿐이다.
- **「시작된 실행」의 경계** — 단계를 남긴 실행과 그 자동 원복(`AUTO_ON_FAILURE` · 정지 뒤에 생겨도)은 끝까지 돌린다. 자산을 만지기 전의 예약(단계 0건 — 관제자 승인 · 선차단 예약)과 아직 생기지 않은 자동 발동(1분 무응답 자동 격리)은 **새 실행**이라 시작하지 않는다. 기준은 「자산을 이미 만졌을 수 있는가」다.
- **순서** — 정지: ①을 즉시 건다. 이미 시작된 실행과 자동 원복은 위 예외대로 마무리한다. 재개: 연결 확인 → 성공해야 `ACTIVE`(정지 사이에 고객이 역할을 지웠을 수 있다).
- **고객사 중앙계정은 서비스 이용을 중단할 수 있고, 이 중단은 위의 정지다**(#528) — 위 규칙이 그대로 적용된다. **운영 정지와 모의 계약은 따로 움직인다**(§1) — 정지는 플랫폼이 고객 계정에 들어가느냐를 정하고, 권리는 계약이 정하기 때문이다. 정지는 새 관제 · 조치를 막고, 계약의 갱신 · 만료는 그대로 진행된다. 다만 계약이 만료되거나 미납이면 그 결과로 정지가 걸린다(§1 · 2차 개정). 정지 중 고객사 중앙계정이 할 수 있는 계약 변경은 갱신 끄기 하나다(고객 계정에 들어가지 않는 계약 변경이라 아래 조회 전용의 예외다). 구매는 서비스가 `ACTIVE`일 때만 받는다. 만료 · 미납으로 정지된 고객사가 납부하는 경로와 그 뒤 재개 순서는 구현 카드가 정한다(2차 개정). 재개는 위 순서대로 중앙 관리계정 또는 해당 고객사가 배정된 관리자 직원계정만 하며, 기존 연결 확인(T-4)을 실제로 통과한 뒤 **그 시점의 권리를 그대로 쓴다** — 재개가 구독 권리를 바꾸지 않는다.
- **정지 중에는 연결 확인(`verify`)도 받지 않는다** — 그것도 고객 계정에 들어가는 일이다. 정지 테넌트에 **새로** 들어가는 길은 **재개(`resume`) 하나**다.
- **기존 기록은 남고 읽을 수 있다.** 고객사 계정도 **로그인하고 조회 전용으로** 자기 테넌트 기록을 본다 — 원격 회수는 고객 계정 접근을 끊는 것이지 고객이 자기 기록을 못 보게 하는 것이 아니다. 승인 · 실행 · 종료 같은 상태 변경은 거절한다(PR #504가 T-17로 넘긴 물음 1). **중앙 관리계정과 해당 고객사가 배정된 관리자 직원계정은 예외다** — 해지한 고객의 열린 인시던트를 정리해야 하므로 종료(`resolve`) 같은 **기록 정리는 허용**한다. 다만 새 실행 접수는 이 두 계정에도 없다 — 그것은 고객 계정에 들어가는 일이다.
- 고객이 **서비스 연결을** 해지하면 스택(역할) 삭제를 **안내**한다(만료 · 미납 정지는 이 해지가 아니다). 고객이 역할을 지우면 다음 연결 확인이 실패로 남는다.

### 4. 테넌트 모델 — 테넌트 하나 = 고객 계정 하나

- **`tenants` 테이블 하나**가 테넌트의 원천이다. 상태는 `PENDING_CONNECTION` → (연결 확인 성공) → `ACTIVE` ⇄ `SUSPENDED` 셋이고, 연결 확인 결과는 「지금 연결된다」가 아니라 **그 시각에 확인한 결과**로 남긴다(계약 원칙). 칸의 정의와 불변식은 계약(`packages/schemas/api/tenants.py`)과 마이그레이션(PR #506)이 원천이며 여기 복제하지 않는다.
- **계정 ID는 유일하다** — 같은 계정을 두 테넌트로 두면 같은 자산을 두 번 수집 · 조치한다. 계정 · 역할을 바꾸는 길은 없다 — 다른 계정이면 다른 테넌트다. 오입력은 **연결된 적 없는 테넌트를 지우고 새로 만드는 것**으로 고친다.
- **`external_id`는 DB에 평문으로 둔다**(Q5). AWS가 비밀값으로 다루지 않고 목적이 혼동된 대리인(confused deputy) 방지이기 때문이다. 다만 내보내는 자리는 **생성 응답 · 연결 전 온보딩 링크 · 재발급 경로** 셋뿐이고 상세 응답에는 없다.
- **데이터의 소속은 뿌리 테이블 5개의 `tenant_id`로 묶는다** — `collection_runs` · `assets` · `threat_events` · `incidents` · `action_executions`. 나머지는 FK로 따라온다(Q1). **기존 행은 `NULL`로 두고, `NULL` = MVP 단일 계정 기록이다.** 마이그레이션이 기본 테넌트를 지어내지 않는다 — 그 시점에는 계정 ID · 역할 · `ExternalId`가 없어 「연결 확인 없는 `ACTIVE`」라는 거짓 기록이 되기 때문이다(PR #506 리뷰 포인트 1). 학원 테넌트가 관리자 API로 생성 · 연결 확인을 마친 뒤 그 테넌트로 채우고 `NOT NULL`로 바꾼다(뒤 카드).
- **사용자의 소속은 `app_users.tenant_id` 하나**다 — 한 사용자 = 테넌트 하나, 소속은 만들 때 정하고 옮기지 않는다(옮기면 남의 기록을 보게 된다). **`NULL`은 「소속 없음」이지 권한이 아니다** — 누가 플랫폼 운영자인지는 T-1(#492)이 따로 표시한다(PR #504 정정 · PR #506). 고객사 사용자는 **테넌트가 `ACTIVE`가 된 뒤에만 초대한다** — 연결 전 테넌트는 지울 수 있어야 하는데 사용자가 있으면 FK가 삭제를 막는다(PR #504가 넘긴 물음 2).
- **모든 조회와 실시간 이벤트는 테넌트 범위다.** 목록 · 상세 · 실행 세 경로(T-5)에 더해 WebSocket도 **범위 밖 이벤트를 보내지 않는다**(지금은 큐 하나로 모든 연결에 같은 이벤트가 간다 — 네 번째 누출 경로). 범위를 요청에 싣는 방법은 T-1이 정한다. 중앙 관리계정은 전부 본다.
- **수집 범위는 테넌트 칸(`regions` · `collect_vpc_ids`)이 원천이다.** 플랫폼이 별도 계정으로 가면 ADR-0010 §6 `COLLECT_VPC_IDS`의 원래 이유(단일 계정에서 플랫폼 자원을 수집에서 빼기)는 사라진다 — 전역 값은 학원 테넌트가 연결되면 그 칸으로 옮긴 뒤 **지운다**(둘이 남으면 어느 쪽이 이기는지가 문제가 된다). 보호 태그 · 판정 임계치는 이번엔 전역 그대로다(T-7 이후).

### 5. 이 ADR이 대체하는 것과 유지하는 것

이 ADR은 아래 결정을 **지금부터** 대체한다. 두 문서의 본문을 고치는 작업(담당 · 시점)은 이슈 #491과 SSOT가 관리하며, 고쳐지기 전까지는 **이 ADR이 두 문서보다 우선한다.**

| 자리 | 지금 서술 | 대체 | 유지 |
| --- | --- | --- | --- |
| SSOT §MVP 확정 범위 「관제: AWS 단일 계정」 | MVP 범위 | Post-MVP는 플랫폼 계정 + 고객 계정 N(시연은 1개) | **MVP 범위 자체는 그대로** |
| ADR-0009 §1 「새 전용 계정은 만들지 않는다 · 대상 계정은 학원 계정」 | 스모크 환경 결정 | **학원 계정은 고객 계정이 된다** — 스모크 VPC · 인스턴스 · 접근 역할은 고객 자산의 자리로 읽는다 | 환경 수명 · VPC 격리 · 비용 통제 |
| ADR-0010 제목 · Context 「단일 계정이지만 SaaS 모양으로」 | 단일 계정 전제 | 플랫폼은 **플랫폼 멤버 계정**에 선다 | 리전 · 네트워크 · WAF 출입문 · 실행 구조 |
| ADR-0010 §3 권한표 「후속 SaaS 설계 후보」 열 | 후보 | **확정** — `vigilantis-platform`의 AssumeRole 대상은 `arn:aws:iam::*:role/vigilantis-access*` 패턴 하나, `vigilantis-access`는 고객이 CloudFormation으로 만드는 역할. 원격 회수 방식과 노출 상한은 §3 | 권한표의 나머지 열 |
| ADR-0010 §6 「`COLLECT_VPC_IDS` 존치 여부는 후속 설계에서」 | 미정 | **테넌트 칸으로 옮기고 전역은 폐기**(§4) | — |

### 6. #485 계약과의 대조

**계약과 다르게 정한 것은 없다.** 계약이 비워 둔 두 물음(PR #504)을 §3·§4에서 정했다 — 정지된 테넌트의 고객사 사용자는 **로그인 · 조회 전용**, 고객사 사용자 초대는 **`ACTIVE` 뒤**. 계약 문구 정리 둘은 계약 후속이다 — `TENANT_SUSPENDED`의 범위를 종료(`resolve`) 거절까지 넓히는 것, 머리말의 「고객 계정에 들어가는 경로는 `verify` · `resume` 둘뿐」을 「이 라우터의 경로 중에서는」으로 좁히는 것(§3의 예외 때문). 계약이 이 ADR과 어긋나면 계약을 고친다(#485 수용 기준 마지막 항목).

## Consequences (결과 · 트레이드오프)

**얻는 것**

- 「AWS 단일 계정」이라는 확정 결정과 코드(PR #489 · #506)의 어긋남이 사라진다. T-4 구현 카드 · T-8 이전 · T-1 범위가 **같은 전제** 위에 선다.
- 플랫폼의 고객별 차단은 앱 정지에 의존한다. 앱 정지에 결함이 있고 고객 역할이 여전히 플랫폼을 신뢰하면 새 세션을 발급받을 수 있다. 「더 들어가지 않는다」의 예외는 진행 중 실행의 마무리다.
- 테넌트 문맥 강제로 「어느 고객 자격으로 나갔는지 모르는 호출」이 구조적으로 생기지 않는다.

**비용 · 유의**

- **직접 API 경로의 모델 사용료는 플랫폼의 제공자 계정으로 청구된다**(3차 개정). 고객 AWS 요금에는 나타나지 않는다. 자산 · 위협 기록을 담은 모델 입력이 국외 제공자에게 가며, 요청으로 끌 수 없는 제공자의 남용 감시용 보관은 개인정보 처리방침 공개로 다룬다(§1).
- **기존 기록의 `tenant_id`가 `NULL`인 구간**이 생긴다 — 학원 테넌트 연결 전까지 대시보드는 「소속 없는 기록」을 보여 준다. 채우기 · `NOT NULL` 전환 카드가 닫혀야 T-5가 뜻 있는 테스트가 된다.
- **고객 분리의 근거는 테스트뿐**이다(시연 고객 1개). T-5가 세 경로 + WebSocket을 전부 덮지 못하면 「섞이지 않는다」를 증명하지 못한다.
- ADR-0009 · ADR-0010의 본문이 고쳐지기 전까지 두 문서의 「단일 계정」 서술과 이 ADR이 **같이 살아 있다.** 읽는 사람은 이 ADR §5를 기준으로 읽는다.
- 세션 900초는 ADR-0011의 선차단 3초 목표와 무관하지만, 테넌트별 세션이 늘면 STS 호출 한도 · 비용을 아직 재지 않았다(김승철 §7). 시연은 고객 1개라 지금은 문제가 아니다.
- 플랫폼 운영자 표시(T-1) · 조회 범위를 요청에 싣는 방법 · 온보딩 템플릿 호스팅은 **이 ADR이 정하지 않는다.** 구현 카드가 정하고, 후속 상세 ADR이 그 결과를 적는다.
