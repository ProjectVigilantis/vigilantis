## 1. 프로젝트 개요

### 프로젝트 주제

24/7 클라우드 자산·보안 상시 관제 및 Agentic AI 기반 원클릭 자율 대응 FinSecOps 시스템

### 팀 구성

| 이름 | 역할 | 담당 DOMAIN |
| --- | --- | --- |
| 김세혁(팀장) | PM · Infra & DevSecOps + Frontend | `BE`(Boto3 실행·롤백) · `INFRA`(Docker·CI·IaC) · `FE`(대시보드) |
| 안성일(팀원) | AI / Guardrail · Architect | `AI`(가드레일·CoT) · FastAPI 아키텍처 · DB |

| 박지현(팀원) | Technical Writer | `DOCS`(프로젝트 기획서 · 저장소 문서화) |

**2026-09-16(수)부터 4인이다.** 유건희(Frontend) 이탈로 담당 DOMAIN을 전부 재배치했고 **범위와 일정은 줄이지 않았다** — `FE` 전부가 김세혁에게, QA 전부가 김승철에게 갔다.

**10/1(목)까지의 담당별 역할은 §2 추진 일정에 있다.** 아래는 상시 담당 경계다.

**접점이 둘 이상인 변경은 양쪽을 모두 리뷰어로 지목한다.** `SEC`(SOAR 차단)은 안성일+김세혁, `SCHEMA`·API 계약은 계약 양쪽 담당자 모두다. **`FE`↔`BE` 접점은 안성일이 본다** — 김세혁이 두 축을 함께 들면서 저자 본인이 승인할 수 없게 됐기 때문이다.

### 추진배경 및 필요성

**□ 추진배경 (Background)**

**클라우드 운영에서 탐지는 이미 충분히 자동화돼 있다.** 유휴 인스턴스도, 열린 보안 그룹도 도구가 찾아 준다. **병목은 그다음이다.**

| 단계 | 현재 | 문제 |
| --- | --- | --- |
| 탐지 | 자동 | — |
| 판단 | **사람** | 알림은 쌓이는데 무엇부터 볼지 근거가 없다 |
| 조치 | **사람** | 콘솔·CLI를 직접 친다. 야간·휴일에는 지연이 그대로 노출 시간이 된다 |
| 회복 | **사람** | 조치가 틀렸을 때 되돌릴 근거가 조치자의 기억에 있다 |

**□ 필요성 (Needs)**

이 세 단계가 특히 비싼 곳이 있다 — **개발로 성공해 구색을 갖췄지만 인프라는 다른 영역인 중소기업**이다. 개발 10년차라도 인프라 구축·유지보수에서는 신입이고, 사업이 커져 인프라가 늘어도 **추가 인건비를 쓰는 선택지가 실제로는 닫혀 있다.**

**그래서 이 프로젝트가 풀려는 문제는 「관제를 더 잘하는 법」이 아니라 「관제 인력을 늘리지 않고도 관제가 유지되는 법」이다.**

**□ 자동화를 막는 것은 성능이 아니라 신뢰다**

「조치를 자동화하자」는 결론은 쉽게 나온다. 그런데 자동화가 실제로 막히는 이유는 성능이 아니라 **신뢰**다.

1. **되돌릴 수 없는 조치를 기계가 한다** — 인스턴스를 격리하거나 보안 그룹을 지우는 일은 취소 버튼이 없다.
2. **LLM이 무엇을 할지 자유롭게 정한다** — 자연어 판단을 그대로 실행에 연결하면 잘못된 대상·잘못된 작업이 통과하는 경로가 열린다.
3. **실패했을 때 되돌릴 근거가 남지 않는다** — 조치 전 상태를 적어 두지 않으면 원복은 사람의 기억에 의존한다.

**이 셋이 이 프로젝트의 설계를 전부 결정했다.** 아래 §목적 및 핵심 가치와 §주요 서비스가 각각의 답이다.

### 목적 및 핵심 가치

**□ 프로젝트 목적 (Goal)**

**Vigilantis는 24/7 AWS 자산·보안 상시 관제 + 4단계 AI 가드레일 기반 원클릭 자율 조치 + 양방향 회복(자동 원복 / 원클릭 해제)을 제공하는 FinSecOps 플랫폼이다.**

「FinSecOps」는 비용 최적화(FinOps)와 보안 대응(SecOps)을 **하나의 조치 파이프라인** 위에 올린다는 뜻이다. 두 축은 탐지 근거와 판단 기준이 다르지만 *탐지 → AI 판단 → 가드레일 검증 → 승인 → 실행 → 회복* 이라는 경로를 공유한다.

**□ 핵심 가치 — AI에게 실행 권한을 주되, 통과할 수 있는 문을 좁힌다**

- AI는 **무엇을 할지 고르지 않는다.** 미리 등재된 **런북 10종** 중에서 **고른다**(Action Whitelist).
- 고른 결과는 실행 전에 **4단계 가드레일**(Schema Check → Action Whitelist → ARN Match → AWS Dry-Run)을 **순서대로** 통과해야 한다.
- 조치 **전에** 원래 상태를 백업 레코드로 남긴다. 원복 파라미터는 AI도 화면도 아닌 **그 레코드에서만** 온다.
- 실패하면 **시스템이 스스로 되돌리고**(자동 원복), 보안 차단은 관제자가 **원클릭으로 해제**한다.

**□ 무엇으로 「됐다」고 판정하는가**

재는 법이 적혀 있지 않은 지표는 아무도 재지 않는다. 아래는 전부 **저장소에서 명령으로 다시 잴 수 있는 값**이다.

| 축 | 지표 | 목표 | 현재(2026-09-17) |
| --- | --- | --- | --- |
| 정확성 | 자산·위협 판정 정답 일치율 | **100%** | ✅ 자산 28/28 · 위협 16/16 |
| 정확성 | AI 출력 안정성 — 실행으로 나가는 값의 흔들림 | **0** | ✅ AI 산출 정답지 6건 회귀 |
| 안전성 | Whitelist 밖 Runbook의 실행 진입 | **0건** | ✅ 구조상 차단 |
| 안전성 | 원복 파라미터 출처 — DB 백업 레코드 | **100%** | ✅ AI·화면 경유 0건 |

### 주요 서비스

**□ 핵심 3축**

| 축 | 무엇을 하나 | 이 축이 지키는 것 |
| --- | --- | --- |
| ① 상시 관제 | 자산·보안 상태를 주기 수집해 판정한다 | 판단의 **근거**가 사람 기억이 아닌 데이터에 있다 |
| ② 4단계 가드레일 | AI 추천을 실행 전에 순서대로 검증한다 | AI가 **고를 수 있는 범위**를 좁힌다 |
| ③ 양방향 회복 | 조치를 되돌리는 경로를 미리 만들어 둔다 | 되돌릴 **근거**가 조치 전에 남는다 |

**□ ① 상시 관제 — 무엇을 보고 무엇으로 판정하나**

AWS **단일 계정 / 1–2개 리전**의 **EC2·SG 중심** 자산과 런북 조치 대상 리소스(NACL, EBS, ASG·Launch Template, ALB Target Group)를 APScheduler 기반으로 주기 수집한다. 위협은 **OpenIP(`0.0.0.0/0`)** 와 **SSH 브루트포스** 2종이며 Golden Dataset 기반 **모의(Mock) 주입**이다.

**3단계 위험 대응** — 위험도에 따라 사람이 개입하는 지점이 달라진다.

| 위험도 | 처분 | 사람의 개입 | 현재(2026-09-17) |
| --- | --- | --- | --- |
| High | `PRE_MITIGATION_0_5S` — 0.5초 선차단 | 차단 **후** 확인 | 🔶 **설계 확정 · 발동은 아직** — 이 경로의 런북은 `RUNBOOK_EC2_ISOLATE` 하나이고 P2라 실 AWS 첫 검증이 10주차다 |
| Medium | `AGENT_WAIT` — 승인 대기 · 1분 미응답 시 자동 격리 | 승인 | 🔶 **설계 확정 · 발동 잡 없음** — 기한 시각을 기록하는 코드만 있고 발동 주체가 없다 |
| Low | `AGENT_WAIT` — 승인 대기 (자동 격리 없음) | 승인 | ✅ 동작 |

**10/1(목) 시연에서 보이는 것은 Low·Medium의 「승인 대기 → 관제자 승인」까지다.** 위 두 자동 경로는 설계로 확정돼 있고 계약·화면까지 서 있지만 **발동 주체가 아직 없어 시연 대본에 들어가지 않는다.**

**□ ② 4단계 가드레일 — AI가 통과해야 하는 문**

**순서가 고정돼 있다.** 앞 단계를 건너뛰는 경로는 없다.

| # | 단계 | 무엇을 검사하나 | 여기서 막히는 것 |
| --- | --- | --- | --- |
| ① | Schema Check | AI 출력이 Pydantic v2 계약을 만족하는가 | 형식이 깨진 출력 |
| ② | Action Whitelist | `Runbook ID`가 등재된 10종 안에 있는가 | **표에 없는 조치** — AI가 새 작업을 지어내는 경로 |
| ③ | ARN Match | 조치 대상 ARN이 수집된 자산과 일치하는가 | 존재하지 않거나 **엉뚱한 대상** |
| ④ | AWS Dry-Run | 실제 AWS가 이 호출을 받아들이는가 | 권한·파라미터 오류 |

**□ ③ 양방향 회복 — 되돌리는 두 경로**

| 축 | 경로 | 발동 주체 |
| --- | --- | --- |
| 자산 (FinOps) | 스펙 JSON 백업 → `get_waiter` **Status Check 2/2** → 실패 시 **자동 원복** | **시스템** |
| 보안 (SecOps) | 선제 차단 → 관제자 **「원클릭 해제」** | **관제자** |

**□ Action Whitelist — 런북 10종 (본편 7 + 롤백 3)**

**여기 없는 Runbook ID는 실행 경로에 진입할 수 없다**(가드레일 ②).

| 분류 | Runbook ID | 위험도 / 승인 | AI 추천 | 등록 롤백 |

| SecOps | `RUNBOOK_NACL_ADD_DENY` | Medium / 관제자 승인 | ✅ | — (해제는 `NACL_RESTORE`) |

| --- | --- |
| 되돌릴 수 없는 조치를 기계가 한다 | **ADR-0008** — 조치 *전에* 백업을 1회 캡처해 불변 보존 |
| LLM이 무엇을 할지 자유롭게 정한다 | **ADR-0002 · 0004** — 등재된 10종 밖으로 나갈 경로가 없다 |
| 실패했을 때 되돌릴 근거가 없다 | **ADR-0004 ③ · 0008** — 원복 파라미터는 **DB 백업 레코드에서만** 온다 |

그 밖에 **ADR-0001**(단일 백엔드 통합) · **0003**(FE 스택) · **0005**(LangGraph 2그래프) · **0006**(LocalStack 표준 환경) · **0007**(가드레일 ④ 계약) · **0009**(실 AWS 스모크 환경)이 있다. **ADR은 살아 있는 문서다** — 0002·0004·0006·0007은 실측이 쌓이며 개정됐고(0006은 6차까지) 개정 이력이 본문 하단에 남는다.

**□ API 계약이 지키는 두 가지**

1. **실행 요청은 Target ARN도 AWS 파라미터도 받지 않는다.** Request는 `{incident_id, runbook_id, idempotency_key}` **셋뿐**이며 무엇을 어디에 할지는 서버가 Incident와 백업 레코드에서 정한다 — **화면이 조작돼도 조치 대상이 바뀌지 않는다.**
2. **화면 표시용 값은 서버가 typed 파라미터에서 파생한다.** LLM이 짓지 않고 실행 요청으로 되돌려 받지도 않는다.

실행 상태는 **7종**이다 — `IN_PROGRESS`·`SUCCESS`·`FAILED`·`ROLLBACK_INITIATED`·`ROLLED_BACK`·`ROLLBACK_FAILED`·`UNVERIFIED`(AWS 조회 실패로 판정하지 못한 종료 상태 — 자동 원복하지 않고 관제자 복구를 연다).

**□ 검증 체계 — 「돌더라」가 아니라 「무엇과 대조해 맞다고 하는가」**

| 층 | 무엇 | 현재 |
| --- | --- | --- |
| **정답지** | Golden Dataset — 입력 자산 **32건** / 판정 정답 **28건** / SecOps 이벤트 **16건** | 자산 유형 7/7종 · 관계 6/6종 · `verdict` 4종 · Skip 사유 6종 전량 |
| **경로** | E2E 시연 시나리오 **T1**(자동 원복 9단계) · **T2**(차단 → 원클릭 해제 8단계) | ✅ 전 구간 흐름 테스트 2건 통과(2026-09-17) |
| **회귀** | CI 3잡 — `test`(PostgreSQL·LocalStack service container) · `web` · `ai-signature` | ✅ `dev` **2133 passed / 0 skipped** |

**정답지 자체도 회귀로 잠근다.** 스키마 드리프트 가드가 골든 추출 스키마와 Pydantic 계약을 **등식**으로 묶고, 커버리지 가드가 판정 대상 유형에 정답이 빠지는 것을 막는다.

### 기대효과

**□ 관제자에게 무엇이 달라지나**

| 단계 | 지금 | Vigilantis |
| --- | --- | --- |
| 판단 | 알림이 쌓이는데 **무엇부터 볼지 근거가 없다** | 규칙 판정 + **AI CoT 3줄 요약 + Evidence ID** — 왜 이 자산인지가 화면에 선다 |
| 조치 | 콘솔·CLI를 직접 친다 | **원클릭.** 대상·파라미터는 서버가 정하고 실행 전 4단계 가드레일을 지난다 |
| 회복 | 되돌릴 근거가 **조치자의 기억**에 있다 | 조치 *전에* 남긴 **백업 레코드**. 자산은 자동 원복, 보안은 원클릭 해제 |
| 야간·휴일 | 지연이 그대로 **노출 시간** | High는 0.5초 선차단 후 확인, Medium은 1분 미응답 시 자동 격리 — **설계 확정이며 발동은 P2 실 AWS 검증(10주차) 뒤다** |

**□ 정성적 기대 효과**

- **판단의 근거가 데이터로 남는다.** 어떤 자산을 왜 그렇게 판정했고, AI가 무엇을 근거로 무엇을 추천했으며, 가드레일 4단계가 각각 무엇을 확인했는지가 **DB에 기록**된다. 사후에 *왜 그 조치를 했나* 를 설명할 수 있다.
- **되돌릴 수 있는 자동화라 도입 문턱이 낮다.** 자동화를 막는 것은 성능이 아니라 신뢰였고 그 셋을 각각 **구조로** 막았다.
- **비용 축과 보안 축이 한 파이프라인을 쓴다.** 탐지 근거는 다르지만 경로가 같아서 **런북을 늘리는 비용이 축마다 따로 들지 않는다.**

**□ 경제성 — 사람 한 명 값보다 싸야 한다**

이 도구는 **사람을 뽑는 대신 쓰는 도구**이므로 사람 한 명 값보다 싸야 존재 이유가 선다.

| 축 | 값 | 산출 근거 |
| --- | --- | --- |
| **인건비** | **연 6,000만 원** | 전담 DevOps 1명을 뽑지 않고 버티는 비용 — 5년차 연봉 5,000만 원 + 4대보험·퇴직금 |
| **유휴 자산** | **월 40만 원**(참고치) | 자산 20대 중 저활성 4대를 **정리(정지·삭제)** 했을 때 — AWS 서울 리전 온디맨드 기준. **이 도구의 조치 범위 밖이다** |

> **수치 기준** — 원티드 DevOps 직무 연봉 데이터(2025) · AWS 서울 리전 온디맨드 요금. **유휴 자산 값은 추정 참고치이며 실적이 아니다.**

- **인건비 6,000만 원**은 **「피하는 비용」**이다 — 이 도구가 없으면 사람을 뽑거나, 뽑지 않고 겸업 담당자가 떠안는다.
- **유휴 자산 40만 원**은 **「정리했을 때의 참고치」**다. **Action Whitelist에는 EC2를 정지·삭제하는 런북이 없다** — 유휴 EC2 조치는 `RIGHTSIZING` 하나이고 같은 패밀리 안에서 **메모리 1/4 이상 · 2 GiB 하한**을 지키는 크기까지만 내린다. **그래서 이 도구가 실제로 줄이는 금액은 위 참고치보다 작다.** 실제 절감은 조치 건마다 계산해 승인 화면에 올린다.

**절감 금액은 이번 범위에서 「제시」까지다.** 집계·추이 축은 범위 밖이며 **실적 수치를 주장하지 않는다.**

**MVP가 증명하려는 것은 금액의 크기가 아니라 경로의 성립이다.** 조치가 실제로 실행되고 되돌릴 수 있다는 것이 서면 금액은 자산 수에 따라 따라온다.

### 활용방안 및 비즈니스 모델(BM)

**□ 주요 활용 방안 및 적용 시나리오**

**[FinOps 전담 없는 중소·중견기업의 비용 절감]**
- 적용 대상: 클라우드 월 비용이 유의미하지만 **전담 인프라 인력이 없는** 기업.
- 활용 방식: Rule Engine과 AI Agent가 분석한 과스펙·유휴 자산 추천 카드를 **버튼 한 번**으로 실행하고, 기동 실패 시 **자동 원복**으로 서비스 장애 리스크 없이 비용을 줄인다.

**[보안 위협의 야간·휴일 대응 공백 메우기]**
- 적용 대상: 보안 담당이 겸업이라 알림을 **제때 못 보는** 조직.
- 활용 방식: 위험도에 따라 선차단 또는 승인 대기로 나누고, 차단 뒤에는 **원클릭 해제**로 오탐 비용을 낮춘다. 해제 근거는 차단 시점의 백업 레코드에서 온다.

**[MSP 통합 관제 — Post-MVP]**
- 적용 대상: 다수 고객사의 AWS 계정을 위탁 관리하는 MSP 사업자.
- 활용 방식: 계정·리전 확장 뒤 단일 대시보드에서 고객사별 헬스 스코어와 승인 대기 건을 상시 관제한다.
- ⚠️ **다중 계정 관제는 현재 MVP 범위 밖이다**(§주요 서비스 범위 경계). Post-MVP 확장 항목으로 적는다.

**□ 비즈니스 모델**

| 구분 | 대상 | 제공 범위 |
| --- | --- | --- |
| **Starter**(Freemium) | 가시성만 먼저 보고 싶은 소규모 팀 | 단일 계정 · 자산 조회와 판정 결과 열람 · **조치 실행 제외** |

**□ 시장 진출 전략**

2. **MSP 제휴** — 통합 관제 툴로 묶음 공급.
3. **Multi-Cloud 확장** — AWS 중심 파이프라인을 다른 CSP로 확장. **런북 등재 구조가 그대로 확장 단위가 된다.**

## 2. 시장현황 및 유사 서비스 분석

### 시장 현황

**클라우드 사용은 빠르게 늘지만, 그것을 관리할 사람은 늘지 않는다.** 이 격차가 이 프로젝트의 시장이다.

**□ 거시 환경 (Macro Environment)**

| | 값 | 뜻 |
| --- | --- | --- |
| 국내 클라우드 시장 | **99.5억 → 382.8억 달러** | 2025년 → 2031년 전망 (전체 CAGR **25.18%**) |
| 성장 동력 | **정부 클라우드 바우처** | 도입비 지원으로 **도입 장벽이 낮아진다** |

- 클라우드 전환은 이미 진행형이고 **관리 대상 자산은 도입 곡선을 그대로 따라 늘어난다.**
- 정부 지원으로 **처음 들어오는 기업**이 늘어난다 — 이들이 곧 「인프라 담당이 없는 채로 클라우드를 쓰는 조직」이다.

**□ 미시 환경 (Micro Environment)**

| | 값 | 뜻 |
| --- | --- | --- |
| **중소기업 세그먼트** | **CAGR 27.2%** | **전체 시장보다 빠르다**(27.2 > 25.18) |
| 국내 SaaS 기업 수 | **1,642개** | 2023년 기준 · **전년 대비 +24%** |

- **우리가 겨냥한 구간이 시장 평균보다 빠르게 큰다.** 바우처로 장벽이 낮아진 결과이며 그에 따라 관리형 DevOps 지원 수요가 함께 생긴다.
- **대상 모집단 자체가 늘고 있다** — 1,642개 SaaS 기업은 대부분 §1 추진배경이 그린 「개발은 잘하지만 인프라는 다른 영역」인 회사다.

**□ 기업 니즈 (Enterprise Needs)**

| | 값 | 뜻 |
| --- | --- | --- |
| 전담 인프라 인력 1명 | **연 6,000만 원** | 5년차 5,000만 + 4대보험·퇴직금 |
| 사이버보안 담당 인력 중 **겸업** 비율 | **63.8%** | 2024년 기준 — 본업이 따로 있고 보안을 얹어서 한다 |

- **사람을 뽑는 선택지가 닫혀 있다.** 고정비 한 줄이 손익에 그대로 반영되는 규모에서 연 6,000만 원은 쉽게 내리는 결정이 아니다.
- **그래서 대다수가 고른 답은 「겸업 유지」다** — 있는 개발자에게 인프라를 얹는다. 그 개발자는 인프라에서는 여전히 신입이고 야간·휴일 알림은 그대로 노출 시간이 된다.

> **인용 출처** — 시장 규모·성장률: Mordor Intelligence, 「South Korea Cloud Computing Market Size & Share Analysis — Growth Trends and Forecast (2026–2031)」(2026-01-15 갱신) · SaaS 기업 수: 과학기술정보통신부 「2024 클라우드산업 실태조사」 · 인건비: 원티드 DevOps 직무 연봉 데이터(2025) · 겸업 비율: 과학기술정보통신부 「2024년 사이버보안 인력수급 실태조사」(**원 보고서를 직접 열지 못해 보도(이투데이 2025-04-10)로 확인한 값이다**)

⚠️ **겸업 63.8%를 우리 주장으로 그대로 옮기지는 않는다.** ① **직무**가 보안이고 인프라가 아니다 ② **분모**가 기업 수가 아니라 **인력 수**다. 같은 조사의 외부 인력 7.8%도 분모가 같다고 확인되지 않아 **두 값을 더하지 않는다.** 인프라 직무의 같은 조사는 찾지 못했다 — **방향은 같지만 그대로 옮겨 적을 수는 없는 근거**로 둔다.

**□ 기존 서비스 분석 요약**

- **탐지·가시성까지는 이미 잘 풀려 있다.** GuardDuty + Security Hub는 에이전트 없이 켜기만 하면 되고 사용량 기반 과금이라 시작 부담이 작다 — **잘하는 도구이고 여기서 경쟁하지 않는다.**
- **멈추는 지점이 분명하다.** 결과물이 **탐지 결과와 점수까지**이고 실행·원복은 사람 몫으로 남는다. §1 추진배경에서 본 대로 **그 사람이 없는 것이 문제였다.**
- **빈 자리는 「경고를 안전하게 실행까지 끌고 가는 도구」다.** 이 프로젝트가 서는 자리이며 아래 SWOT의 강점·기회가 전부 이 자리에서 나온다.

**□ 2. SWOT 교차 분석 기반 실행 전략**

**a. SO 전략 (강점 극대화 + 기회 포착)**

**[좁지만 확실한 조치 범위를, 빠르게 크는 세그먼트에 태운다]**
- **「런북 10종으로 시작해 등재로 넓히는」 모델**을 바우처로 새로 들어오는 기업에 맞춘다. 처음 클라우드를 쓰는 조직은 **기능이 많은 도구보다 사고를 안 내는 도구**를 원한다.

**[「되돌릴 수 있다」를 판매 메시지의 맨 앞에 둔다]**
- 자동화 도입을 막는 것은 성능이 아니라 신뢰였다(§1 추진배경). **조치 전 백업 · 4단계 가드레일 · 양방향 회복**을 전면에 내세우면 기능 비교가 아니라 **도입 결정 자체의 허들**을 낮추는 쪽으로 경쟁 축을 옮길 수 있다.

**b. ST 전략 (강점 활용 + 위협 극복)**

**[감사 가능성으로 「AI가 인프라를 망친다」는 우려를 구조로 반박한다]**
- 위협은 기능 경쟁이 아니라 **신뢰**다. Evidence ID 기반 판단 근거, 가드레일 4단계 기록, ADR 9건이 **「왜 그 조치를 했나」에 사후에 답할 수 있게** 한다. **설명 가능성**을 파는 것이 CSP 기본 기능과 겹치지 않는 자리다.

**[CSP가 조치까지 내려와도 남는 자리를 지킨다]**
- CSP 기본 기능은 **자사 서비스 경계 안**에서 움직인다. 우리는 **비용 축과 보안 축을 한 파이프라인**에 올려 두었으므로 두 축을 오가는 조치(격리 → 해제, 다운사이징 → 자동 원복)에서 차이가 난다.

**c. WO 전략 (약점 보완 + 기회 활용)**

**[좁은 범위를 「확장 절차」로 바꾼다]**
- 런북 10종이라는 제약을 감추지 않고 **ADR 등재 절차 자체를 제품의 일부**로 보여 준다. 고객 요청이 곧 다음 런북 후보가 되며 **무엇이 실행될 수 있는가의 상한이 문서로 보이는 것**이 오히려 도입 설득에 쓰인다.

**[모의 주입을 「재현 가능한 검증 자산」으로 쓴다]**
- 실환경 미연동은 약점이지만 Golden Dataset 32건과 E2E 2트랙은 **같은 장면을 매번 재현**한다. 도입 전 PoC에서 **고객 환경을 건드리지 않고** 동작을 보여 줄 수 있다.

**d. WT 전략 (약점 최소화 + 위협 회피)**

**[검증된 것과 이월된 것을 문서로 구분하는 운영을 유지한다]**
- P2 3종 미검증을 숨기면 사고 한 번에 신뢰가 무너진다. **ADR-0006 §4 이월 목록처럼 「무엇이 검증됐고 무엇이 남았는가」를 상시 문서화**해 과장하지 않는 쪽으로 대형 벤더와 차별화한다.

**[런북 유지 비용을 구조로 흡수한다]**
- 클라우드 API 변경은 피할 수 없다. 런북별 파라미터 계약을 코드(`packages/schemas`)에 두고 **CI 3잡으로 회귀를 잠가** 변경이 생겨도 **깨지는 자리가 즉시 드러나게** 한다.

| **판정에 48시간 관측 리드 타임** | CPU 관측치 48개(약 2일) 미만이면 판정이 데이터 부족으로 넘긴다. 그래서 환경 기동을 **8주차 9/29(화)** 로 앞당겼다 |

### 차별성

**□ 「탐지 다음」을 다르게 잡았다**

클라우드 비용 최적화 도구도, 보안 탐지 도구도 이미 많다. **탐지는 경쟁 지점이 아니다.** 이 프로젝트가 다르게 잡은 것은 **그다음 — 판단·조치·회복**이다.

**[① AI에게 「만들라」가 아니라 「고르라」고 한다]**
- 자연어 판단을 그대로 실행에 잇는 대신 **미리 등재한 런북 10종 중에서 고르게** 한다. AI가 새 작업을 지어내는 경로가 **구조적으로 없다**(가드레일 ②).
- 흔한 접근은 LLM에게 스크립트나 IaC를 생성시키는 것인데, 그러면 *무엇이 실행될 수 있는가* 의 **상한이 사라진다.**

**[② 되돌릴 근거를 조치 「전에」 만든다]**
- 원복 파라미터의 출처를 **DB 백업 레코드 하나로 못 박았다**(ADR-0004 ③ · ADR-0008). AI 출력도 화면 입력도 원복 값이 될 수 없다.
- **자동화의 전제가 성능이 아니라 회복 가능성**이라는 판단이며 이것이 도입 문턱을 낮춘다.

**[③ 롤백도 같은 문을 지나게 했다]**
- 롤백 런북 3종을 **Whitelist에 정식 등록**해(ADR-0004) 우회 경로를 만들지 않았다.
- 우회로를 뚫는 쪽이 구현은 쉽지만 그 순간 **가장 위험한 조치가 가장 덜 검증된다.**

**□ 왜 이 조합이 흔치 않은가**

세 요소는 각각 새롭지 않다. **셋이 함께 서야 자동화가 성립한다**는 것이 이 프로젝트의 주장이다.

- 화이트리스트만 있으면 — 실행은 막지만 **실패했을 때 되돌릴 수 없다.**
- 백업만 있으면 — 되돌릴 수는 있지만 **애초에 엉뚱한 조치가 나간다.**
- 자동 원복만 있으면 — 되돌리는 동작 자체가 **검증 없이 돈다.**

그래서 §1 추진배경의 신뢰 3가지에 **각각 구조를 하나씩** 대응시켰고 그 대응이 ADR 문서로 남아 있다.
