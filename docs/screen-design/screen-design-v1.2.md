# Vigilantis 화면 설계서

> 버전: **v1.2**
> 기준일: 2026-08-12
> 작성: 유건희 (Frontend / UI·UX)
> 범위: MVP. Post-MVP 화면은 10장에 목록만 유지
> 상태: **와이어프레임 확정 (16장). 이 문서를 기준으로 `apps/web`을 새로 구현한다.**

## 0. 문서 개요

### 0.1 목적

Dashboard(`apps/web`)의 화면을 확정하고, 구현이 따라야 할 기준을 정의한다.
화면 구성은 `figma-wireframe/`의 저충실도 와이어프레임과 1:1로 일치한다.
화면 요소는 실제 응답 필드에 매핑하는 것을 원칙으로 한다. 다만 기획서가 요구하지만 아직 계약에
없는 요소는 화면에서 빼지 않고 ⏳로 표시해 남긴다. 화면이 백엔드에 필요한 필드를 정의하는 쪽이,
칸을 지웠다가 나중에 다시 그리는 것보다 낫다. ⏳ 항목은 9장에 필요한 필드와 함께 모은다.

### 0.2 입력 기준

| 문서 | 사용 범위 |
| --- | --- |
| `Vigilantis_통합설계_개인작업본_08121040.md` 4장 | **화면 설계의 1순위 기준**. REST 3개·WebSocket 1개의 필드·enum·상태 |
| `Vigilantis_통합설계_개인작업본_08121040.md` 2장 | A·B·C 업무 흐름과 실패 처리 의미 |
| `Vigilantis_프로젝트기획서(v1.1).docx` | UI 요구사항(All Systems Operational 시그널, 헬스 게이지, 자산 분포 차트, 낭비 자원 하이라이트, Alert Toast, 판단 근거 3줄) |
| `Vigilantis_시스템&데이터설계서(v1.11).docx` | Guardrail 4단계 표시, Evidence 기반 Decision Trace 표시 원칙 |

기획서·시스템설계서에는 있으나 MVP 계약에 API가 없는 화면(Drift, 비용 절감액, 네이티브 앱, RBAC, 감사 화면)은 10장으로 분리한다.

### 0.3 기술 전제

Next.js (App Router, TypeScript) / Tailwind CSS / 네이티브 WebSocket.

Shadcn UI와 차트 라이브러리는 필요해지는 시점에 넣는다. 이 문서의 화면 대부분은 표시용이라
Radix 프리미티브가 할 일(포커스 트랩, 키보드 내비게이션)이 없고, 도넛·게이지는 CSS와
인라인 SVG로 끝난다. Dialog 포커스 트랩이나 축·툴팁이 필요해지면 그 컴포넌트만 추가한다.

### 0.4 표기 규칙

- `필드명` — API 응답의 실제 필드
- ⚠️ — 계약에 필드는 있으나 값·규칙이 미확정인 항목 (9장에 집계)
- ⏳ — 계약에 필드 자체가 없어 백엔드 추가가 필요한 항목 (9장에 집계). 화면에서 빼지 않고 자리를 유지한다
- 모든 시각은 UTC ISO 8601로 수신하고 화면에서는 로컬 시간으로 표시한다.

### 0.5 변경 이력

| 버전 | 날짜 | 내용 |
| --- | --- | --- |
| v0.1 | 2026-08-12 | 초안. MVP 계약(REST 3개·WS 1개) 기준으로 9개 화면 확정 |
| **v1.1** | 2026-08-12 | 와이어프레임 제작 결과를 반영. 아래 4건이 바뀜 |
| **v1.2** | 2026-08-12 | 팀장 추가 명세(FinOps·보안 상세 흐름) 반영 |

v1.2에서 바뀐 것:

1. **자원 5종** — EC2·SG에 EBS Volume·ALB·Elastic IP 추가. 토폴로지가 ALB → EC2 → EBS 3계층으로.
2. **런북 패키지** — 단일 런북 추천에서 조합 추천으로. Runbook 사전(3.2.1) 신설, 11개 등재.
3. **승인 도입** — APR-001 신설, 실행 phase가 6칸에서 7칸(`승인` 삽입), 승인 상태 4종(3.2.2).
   9.1의 C4 충돌이 해소됐다.
4. **화면 3장 추가** — APR-001 승인함 / INC-003 공격 타임라인 / HIS-001 감사 로그.
5. **절감액이 1급 요소로** — INC-002 A에 절감 예상 블록, DSH-001에 30일 추이 차트.
6. **파괴적 조치 처리** — EBS 삭제 등에 경고와 사전 백업 고지를 강제 (4.6).
7. 백엔드 요청이 12건에서 **22건**으로 늘었다.
8. **프레임 규격을 16:9 (1920 × 1080)로 변경.** 발표·모니터가 전부 16:9라 레터박스 없이
   꽉 찬다. 가로가 넓어져 고정폭 열(200px 이상)을 1.33배로 함께 조정했다.
9. **타이포 +35%, 9px 주석 제거.** 최소 글자가 9 → 12px. 근거 설명은 이 문서에 이미
   있으므로 와이어프레임에서 걷어냈다 — 저충실도는 구조를 보이는 물건이다.

v1.1에서 바뀐 것:

1. **DSH-001 전면 개편** — 카드 3개에서 10개, 3행 구조로. `자산 토폴로지`·`보안 위협 맵`·
   `즉시 조치 가능`·`위험도 현황`·`분석 상태`·`누적 절감`을 추가했다. v0.1의 대시보드는
   기능이 적고 빈 공간이 많았다.
2. **계약 밖 요소 처리 원칙 변경** — v0.1은 "계약에 없는 값은 화면에 만들지 않는다"였다.
   v1.1부터는 화면에 자리를 남기고 ⏳로 표시한 뒤 9장에서 백엔드에 요청한다. 화면이 필요한
   필드를 정의하는 쪽이, 칸을 지웠다가 다시 그리는 것보다 낫다.
3. **화면 프레임 규격 확정** — 1440 × 1024 (v1.2에서 16:9로 변경).
4. **프로토타입 경로 명시** — 2장에 실제로 연결한 이동 경로를 적었다.
5. **상위 문서 충돌 기록** — 9.1 신설. 기획서·시스템설계서와 어긋나는 5건을 결정 대기로
   올렸다. 와이어프레임은 결정이 나도 버릴 것이 없도록 중립 표현으로 그렸다.

`apps/web`의 기존 구현은 삭제됐다. **v1.2를 기준으로 새로 만든다.**
목업 이미지(`images/*.png`)도 v0.1 시점 산출물이라 DSH-001은 현재 설계와 다르다.

`./render.sh`로 다시 뽑는다. 수치·문자열은 통합설계 4장의 JSON 예시(`inc-opt-001`,

### 1.4 화면 병합 근거

화면을 늘리는 대신 상태·변형으로 흡수한 지점:

- `GET /assets` 한 번의 응답이 `items[]`(목록)와 `relations[]`(토폴로지)를 모두 담으므로 **AST-001 한 화면의 뷰 전환**으로 둔다. 두 화면으로 나누면 같은 응답을 두 번 조회하게 된다.
- `GET /incidents/{id}`는 A·B를 하나의 응답 형태로 표현하고 `incident_type`으로 구분하므로 **INC-002 한 화면의 두 변형**으로 둔다.
- 실행 진행·성공·실패·롤백은 같은 Execution의 `status`·`phase` 변화이므로 **ACT-002 한 패널의 상태**로 둔다.

## 2. 화면 흐름도

### 2.1 흐름 A — 자산 최적화

```text
DSH-001 (메인 대시보드)
  │  자산 카드 클릭
  ▼
AST-001 (자산 관제)
  │  자산 행/노드 클릭
  ▼
AST-002 (자산 상세 패널)
  │  incident_refs 클릭
  ▼
INC-002 (인시던트 상세 · OPTIMIZATION 변형)
  │  [이 조치 실행] 클릭        ← action.mode = RECOMMENDED 일 때만 노출
  ▼
ACT-001 (실행 확인 모달)
  │  [실행] 클릭 → POST /actions/execute
  ▼
ACT-002 (실행 상태 패널)  ← WS로 최종 상태까지 갱신
```

### 2.2 흐름 B — 보안 위협

```text
(WS SECURITY_INCIDENT_UPDATED 수신)
  ▼
CMN-001 (Alert Toast)
  │  [상세 보기] 클릭
  ▼
INC-002 (인시던트 상세 · SECURITY 변형)
  │  [차단 해제] 클릭          ← action.mode = PREEMPTIVE_EXECUTED
  │                              && rollback_available = true 일 때만 노출
  ▼
ACT-001 (실행 확인 모달 · 해제 변형)
  │  [해제 실행] 클릭 → POST /actions/execute (ROLLBACK_EXECUTION)
  ▼
ACT-002 (실행 상태 패널)
```

`[차단 유지]`는 화면 조작이며 API를 호출하지 않는다. Incident를 읽음 처리하고 목록으로 돌아간다.

### 2.4 프로토타입 연결

와이어프레임에는 위 경로가 클릭 인터랙션(`ON_CLICK` → `NAVIGATE`)으로 연결돼 있다.
Figma 우측 `프로토타입` 탭에서 확인하고 ▶ 로 클릭해 볼 수 있다.

**플로우 시작점 2개**

| 시작점 | 프레임 |
| --- | --- |
| 흐름 A — 자산 최적화 | DSH-001 |
| 흐름 B — 보안 위협 (Toast 수신) | CMN-001 |

흐름 B가 Toast에서 시작하는 것은 2.2를 따른 것이다. 실제 방아쇠는 WebSocket
`SECURITY_INCIDENT_UPDATED` 수신이라 화면 조작으로 재현할 수 없으므로, 프로토타입에서는
CMN-001을 시작점으로 대신 둔다.

**되돌아가는 경로**

| 조작 | 도착 |
| --- | --- |
| INC-002 `← 인시던트` | INC-001 |
| ACT-001 `취소` | 원래 INC-002 (A는 A 변형, B는 B 변형) |
| INC-002 B `차단 유지` | INC-001. API를 호출하지 않는 화면 조작이다 |
| AST-001 목록 ⇄ 토폴로지 | 같은 화면의 뷰 전환. 재조회하지 않는다 |

`ACT-002 실행 상태 6종`과 `CMN-002`는 클릭 흐름의 목적지가 아닌 **참조용 카탈로그**라
프로토타입에서 제외했다. 와이어프레임 코드에 `catalog: true`로 표시돼 있다.

### 3.2.1 Runbook 사전

Guardrail 2단계(Action Whitelist)가 대조하는 허용 목록이며, 화면은 여기 있는 ID만 표시한다.
**출처**를 반드시 구분한다 — 추정 ID를 확정된 것처럼 쓰면 백엔드와 어긋난다.

| Runbook ID | 표시 | 대상 | 파괴적 | 출처 |
| --- | --- | --- | --- | --- |
| `RUNBOOK_EC2_RIGHTSIZING` | EC2 스펙 조정 | EC2 | | 팀장 문서 |
| `RUNBOOK_EC2_ENABLE_AUTOSCALING` | Auto Scaling 전환 | EC2 | | 팀장 문서 |
| `RUNBOOK_EBS_DELETE_UNATTACHED` | 미연결 EBS 삭제 | EBS | **예** | 팀장 문서 |
| `RUNBOOK_EC2_ISOLATE` | EC2 격리 | EC2 | | 팀장 문서 |
| `RUNBOOK_EC2_DOWNSIZE` | EC2 다운사이징 | EC2 | | 통합설계 4장 |
| `RUNBOOK_IP_BLOCK` | Source IP 차단 | SG | | 통합설계 4장 |
| ⏳ `RUNBOOK_SG_ISOLATE` | 격리 SG로 교체 | SG | | **추정** |
| ⏳ `RUNBOOK_ALB_DEREGISTER` | ALB 타겟 이탈 | ALB | | **추정** |
| ⏳ `RUNBOOK_NACL_DENY_IP` | NACL DENY 추가 | NACL | | **추정** |
| ⏳ `RUNBOOK_IAM_KEY_ROTATE` | IAM Key 회전 | IAM | | **추정** |
| ⏳ `RUNBOOK_EC2_REDEPLOY_CLEAN_AMI` | 클린 AMI 재배포 | EC2 | **예** | **추정** |

팀장 문서는 보안 런북이 **7개**라고 했으나 `RUNBOOK_EC2_ISOLATE` 하나만 명시했다.
나머지는 흐름 설명에서 유추한 것이라 ⏳로 표시했다 (9장 #13).

`RUNBOOK_EC2_RIGHTSIZING`과 계약의 `RUNBOOK_EC2_DOWNSIZE`는 같은 조치로 보이나
이름이 다르다. 어느 쪽으로 통일할지 확인이 필요하다 (9장 #14).

**파괴적 조치**로 표시된 런북은 실행 확인 모달에서 되돌릴 수 없음을 경고하고,
사전 백업(EBS 최종 스냅샷 등) 수행 여부를 명시한다 (4.6).

### 3.2.2 승인 상태

| 값 | 표시 | 색 |
| --- | --- | --- |
| `PENDING_APPROVAL` | 승인 대기 | 노랑 |
| `APPROVED` | 승인됨 | 파랑 |
| `REJECTED` | 반려됨 | 회색 |
| `EXECUTION_BLOCKED` | 실행 차단 | 빨강 |

`EXECUTION_BLOCKED`는 Guardrail 실패 또는 승인 거절로 종료된 상태다 (시스템설계서 표4).

### 3.3 값 없음 처리

계약이 `null`과 `[]`를 구분해서 보내므로 화면도 구분한다.

| 상황 | 표시 |
| --- | --- |
| `health_score = null` | 게이지 대신 `—` 와 `확인 불가` 배지. 0으로 그리지 않는다 |
| `initial_risk = null` (A) | 위험도 영역 자체를 렌더하지 않는다 |
| `reviewed_risk = null` (B) | `정밀평가 진행 중` 또는 `정밀평가 실패` (`analysis_status` 기준) |
| `evidence = []` | `표시할 근거가 없습니다` |
| `incident_refs = []` | 자산 카드에 인시던트 영역 미표시 |
| `execution_id = null` | 실행 이력 영역 미표시 |

### 3.4 판단 근거 표시 원칙

- `decision_summary`는 3줄 문자열 배열이며 그대로 3줄로 렌더한다. 요약·병합·재작성하지 않는다.
- raw Chain-of-Thought는 계약에 없으므로 화면에도 없다. Evidence는 `evidence_id`를 그대로 노출해 감사 대조가 가능하게 한다.

### 3.5 절대 하지 않는 것

`POST /actions/execute`에 `target_arn`·`parameters`·복구값을 절대 담지 않는다. 화면은 이 값들을 **표시 전용**으로만 다룬다. 실행 문맥은 서버가 `incident_id`로 재구성한다.

**데이터 바인딩 — 1행**

| 화면 요소 | 산출 방식 |
| --- | --- |
| 메인 시그널 문구 | `items[]`에 `health_status=CRITICAL`이 있거나 미조치 `SECURITY` 인시던트가 있으면 `주의가 필요합니다`, 아니면 `All Systems Operational` |

| 최근 수집 | `items[].collected_at` 중 최댓값 |
| 헬스 게이지 | `items[].health_score` 평균. 전부 `null`이면 `—` + `확인 불가` ⚠️ 확인 #5 |
| 추천 실행 / 차단 해제 건수 | `action.mode = RECOMMENDED` 수 / `action.rollback_available = true` 수 |

**데이터 바인딩 — 2행**

| 화면 요소 | 산출 방식 |
| --- | --- |
| 자산 통계 — 자원 유형 도넛 | `items[]`를 `resource_type` 5종으로 group by |
| 자산 통계 — CPU 사용률 분포 | ⏳ 최근 14일 CPU 평균을 구간별(0–5% / 5–20% / 20%+)로. 5% 미만이 Idle 판정 후보 (9장 #24) |
| 자산 통계 — 리전 · AZ 분포 | ⏳ 자산별 AZ 필드 필요 (9장 #23) |
| 보안 위협 맵 — 소스 노드 | `SECURITY` 인시던트의 `action.parameters.blocked_ip_cidr` |
| 보안 위협 맵 — 대상 SG | `asset_refs` → `items[]` 조인, `action.mode = PREEMPTIVE_EXECUTED` 표시 |
| 보안 위협 맵 — 영향 자산 | 해당 SG를 가리키는 `relations[]`의 EC2 |
| 인시던트 카드 | `incident_type` / `title` / `incident_status` / 위험도 전이 / `action.runbook_id` |

자산 토폴로지와 보안 위협 맵을 나눈 이유는 **그래프가 다르기 때문**이다. 보안 맵에는 자산 쪽에 없는
외부 Source IP 노드가 들어가 공격 경로(외부 IP → SG → EC2)를 만든다. 같은 그래프에 색만 덧칠해서는
나오지 않는다. 기획서 Web 보안관제 스코프의 `실시간 토폴로지 위협 맵`이 이것이다.

**데이터 바인딩 — 3행**

| 카드 | 산출 방식 |
| --- | --- |
| 자산 분포 · Rule 판정 | 도넛은 `resource_type` **5종** 분포, 목록은 EC2/SG · EBS 미연결 · ALB/EIP · 낭비 후보 |
| 위험도 현황 | `initial_risk.level`·`reviewed_risk.level` 분포, `reviewed_risk = null`은 `평가 대기`, `analysis_status = FAILED`는 `평가 실패` |

| 수집 · 실행 | `collected_at` 최댓값·최솟값, WS `STATE_SNAPSHOT`의 진행 중 Execution 수 ⚠️ 확인 #4, `analysis_status = IN_PROGRESS` 수 |

분석 진행 중 건수를 표면에 둔 이유는, 계약상 AI 분석이 실패해도 자산 조회는 유지되기 때문이다.
숨기면 추천이 없는 것과 분석이 죽은 것을 구분할 수 없다.

```text
`미연결`은 비용이 계속 청구되는 상태이므로 주황으로 표기한다.
```

| 판정 | `rule_result.is_idle`·`is_unused`가 true면 판정 배지, false·null이고 `skip_reason_code`가 있으면 Skip 사유 |

| 트래픽 유입 경로 | 상단에 `외부 요청 ▶ WAF ▶ ALB ▶ AZ별 EC2 분산` 을 고정 표시 |

| AZ 구분 | 행마다 `AZ-a` · `AZ-c` 배지. Multi-AZ 분산이 보이게 한다 |
| 갱신 시각 | `generated_at` |

**액션** — 행/노드 클릭 → AST-002 열기. 목록 ⇄ 토폴로지 전환은 **재조회 없이** 동일 응답을 재사용한다.

**예외**

- 페이지네이션은 MVP 계약에 없다. 응답 전량을 렌더한다.
- `relations = []`면 토폴로지는 연결선 없는 노드만 그린다. 빈 화면으로 두지 않는다.
- 미사용 SG는 탐지·표시 대상이지만 허용 Runbook이 없다. `skip_reason_code = SKIP_RUNBOOK_UNAVAILABLE`이면 실행 버튼을 노출하지 않는다.
- **미연결 EBS·EIP는 비용이 계속 청구되므로** `state`를 `미연결 (비용 발생)`으로 주황 표기한다. EBS는 `RUNBOOK_EBS_DELETE_UNATTACHED` 실행 후보이며 **파괴적 조치**다 (4.6).
- 미연결 자원은 **트래픽 경로 밖** 영역에 따로 모은다. 경로 안에 섞으면 "연결돼 있는데 안 쓰는 것"과 "아예 연결이 없는 것"이 구분되지 않는다.

**트래픽 유입 경로를 그리는 이유**

정적인 연결선만으로는 "이 EC2가 왜 중요한가"가 보이지 않는다. 외부 요청이 어디로 들어와
어느 자산을 거치는지 보여야 조치의 영향 범위를 판단할 수 있다. 팀장 보안 명세의
`외부 요청 → WAF → ALB → Multi-AZ EC2` 를 그대로 옮긴 것이며, 보안 위협 맵(4.1)의
공격 경로와 같은 축을 쓴다.

⏳ 계약의 `relations[]`는 `relation_type`이 `ATTACHED_TO` 하나뿐이라 방향과 경로를
표현할 수 없다. 트래픽 경로용 관계 유형이 필요하다 (9장 #23).

### 4.4 INC-001 인시던트 목록

> ⚠️ **이 화면은 현재 계약으로 완전하게 구현되지 않는다. 9장 1번 항목.**

**목적** — A 최적화 진단과 B 보안 위협을 한 목록에서 처리한다.

**계약 공백과 임시 구현안**

MVP 계약에는 `GET /incidents/{id}` 단건 조회만 있고 목록 API가 없다. 현재 계약으로 인시던트 집합을 얻는 경로는 두 개뿐이다.

| 경로 | 얻는 것 | 한계 |
| --- | --- | --- |
| `GET /assets` → `items[].incident_refs[]` | `incident_id`, `incident_type` | `title`·`incident_status`·위험도가 없어 카드를 그리려면 건별 `GET /incidents/{id}` 필요 → **N+1** |
| WS `STATE_SNAPSHOT` | 현재 B Incident, 진행 중 C Execution | A `OPTIMIZATION` 인시던트가 포함되지 않음 ⚠️ (data 스키마 미정의) |

임시 구현: 두 경로의 `incident_id`를 합집합으로 모으고 건별 조회로 채운다. MVP 자산 규모(단일 계정·1~2 리전)에서는 동작하지만 목록 API가 나오면 즉시 교체한다.

```text
┌─────────────────────────────────────────────────────────────────────┐
│  인시던트                                                           │
│  유형 [전체 ▾]  상태 [전체 ▾]                                      │
├─────────────────────────────────────────────────────────────────────┤
│ ┌─────────────────────────────────────────────────────────────────┐ │
│ │ [보안]  SSH Brute Force 선제 차단              조치됨           │ │
│ │ 위험도  높음 → 중간                                             │ │
│ │ 대상    demo-api-sg                            선제 차단됨      │ │
│ │ 08-12 09:12                                    [해제 가능]      │ │
│ └─────────────────────────────────────────────────────────────────┘ │
│ ┌─────────────────────────────────────────────────────────────────┐ │
│ │ [최적화] Idle EC2 다운사이징 후보              미조치           │ │
│ │ 대상    demo-api                               조치 제안        │ │
│ │ 08-12 09:11                                                     │ │
│ └─────────────────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────────────────┘
```

**정렬** — `updated_at` 내림차순. 미조치 `SECURITY`를 최상단 고정.

**데이터 바인딩** — 카드 필드는 모두 `GET /incidents/{id}` 응답 기준: `incident_type`·`title`·`incident_status`·`initial_risk.level`·`reviewed_risk.level`·`asset_refs[0]`·`action.mode`·`action.rollback_available`·`updated_at`.

**액션** — 카드 클릭 → INC-002. 목록에서 직접 실행하지 않는다. 실행은 근거를 확인한 상세에서만 가능해야 한다.

| `PREEMPTIVE_EXECUTED` | `false` | `[차단 유지]` 만 |
| `NONE` | — | 없음 (조회 전용) |

`analysis_status = IN_PROGRESS` \| `FAILED`이면 A의 실행 버튼을 비활성화한다. B는 이미 차단이 수행된 상태이므로 정밀평가 실패와 무관하게 해제 버튼을 유지한다(자동 해제하지 않는다는 계약과 일치).

**예외**

- `404 INCIDENT_NOT_FOUND` → CMN-002 전체 오류 상태.
- B에서 `reviewed_risk = null` → 정밀 평가 카드 자리에 `analysis_status` 기반 안내(`정밀평가 진행 중` / `정밀평가 실패`)를 넣고 카드 자리는 유지한다. 카드를 없애면 초기 판정만 있는 것처럼 오독된다.
- 두 위험도가 다를 때 어느 쪽도 강조하지 않는다. 병렬 표시하고 자동 해제하지 않는다는 안내 문구를 항상 붙인다.

### 4.6 ACT-001 원클릭 실행 확인

**목적** — 되돌리기 어려운 AWS 변경 직전에 대상과 결과를 한 번 더 확정한다. 중복 클릭을 여기서 차단한다.

**A 변형**

```text
        ┌────────────────────────────────────────────────┐
        │  선택한 조치를 실행합니다                      │
        ├────────────────────────────────────────────────┤
        │  대상    demo-api                              │
        │  실행할 런북 (3건 중 선택)                     │
        │   ☑ 스펙 조정      t3.xlarge → t3.large        │
        │   ☑ ASG 전환       min 1 / max 4               │
        │   ☑ 미연결 EBS 삭제              [파괴적]      │
        │                                                │
        │  ⚠ 파괴적 조치 포함 — EBS 삭제 직전 최종        │
        │    스냅샷을 강제 생성합니다                     │
        │                                                │
        │  절감 예상  월 $000 (00%)                       │
        │  Guardrail 4단계 → 승인 요청 → 실행             │
        │                                                │
        │                  [ 취소 ]  [ 승인 요청 ]       │
        └────────────────────────────────────────────────┘
```

**B 변형**

```text
        ┌────────────────────────────────────────────────┐
        │  선제 차단을 해제합니다                        │
        ├────────────────────────────────────────────────┤
        │  대상 SG   sg-0123456789abcdef0                │
        │  해제 대상 203.0.113.10/32 차단 규칙           │
        │  원본 실행 exe-block-001                       │
        │                                                │
        │  해제하면 해당 IP의 접근이 다시 허용됩니다.     │
        │  원본 차단 이력은 보존됩니다.                   │
        │                                                │
        │                    [ 취소 ]  [ 해제 실행 ]     │
        └────────────────────────────────────────────────┘
```

**요청 구성** — 표시값과 전송값을 분리한다. 모달에 보이는 ARN·스펙·IP는 **전송하지 않는다.**

| `action_type` | 전송 필드 |
| --- | --- |
| `EXECUTE_RUNBOOK` | `incident_id`, `action_type`, `runbook_id`, `original_execution_id: null`, `idempotency_key` |
| `ROLLBACK_EXECUTION` | `incident_id`, `action_type`, `runbook_id: null`, `original_execution_id`, `idempotency_key` |

**`idempotency_key` 생성 규칙**

- 모달이 **열릴 때** 1회 생성하고 모달 인스턴스 수명 동안 고정한다. 버튼 클릭 시점에 만들면 중복 클릭이 서로 다른 키가 되어 멱등성이 무력화된다.
- 취소 후 재진입하면 새 키를 만든다.
- 실행 버튼은 첫 클릭 즉시 비활성 + 스피너로 전환한다.

**파괴적 조치 처리**

3.2.1에서 `파괴적`으로 표시된 런북(`RUNBOOK_EBS_DELETE_UNATTACHED`,
`RUNBOOK_EC2_REDEPLOY_CLEAN_AMI`)이 패키지에 포함되면:

1. 경고 블록을 **강조 표시**하고 어떤 자원이 삭제되는지 명시한다
2. 사전 백업 내용을 함께 적는다 — EBS는 **최종 스냅샷 강제 생성**
3. 되돌릴 수 없는 조치임을 문장으로 말한다. 색만으로 표시하지 않는다

⏳ 런북별 `destructive` 플래그와 백업 수행 여부 필드가 필요하다 (9장 #22).

**응답 처리**

| 응답 | 화면 처리 |
| --- | --- |
| `202` | 모달 닫고 ACT-002를 `IN_PROGRESS`/`RESERVED`로 연다. Guardrail 통과 후 `PENDING_APPROVAL`로 전환되며 APR-001에 올라간다 |
| `200` (`idempotency_reused = true`) | 모달 닫고 ACT-002를 응답의 현재 상태로 연다. `이미 접수된 요청입니다` 안내 |
| `409 IDEMPOTENCY_CONFLICT` | 모달 유지, `요청이 변경되었습니다. 화면을 새로고침한 뒤 다시 시도해 주세요.` |
| `409 ACTION_NOT_AVAILABLE` | 모달 닫고 INC-002 재조회. 상태가 이미 바뀐 경우 |
| `422` / `503` / `500` | 모달 유지 + CMN-002 인라인 오류. 재시도 버튼 제공 |

### 4.7 ACT-002 실행 상태 패널

**목적** — REST 202로 시작해 WebSocket으로 최종 상태까지 따라간다. INC-002 하단에 인라인으로 붙는다.

```text
├─────────────────────────────────────────────────────────────────────┤
│  실행 상태                                    exe-action-001        │
│                                                                     │
│   ●━━━━━━●━━━━━━●━━━━━━◐──────○──────○                              │
│   예약   검증   백업   실행   점검   완료                            │
│                                                                     │
│   진행 중 · EC2 변경을 실행하고 있습니다.                           │
│                                                                     │
│   ┌─────────────────────────────────────────────────────────────┐  │
│   │ Guardrail 검증                                               │  │
│   │  ✓ 1. Schema Check          ✓ 3. ARN Match                  │  │
│   │  ✓ 2. Action Whitelist      ✓ 4. AWS Dry-Run                │  │
│   └─────────────────────────────────────────────────────────────┘  │
│                                                                     │
│   09:15:30  요청이 접수됐습니다.                                    │
│   09:15:31  Guardrail 검증을 통과했습니다.                          │
│   09:15:32  변경 전 스펙을 저장했습니다.                            │
│   09:15:33  EC2 변경을 실행하고 있습니다.                           │
└─────────────────────────────────────────────────────────────────────┘
```

**진행 표시기 매핑** — `ROLLBACK`을 그대로 한 칸으로 그리면 정상 경로에 섞여 오독된다.
정상 7칸으로 그리고 `ROLLBACK`은 별도 복구 상태로 전환한다.

| `phase` | 표시기 | 라벨 |
| --- | --- | --- |
| `RESERVED` | 1/7 | 예약 |
| `GUARDRAIL_CHECK` | 2/7 | 검증 |
| `APPROVAL` | 3/7 | 승인 — 관제자 One-Click 승인 대기 (APR-001) |
| `SNAPSHOT_SAVE` | 4/7 | 백업 |
| `AWS_EXECUTION` | 5/7 | 실행 |
| `STATUS_CHECK` | 6/7 | 점검 |
| `COMPLETED` | 7/7 | 완료 |
| `ROLLBACK` | 표시기를 복구 진행 바로 교체 | 복구 중 |

**Guardrail 블록** — 시스템설계서의 4단계 표시 요구를 반영한다. ⚠️ 단계별 PASS/FAIL은 PostgreSQL에 저장되지만 REST·WS 계약에 단계별 결과 필드가 없다(9장 3번). 현재 계약에서 표현 가능한 범위:

| 조건 | 표시 |
| --- | --- |
| `phase`가 `GUARDRAIL_CHECK` 이후로 진행 | 4단계 전체 통과로 표시 |
| `status = FAILED` && `error_code = GUARDRAIL_FAILED` | 4단계 전체 실패로 표시, 실패 단계는 특정하지 않음 |

**타임라인** — WS `data.message`를 수신 순서대로 누적한다. `message`는 서버가 만든 사용자용 문장이므로 화면에서 다시 쓰지 않는다.

**최종 상태 표시**

| `status` | 최종 | 표시 |
| --- | --- | --- |
| `IN_PROGRESS` | 아니오 | 진행 바 + 스피너 |
| `SUCCESS` | 예 | ✓ 초록 `조치가 완료됐습니다` |
| `FAILED` | 예 | ✕ 빨강 `실행하지 못했습니다` + `error_code` |
| `ROLLBACK_INITIATED` | 아니오 | ⟲ 주황 `복구를 시작했습니다` + 복구 진행 바 |
| `ROLLED_BACK` | 예 | ⟲ 파랑 `이전 상태로 복구했습니다` |
| `ROLLBACK_FAILED` | 예 | ⚠ 빨강 `복구에 실패했습니다. 수동 확인이 필요합니다` |

⚠️ `ROLLED_BACK`·`ROLLBACK_FAILED`는 계약상 **추가 제안 상태**다. 미채택 시 이 두 행은 `FAILED` + `error_code`로 축약된다(9장 2번).

**로딩 종료 조건** — 최종 상태(`SUCCESS`·`FAILED`·`ROLLED_BACK`·`ROLLBACK_FAILED`) 수신 시 스피너를 끄고 INC-002를 재조회한다. 최종 상태 수신 없이 WS가 끊기면 재연결 후 `STATE_SNAPSHOT`으로 복구한다.

### 4.8 CMN-001 실시간 알림·연결 상태

**목적** — WebSocket 수명주기를 화면 하나가 소유한다. 페이지가 각자 연결을 열지 않는다.

```text
GNB 우측:
  ● 실시간 연결됨      (초록)
  ◐ 재연결 중…         (노랑, 스피너)
  ○ 연결 끊김 [재연결] (회색, 수동 버튼)

우하단 Toast:
  ┌──────────────────────────────────────────┐
  │ 🔴 보안 위협 감지                        │
  │ 허용된 범위에서 Source IP 선제 차단을    │
  │ 완료했습니다.                            │
  │                          [ 상세 보기 ]   │
  └──────────────────────────────────────────┘
```

**이벤트 처리**

| `event_type` | 처리 |
| --- | --- |
| `STATE_SNAPSHOT` | 전역 스토어를 통째로 교체. Toast 없음 |
| `SECURITY_INCIDENT_UPDATED` | Toast + 해당 `incident_id` 갱신. INC-002를 보고 있으면 인플레이스 갱신 |
| `ACTION_EXECUTION_UPDATED` | ACT-002 갱신. Toast는 최종 상태에서만 |
| `ERROR` | 연결·구독 오류. Toast(회색). 실행 상태로 오해되지 않게 문구를 구분 |

**Toast 정책**

⏳ **위치 결정 대기.** 기획서는 `상단 Alert Toast`, 계약 기준 본 문서는 우하단 스택이다 (9.1 C3).
와이어프레임에는 우하단 안으로 그려두고 결정 대기를 표기했다.

- `SECURITY_INCIDENT_UPDATED`는 항상 표시. 8초 유지.
- `ACTION_EXECUTION_UPDATED`는 최종 상태에서만 표시. 중간 `phase`마다 띄우면 한 번의 실행이 5~6회 알림이 된다.
- 동일 `incident_id`의 Toast는 최신 1건으로 대체한다.
- 최대 3개 스택, 초과 시 오래된 것부터 제거.

**연결·복구**

1. 앱 진입 시 1회 연결하고 페이지 이동 중 유지한다.
2. 끊기면 지수 백오프로 재연결한다(1s → 2s → 4s → 8s → 최대 30s).
3. 재연결 성공 시 `STATE_SNAPSHOT`을 기다려 현재 상태를 교체한다. 누락 이벤트 재생은 계약상 없다.
4. 재연결 실패가 지속되면 `연결 끊김` + 수동 `[재연결]` 버튼을 노출한다.

**전달 원칙** — WS 이벤트는 알림이고 상태의 기준이 아니다. 최종 상태 수신 후에는 REST로 재조회해 화면 값을 확정한다.

### 4.9 CMN-002 로딩·빈·오류 상태

**로딩** — 목록·토폴로지·상세는 실제 레이아웃 형태의 스켈레톤을 쓴다. 전체 화면 스피너는 쓰지 않는다.

**빈 상태**

| 화면 | 조건 | 문구 |
| --- | --- | --- |
| AST-001 | `items = []` | `관제 중인 자산이 없습니다.` |
| AST-001 (필터) | 필터 결과 0건 | `조건에 맞는 자산이 없습니다.` + 필터 해제 |
| INC-001 | 인시던트 0건 | `처리할 인시던트가 없습니다. 전체 인프라를 정상 관제 중입니다.` |
| INC-002 근거 | `evidence = []` | `표시할 근거 데이터가 없습니다.` |

INC-001의 빈 상태는 오류가 아니라 **정상 신호**다. 기획서의 "조치 대상이 없어도 정상 관제 중" 요구가 여기에도 적용된다.

**오류 상태** — 공통 응답의 `error.code`로 분기하고, `error.message`를 그대로 표시한다. `details`와 `request_id`는 접기 영역에 둔다.

| HTTP | `error.code` | 화면 처리 |
| --- | --- | --- |
| `404` | `INCIDENT_NOT_FOUND` | 전체 오류 화면 + `목록으로` |
| `409` | `ACTION_NOT_AVAILABLE` | Toast + 해당 Incident 재조회 |
| `409` | `IDEMPOTENCY_CONFLICT` | ACT-001 인라인 오류 (4.6 참조) |
| `422` | `VALIDATION_ERROR` | 인라인 오류. 계약 불일치이므로 사용자 재시도로 해결되지 않음을 명시 |
| `503` | `STATE_STORE_UNAVAILABLE` | 전체 오류 화면 + `다시 시도` |
| `500` | `INTERNAL_ERROR` | 전체 오류 화면 + `request_id` 표시 (문의용) |

`request_id`는 모든 오류 화면에서 복사 가능해야 한다.

### 4.10 APR-001 승인함 (Human-in-the-Loop)

**목적** — AI가 생성한 조치 패키지를 관제자가 확인하고 One-Click으로 승인·반려한다.
자산·보안 두 흐름의 승인이 한 곳에 모인다.

**정렬** — 요청 시각 오름차순. 오래 기다린 건이 위로 온다.

| 화면 요소 | 산출 방식 |
| --- | --- |
| 대기 건수 배지 | `PENDING_APPROVAL` 상태 수 |
| 카드 제목·유형 | 요청 원본 Incident의 `incident_type`·`title` |
| 요약 | A는 절감 예상(금액·비율), B는 위험도·현재 격리 상태 |
| 런북 건수 | 패키지에 포함된 런북 수 |
| 요청자 | ⏳ 승인 API 필요 (9장 #18) |

**액션** — `상세` → INC-002 / `승인` → 실행 시작(ACT-002) / `반려` → `EXECUTION_BLOCKED` 종료

승인은 Guardrail **이후** 단계다. 검증을 통과한 것만 승인함에 올라온다.
반려된 건은 재실행하지 않고 종료하며, 사유를 감사 로그에 남긴다.

### 4.11 INC-003 공격 타임라인 (XAI)

**목적** — CloudTrail · OS Auth Log · WAF Log를 시간순으로 재구성해 공격 시나리오를 보여준다.
`decision_summary` 3줄만으로는 "왜 그렇게 판단했는가"가 설명되지 않는다.

INC-002 B의 `공격 타임라인 보기`에서 진입한다.

| 화면 요소 | 산출 방식 |
| --- | --- |
| 타임라인 행 | 시각 · 로그 출처(WAF/OS Auth/CloudTrail/GuardDuty) · 내용 ⏳ (9장 #20) |
| 근본 원인 블록 | AI가 추론한 인과 사슬. 예: `0.0.0.0/0 SSH 개방 → 자격증명 유출 → IAM Key 탈취` |
| 판단 근거 3줄 | `decision_summary[]` |
| 근거 데이터 | `evidence[]` — 타임라인 행과 `evidence_id`로 대조 |

raw Chain-of-Thought는 여전히 노출하지 않는다. 타임라인은 **로그 사실의 재구성**이고
근본 원인 블록은 그 위에 얹은 AI 판단이다. 둘을 시각적으로 구분한다.

### 4.12 HIS-001 실행 이력 · 감사 로그

**목적** — 누가 언제 무엇을 승인해 어떤 조치가 실행됐는지 전 과정을 남긴다.

| 화면 요소 | 산출 방식 |
| --- | --- |
| 기간·결과 필터 | ⏳ 감사 조회 API (9장 #21) |

3. `ROLLBACK_FAILED`는 자동 재시도 버튼을 두지 않는다. 수동 확인이 필요한 상태이며 임의 재실행은 위험하다.

## 6. 흐름 B 표시 원칙

### 6.1 선제 차단은 이미 일어난 일이다

B의 One-Click은 차단 **승인**이 아니라 이미 수행된 차단의 **해제**다. 화면 문구에서 `차단하시겠습니까`류의 사전 승인 표현을 쓰지 않는다.

### 6.2 두 위험도는 병렬이다

`initial_risk`(규칙 기반)와 `reviewed_risk`(AI 정밀평가)는 서로 다른 필드이며 후자가 전자를 덮어쓰지 않는다. 화면도 하나로 합치거나 한쪽만 보여주지 않는다.

### 6.3 위험도 전이 표기

목록·대시보드의 좁은 공간에서는 `높음 → 중간` 형태로 축약한다.

| 조건 | 표기 |
| --- | --- |
| 둘 다 있음 | `{initial} → {reviewed}` |
| `reviewed_risk = null`, `analysis_status = IN_PROGRESS` | `{initial} → 평가 중` |
| `reviewed_risk = null`, `analysis_status = FAILED` | `{initial} → 평가 실패` |
| 둘 다 `null` (A) | 위험도 영역 미표시 |

### 6.4 차단 상태와 분석 상태를 섞지 않는다

정밀평가가 실패해도 실제 차단은 유지된다. `analysis_status = FAILED`가 차단 실패로 읽히지 않도록 두 배지를 다른 영역에 배치한다(위험도 카드 / 수행된 조치 카드).

## 7. 흐름 A 표시 원칙

### 7.1 조회는 재분석하지 않는다

`GET /assets`·`GET /incidents/{id}`는 저장된 결과만 읽는다. 화면에 `재분석`·`다시 판정` 버튼을 만들지 않는다. `⟳`는 재조회 아이콘이며 `generated_at` 갱신만 의미한다.

### 7.2 수집 실패 자산을 정상으로 표시하지 않는다

수집 실패·Metric 부족 자산은 `데이터 확인 불가`로 남기는 것이 계약이다. 화면은 `health_status = UNKNOWN`, `health_score = null`, `skip_reason_code = SKIP_METRIC_INSUFFICIENT`를 정상(초록)으로 렌더하지 않는다.

### 7.3 미사용 SG는 표시하되 실행 대상이 아니다

MVP에 SG 정리 Runbook이 없다. 토폴로지에서 하이라이트하되 실행 버튼은 만들지 않으며, 이유를 `실행 가능한 조치 없음`으로 명시한다.

### 9.1 상위 문서 충돌 (결정 대기)

통합설계 3.7이 `MEDIUM 포함안은 별도 검토 문서로 유지`라고 적었으므로 C5는 계약 쪽이
의도적으로 보류한 것으로 보인다. C4는 계약에 언급 자체가 없다.

## 11. 확인 기준

이 초안이 통과해야 할 조건.

1. 9개 화면의 모든 표시 요소가 계약의 실제 필드로 추적된다. 근거 없는 필드가 없다.
2. 화면이 `POST /actions/execute`에 ARN·스펙·복구값을 보내지 않는다.
3. `initial_risk`와 `reviewed_risk`가 화면에서 병렬로 유지된다.
