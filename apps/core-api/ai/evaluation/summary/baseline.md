# FinOps AI 요약 3줄 — 기준선과 재통과 절차

요약 프롬프트·모델·`capabilities`를 바꿀 때 무엇을 다시 통과시켜야 하는지의 상시 규약이다. 첫 판(`v1`)의 배경과 근거는 Issue #243, 계측 자산은 #237이다. `v2`는 #251, 현재 판 `v3`는 #583 3단계(요약 호출이 decision을 내고 후보 호출이 그것을 전사)다.

이 기준선은 골든 14일 기록 fixture에서 고른 FinOps COST_CANDIDATE EC2 6건의 측정 기록이다. #626 이후 새로 수집하는 1일 관측 입력은 범위 밖이다. SecOps 품질 기준선은 #324에서 별도로 수립한다. Python 이름만 정리할 때도 출력 모델의 JSON Schema title·description과 실제 모델 입력을 보존한다.

## 기준선

- **승인 스냅샷** `apps/core-api/ai/evaluation/summary/summary_prompt_snapshot.json` — 판 이름 · 프롬프트·요청 해시 · 모델·노브 · 판정자 판·해시 · 통과 시점 지표 · 승인 상태(`approval`) · 이전 승인 기록(`history`). 프롬프트 전문은 담지 않는다(ADR-0005 미보존 대상).
- **통과 기준선은 하나** — 관제자가 요약 3줄과 조치 카드만 보고 승인·차단을 고를 수 있는가(`apps/core-api/ai/evaluation/summary/summary_defects.md`). 직접 묻지 않고 **복원 대조**로 잰다: 3줄과 카드만 본 판정자가 판정을 가른 값(`cpu_avg`·`cpu_max`·`cpu_datapoints`)을 복원해 골든 입력과 맞는가.
- **고정 입력 세트** — `datasets/golden/finops/input/asset_inventory_001~003.json`의 `COST_CANDIDATE` EC2 6건(A1·A7·A11·A12·A14·A16). 세트(케이스 ID·입력 지문)는 스냅샷 `fixed_set`에 적혀 있다. 골든이 바뀌는 것은 골든 담당의 일이라 CI로 막지 않는다 — `scripts/finops_eval.py`가 스냅샷과 다르면 알리고, `scripts/finops_judge.py`는 세트가 다른 원자료끼리의 짝 비교를 거절한다. 골든이 바뀐 뒤 처음 프롬프트를 손대는 판이 이전 판을 새 세트에서 그 판 프롬프트로 다시 만들어 짝을 맞춘다(판 번호는 프롬프트의 것이라 골든만 바뀌면 그대로다).

## 현재 기준선 — v3 (2026-11-12)

상태는 셋으로 나눠 적는다.

- **품질 측정 — 수용.** #583 3단계 2라운드에서 합격선을 전부 충족했다. 그래서 작성자(안성일)가 측정 전에 정해 둔 범위(합격선을 넘으면 기준선을 다시 고정, 유료 재측정은 최대 5라운드) 안에서 스냅샷을 다시 고정했다. 측정 뒤에 따로 다시 승인한 것은 아니다(`approval.measurement`).

## 재통과 절차

1. **생성** `uv run python scripts/finops_eval.py --repeats 10 --json <판>.json` — 60실행 · 120호출. 돌리기 전 `--estimate`로 규모를 확인하고 승인받는다. 출력의 `중복 제거 활성 6/6`이 아니면 페이로드가 이전 판과 다르다 — 그 판의 비교는 무효다.
2. **판정** `uv run python scripts/finops_judge.py <이전 판>.json <판>.json --out judged.json` — 이전 판 원자료를 **같은 호출에** 넣어 같은 판정자로 짝 비교한다(결함 2 라벨은 회차마다 흔들려 다른 패스끼리 비교하면 잡음이 섞인다). 원자료의 입력이 현재 골든과 다르면 거절한다 — 정답·사실표를 현재 골든에서 만들기 때문이다. 그때는 골든을 복원하거나 원자료를 다시 만든다. 3단계 지표는 `ai.evaluation.summary.finops_stage3`로 낸다. `metrics`는 호출 없이 원자료에서 decision 뒤집힘·DECISION_MISMATCH·NO_PROPOSAL 비교를 내고, `rationale_supports_decision`은 `packet`·`review-template`·`review-score`로 두 검토자의 독립 판정을 집계한다. 새 문턱 없이 기록하는 것은 decision 뒤집힘·DECISION_MISMATCH·`rationale_supports_decision`이다. NO_PROPOSAL과 계약 위반 FAILED는 아래 합격선(이전 판 이하, 기준 0)을 그대로 따른다.
3. **합격선 대조** — 아래 표. 0→1은 통계로 못 가르므로 안전 항목은 1건이라도 원문을 열어 도구 결함인지 실제인지 판정한다.
4. **판정자 보정 — 보류.** 결함 2·3·4 라벨은 판정자 진단값이며 합격선에 걸리지 않는다. 팀에 관제 도메인 전문가가 없어 비전문가가 매긴 라벨은 판정자 검증이 되지 않으므로, 팀이 관제자 역할을 실제로 해 본 뒤에 붙인다 — 그때도 먼저 붙일 것은 판정자 지적의 **정밀도**(지적한 표현이 문장에 실재하는가) 확인이고, 놓친 결함(재현율)은 전문가 리뷰 없이는 못 잰다. `scripts/finops_judge.py --calibration-sheet`는 그때 쓰라고 남겨 둔 도구다. 진단 라벨의 이중 모델 대조와 갈린 행의 사용자 판정은 라벨을 확인하는 일이며 이 보정을 대신하지 않는다.
5. **반영** — 복원 안 된 값·플래그된 결함 → 어느 줄이 실어야 했나 → 지시문에 있으면 문구 수정, 없으면 1줄 추가, 새 결함 부류면 체크리스트 항목 추가. 결함 목록 밖의 도피·과잉(후보 비움·후보 과다)은 `summary_defects.md §실측이 더한 규칙`에 한 줄로 쌓는다. **반영했으면 1로 돌아간다** — 승인할 문구는 반드시 그 문구로 생성·판정한 결과가 있어야 한다. 라운드 수는 자유지만 마지막 라운드가 최종 문구다.
6. **스냅샷 갱신** — 판 이름을 올리고 해시(`prompt_sha256`·`request_sha256`)·지표·판정자 해시·`fixed_set`을 **마지막 라운드의 원자료**(`--json`)에서 옮겨 적는다. 원자료의 `prompt_sha256`이 현재 `finops_prompt_fingerprint()`와 같아야 한다 — `finops_judge.py`가 현재 문구로 만든 원자료가 없으면 알린다. `previous`에는 같은 판정 호출에서 짝 비교한 이전 판 지표를 적고, 내려가는 승인 기록은 `history`로 옮긴다. `approval`에는 품질 측정 수용과 팀 승인을 따로 적는다. 출력 예시(`outputs`)는 새 판 원자료에서 다시 옮긴다.
7. **PR** — 기준선 갱신의 검토 근거는 스냅샷 diff다. 같은 PR의 다른 변경은 그 PR·이슈의 검토 범위를 따른다.

## 기준선을 읽을 때 (#237 한계)

- 일치율은 유효 출력 2회 이상 케이스만 분모다 — `finops_eval.py`가 `유효 2회 이상 N/6케이스`를 함께 찍는다. FAILED가 많은 판은 이 수가 먼저 줄어든다.
- 사실 정합성 0건은 "숫자 귀속까지 정확"이 아니다 — 입력 어딘가에 있는 수면 통과한다. 귀속은 복원 슬롯(`cpu_avg`·`cpu_max`·`cpu_datapoints`)이 본다.
- `중복 제거 활성 6/6`이 아니면 페이로드가 이전 판과 다르다 — 그 판의 비교는 무효다.
- 결함 2(단정/추정) 라벨은 같은 출력에도 판정자가 흔들린다(v0 실측 42/60 일치). ±6 안의 차이는 잡음으로 본다.

## 무효 조건

`finops_eval.py`가 찍는 조합 라벨이 스냅샷의 모델·노브와 다름 · 전송 실패 >10% · 도구 결함 발견(원자료로 재채점, 재호출 없음) · 고정 입력 세트가 스냅샷과 다름.
