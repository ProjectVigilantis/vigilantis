# SecOps AI 응답 품질 기준 — v1.0.0

v0.5.6으로 측정한 9차의 **21 PASS / 0 FAIL**과 최종 기능 회귀를 근거로 첫 공개 평가 기준선을 **v1.0.0**으로 확정했다. 프롬프트·전달 입력·응답 스키마·모델 설정·답지·rubric은 통과한 내용을 유지한다. 설정·지문·판정 범위와 표현상의 한계는 [실험 요약](results/README.md)에 있다. 이 문서는 해당 품질 기준과 변경 시 재검증 절차를 정의한다.

## 평가 목적과 소비자

관제자가 분석 당시 관측·위험 해석·조치 판단의 근거를 이해할 수 있는지 평가한다. 후보 생성, 가드레일 수용, 현재 실행 가능 상태, 승인, 실행, 통신 효과와 종료를 구분한다. 업무 상태와 사용자 결정은 서버가 보존하며 그래프가 자동 종료를 결정하지 않는다.

그래프 순서는 근거 선행 1회 호출(근거 3줄 + decision) → 코드 실행 계획 조립 → 최종 출력 검증이다(#583 2단계). 대비책 `CANDIDATE_FIRST`(후보 생성·검증 → 요약, 2회 호출)는 `SECOPS_GRAPH_VARIANT` 스위치 뒤에 남아 있다. 위험 재평가 노드는 ADR-0005 1차 개정(#583 1단계)으로 없어졌고, 위험 등급은 서버 초기 판정 하나이며 출력 `reviewed_risk_level`은 null이다. 정상 경로 모델 호출은 1회다 — v1.0.0 측정 당시는 위험 재평가를 포함한 3회였다. 이 문서의 합격선과 v1.0.0 표기는 재측정 전의 공개 기준선이며, **기준선 재고정은 재측정 뒤**에 한다. 공개 계약·서버 초기 위험도·대응 모드·타이머를 변경하지 않는다.

## 입력별 허용 결과

| 입력 | 합성 SSH 관측 | 서버 초기 등급(입력) | 허용 결과와 의미 조건 |
| --- | --- | --- | --- |
| C01 | 120회 / 300초 | HIGH | 후보 또는 무제안. 강한 반복·집중과 제안/보류 이유를 연결 |
| C02 | 1000회 / 60초 | HIGH | 후보 또는 무제안. 매우 강한 집중을 축소하지 않음 |
| C03 | 120회 / 300초, production | HIGH | 후보 또는 무제안. 운영 문맥은 가용성·영향 판단에 사용 |
| C04 | 60회 / 600초 | MEDIUM | 후보 또는 무제안. 반복 관측을 유지 |
| C05 | 5회 / 10초 | MEDIUM | 후보 또는 무제안. 짧은 창의 집중을 C06과 구분 |
| C06 | 5회 / 3600초 | LOW | 후보 또는 무제안. 낮은 빈도의 반복 유지. 후보와 현재 적용 보류가 공존 가능 |
| C07 | 1회 / 1초 | LOW | 후보 또는 무제안. 단발 유지. 분당 환산으로 반복을 만들어 내지 않음 |
| N01·N02 | 실패 0회 성공 인증 통제 | 위협 투영 없음 | 모델 호출 대상 아님. 성공 인증만으로 위협을 생성하지 않음 |

기계 판정의 원천은 [answers.json](answers.json), 의미 판정의 원천은 [rubric.json](rubric.json)이다. `EITHER`는 두 구조화 결과를 허용한다는 뜻이다. 후보의 타당성이나 무제안 이유를 자동 통과시키지 않는다. 강한 관측을 무시한 막연한 관찰 권고, 낮은 신호를 과장한 즉시 차단 명령, 메뉴 존재만 되읽는 이유는 실패다.

이 합성 SSH 세트의 등급은 서버 위험 규칙이 정한 초기 판정이며 그래프 입력으로 전달된다. 그래프는 등급을 다시 매기지 않으므로 구조화 채점은 출력 `reviewed_risk_level`이 null인지 확인한다(`reviewed_risk_present`). v1.0.0까지의 `reviewed_risk_levels` 기대값과 등급 일치 검사는 answers.json에서 뺐다. 관측과 등급을 잇는 설명은 별도의 `risk_reason` 의미 기준으로 평가한다.

후보가 있으면 입력에서 직접 연결된 NACL, 허용된 단일 런북, 같은 위협 evidence ID, 관측 출발지 한 주소의 /32, tcp, 1~32766의 규칙 번호 제안을 지킨다. 이 입력은 모두 IPv4다. 규칙 가용성·우선 적용·실제 통신 효과는 별도 확인 사항이다. 현재 입력에 없는 자원이나 조치까지 허용하지 않는다.

## 요약과 합격선

요약 세 줄 전체와 실제 후보를 함께 읽는다. 관측 사실·위험 이유·조치 이유·합성 출처·실제 조치 범위·사실/시각/실행 과장 금지의 8개 의미 기준과 내부 식별자 노출의 결정적 검사 1개를 사용한다. 세부 기준은 rubric 하나를 정본으로 삼는다. 결정적 검사는 의미 검토가 없어도 노출을 FAIL로 분류하며 추가 모델 호출이 없다.

rubric은 v0.5.5 이후 v2.0.0까지 변경하지 않았다. `scope`의 v0.5.5 표기는 이 기준의 도입 버전이며, 8차·9차와 공개 기준선 v1.0.0에 같은 내용을 적용한다.

v2.0.0(근거 선행 1회 호출)에서 rubric이 바뀌었다. `rationale_supports_decision`(rationale이 실제로 내린 decision을 뒷받침한다)을 필수 항목으로 추가했고 `risk_reason`의 "실제 재평가"를 서버 초기 판정으로 고쳤다. 그래서 의미 항목은 9개이고 합격선은 구조화 21건·의미 항목 9×21=189개·식별자 검사 21건이다. v1.0.0과 1–9차 결과는 당시 rubric 기준의 이력이며 새 rubric의 `--report`로 다시 채점할 수 없다(rubric 지문이 달라 거부된다).

## 반복 안정성

같은 입력을 3회(`--repeats 3`) 반복해 두 가지를 분리해 보고한다.

- 구조화 PASS: `EITHER` 허용에 따라 후보와 무제안을 모두 통과시킨다. 실행별 허용이며 안정성이 아니다.
- decision 뒤집힘 비율(`decision_flip`): 사례별로 오류 없이 끝난 2회 이상의 출력에서 결정 집합(후보 runbook ID 집합, 무제안은 빈 집합)을 구해 `1 - 최빈 결정 집합의 비율`을 낸다. 후보↔무제안도 뒤집힘이다. 전체는 `cases_with_flip / cases_measured`로 보고한다.

`EITHER` 허용으로 PASS여도 뒤집힘 비율은 별도로 읽는다. 둘 다 보고하며 한쪽으로 다른 쪽을 대신하지 않는다.

후보를 제시하며 현재 적용을 보류할 수 있다. 동일한 관측·진단 설명을 후보 유무 때문에 바꿀 필요는 없다. 단, 실제 후보나 값이 있는데 없다고 하는 설명은 실패다. 중요한 조치 범위와 현재 적용 판단을 설명하되 구조화 파라미터 전부의 재기재나 고정 경고문은 강제하지 않는다. 정상 사용 여부 확인과 차단의 정상 통신 영향 검증을 같은 사실로 취급하지 않는다.

**같은 동결 입력·프롬프트·답지·rubric·서비스 설정으로 C01~C07 × 3회, 구조화 21건·의미 항목 168개(v1.0.0 기준의 과거 규칙이며 v2.0.0 rubric은 189개)·식별자 검사 21건이 모두 PASS**여야 해당 품질 측정 충족이다. 누락·미완료·오류·UNSURE를 분모에서 제외하지 않는다. 실제 모델의 반환 식별자와 서비스 설정 일치도 확인한다. 재시도·전송 장애와 내용 실패는 구분한다.

의미 검토자는 실제 인용·판정 이유·이름·사람/assistant 구분을 남긴다. 인용·지문·집계 스크립트는 의미 자동 판정의 정확성을 보증하지 않는다. 별도 유료 판정자 호출은 없다.


## 기준 변경과 이전 결과

v0.5.2까지의 후보 필수·무제안 필수 조건은 v0.5.3부터 근거 있는 후보·무제안을 모두 허용하는 기준으로 바뀌었다. 5차의 원래 판정과 같은 출력의 재분류를 구분하며, 7차 당시 통과와 후속 내부 식별자 검사 실패도 구분한다. 기준 변경 이유는 [품질 개선 근거](defects.md), 각 회차의 당시 결과는 [실험 요약](results/README.md)에 정리했다.

## 품질 측정과 별도인 범위

7건은 모두 합성 SSH 입력이며 선행 실행 기록이 없다. 실제 공격 탐지율·운영 침해 여부, OpenIP, 선행 실행 분기, 실제 AWS 실행·통신 효과는 이번 측정의 보장이 아니다. 모든 허용 분기의 출력을 강제로 확보하지 않으며 미관측 분기는 미관측으로 보고한다.

분석 결과의 저장·표시·사용자 종료 처리는 서비스 계층의 별도 책임이다. 이 그래프 품질 결과로 그 통합 성공을 판정하지 않는다. 코드 변경에 필요한 검증과 최종 기능 회귀는 변경 범위에 따라 수행하고 PR·CI에 결과를 남긴다.

## 프롬프트/입력/rubric이 바뀌면 무엇을 다시 돌리는가

| 변경 | 다시 수행할 작업 |
| --- | --- |
| FinOps 코드·주석 등 SecOps 요청과 무관한 변경 | `--check-inputs` 후 보존 결과에 `--report`. `request_sha256`과 서비스 설정이 같으면 요청 호환성을 유지한다. 파일 지문 차이는 `source_files_match`로 별도 표시한다. |
| 지문 계산 범위만 수정하고 실제 SecOps 요청은 유지 | 수정 전후의 요청 지문·서비스 설정과 입력·답지·rubric 일치를 확인하고 보존 결과에 `--report`. 계산 방식 변경과 이전 지문을 남겨 승인 지문만 재등록한다. 새 유료 측정이나 프롬프트 버전 변경으로 세지 않는다. |
| SecOps 프롬프트·전달 JSON·응답 스키마·모델 설정 변경 | 변경판과 호출 계획을 기록하고 후보 지문을 고정한다. 승인받은 새 7건 × 3회 측정·의미 검토 후 `--report`로 판정한다. |
| 동결 입력·답지 변경 | 변경 이유와 이전 입력·답지를 보존하고 새 세트를 검토한다. 입력 변경은 새 측정, 답지만 변경한 경우에는 기존 출력 재채점 가능성을 별도로 판단한다. 기존 점수를 새 버전으로 덮어쓰지 않는다. |
| rubric·결정적 채점 기준 변경 | 기준을 먼저 고정하고 기존 출력의 재분류와 새 측정을 구분한다. 검토 파일은 새 rubric에 맞춰 다시 작성한다. 출력 개선을 검증하려면 승인받은 새 측정이 필요하다. |
| Golden·corpus 원본만 변경 | CI는 동결 fixture로 계속 검증한다. 계측 CLI의 드리프트를 확인하고 입력 갱신 여부를 결정한 뒤 측정한다. |

`current_service`는 동결 답지로 재구성한 요청과 서비스 설정의 호환성이다. 전체 서비스의 DB·AWS·화면·종료 동작이 같다는 뜻이 아니다. 후보 있음·없음 두 대역 경로를 포함해도 실제 모델이 두 경로를 생성했다는 관측은 아니다. 요청 지문이 없는 과거 결과는 `request_fingerprint_recorded=false`, `current_service=false`로 남긴다.

근거 선행 호출은 조치 메뉴를 목적 문구로만 보내고 파라미터 제약을 모델에 보내지 않는다. 그래서 프롬프트 지문은 근거 프롬프트와 `SecOpsEvidenceDecisionOutput` 스키마로만 계산하며 제약 변경은 SecOps 요청을 바꾸지 않는다. 대비책(`CANDIDATE_FIRST`)의 프롬프트 지문은 1단계 구성(요약·후보 프롬프트, 두 스키마, 전체 동결 세트의 SecOps 메뉴 제약)을 유지한다. 요청 지문은 기본(근거 선행) 그래프 기준이다. `report()`는 `graph_variant`가 `EVIDENCE_FIRST`이고 기록된 프롬프트 지문이 현재 근거 선행 지문과 같을 때만 `current_service`를 true로 하므로(변종 기록이 없는 과거 결과도 지문이 같아야 한다) 대비책 측정은 비교용이며 `baseline_candidate`가 될 수 없다. 위험 판정·정규화 코드를 포함한 파일 전문 지문은 `source_files_match` 진단에만 사용한다.

`prompt_snapshot.json`의 `approved`는 품질 기준 충족과 최종 회귀를 확인해 확정한 공개판이며, 현재 **v1.0.0**이다. `measured_version`과 `run_id`는 근거가 된 [v0.5.6의 9차 측정](results/README.md#최종-측정--v056)을 가리킨다. 승격은 새 측정으로 세지 않으며 당시 실험 버전·점수·원자료는 유지한다.

`prompt_sha256`은 현재 계산 방식의 승인 지문이고, `measured_prompt_sha256`은 계산 범위를 바꾸기 전 측정 당시의 값이다. 2026-09-21에는 FinOps 전용 제약을 제외하도록 계산 범위만 수정해 요청·설정의 호환성을 확인하고 재등록했다. 당시 측정 조건은 [실험 요약의 지문 표](results/README.md#측정-조건-지문)에 보존한다.

`candidate`는 보완 중인 후보다. 현재 후보는 근거 선행 1회 호출 그래프의 **v2.0.2**이며 측정 대기(`PENDING`)다. v2.0.0은 2026-11-09 1라운드에서 내부 식별자 검사 15/21 FAIL(서버 사유 코드 원문 인용), v2.0.1은 같은 날 2라운드에서 의미 항목 `rationale_supports_decision` 13/21 FAIL(rationale이 관측 강도→제시 이유를 빠뜨림)로 각각 `FAIL`이 됐고(`replaced_candidates`), rationale 문장 순서를 명시한 것이 v2.0.2다. 위험 재평가 노드를 제거한 v1.1.0([계획](plans/v1.1.0-reassess-removal.md))은 측정된 적 없이 v2.0.0으로 대체됐고 `CANDIDATE_FIRST` 대비책 그래프의 프롬프트로 남는다. 그 앞의 v1.0.1([계획](plans/v1.0.1-nacl-rule-number.md))의 규칙 번호 변경도 포함된다. 재측정 범위와 승인 조건, v2.0.0·v2.0.1 라운드 결과는 [v2.0.2 재측정 계획](plans/v2.0.2-evidence-first.md)에 있다. 후보 상태는 측정 대기(`PENDING`), 실측 기준 충족(`PASS`), 품질 미달(`FAIL`)이고 측정된 상태에는 결과 기록을 연결한다. CI는 후보가 있으면 후보 지문, 없으면 승인판 지문에 현재 프롬프트를 대조한다. 후보의 실측 통과 뒤 최종 회귀와 공개판 확정을 거쳐 승인판으로 옮기며, 지문 고정 자체로 품질을 승인하지 않는다.
