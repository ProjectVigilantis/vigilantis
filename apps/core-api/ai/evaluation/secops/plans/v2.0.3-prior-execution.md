## 결정(10라운드 시점)

9케이스 셋에서 비율 기준을 충족한 판은 없었다. `approved`는 v2.0.2로 두며 7케이스 셋(3라운드 21/21)에서만 유효했다. 배포 프롬프트는 v2.0.5이고 10라운드 결과를 `candidate`, `quality_status` FAIL로 기록했다. 입력 보강 뒤 이 기록은 `history`로 옮겼다.

프롬프트 수정은 멈춘다. 서버 위험 규칙(`security/risk_evaluator.py`의 `_evaluate_ssh_bruteforce`)은 횟수 ≥ 10과 분당 ≥ 20 중 정확히 하나만 충족하면 MEDIUM이고 두 경우 모두 사유 코드 `RISK_SSH_BRUTEFORCE`를 낸다. 10라운드 당시 입력에는 어느 임계값을 충족했는지가 없어 C04(횟수만 충족)와 C05(빈도만 충족)는 v2.0.5와 v2.0.6 사이에서 자리를 바꿨다(C04 10/10↔4/10, C05 5/10↔10/10). C08은 두 판 모두 7/10이었다 — 당시 `ai/capabilities.py`의 `build_secops_capabilities`는 선행 실행 상태를 받지 않아 NACL 목적 문구가 선행 격리 성공을 반영하지 못했다(현재 구현은 아래 입력 보강 후속). C09는 두 판 모두 기준 안(8/10, 9/10)이다. v2.0.5를 택한 이유는 그 C05 결함이 횟수·창은 맞게 쓴 누락인 반면 v2.0.6의 C04 결함은 잘못된 서술이고, v2.0.6이 더한 문장이 C09의 격리 부재 단정도 유발했기 때문이다.

다음 작업으로 코드가 위험 근거와, 선행 격리가 성공한 경우 NACL 조치의 구별되는 목적을 모델 입력에 공급하고 사례별 비율을 보고 지표로 내기로 했다. 구현 내용과 11라운드 결과는 아래 절에 있다.

## 입력 보강 후속

프롬프트 본문(v2.0.5, 지문 `b9d76896…`)·응답 스키마·FinOps·답지·rubric은 바꾸지 않고 모델 입력만 보강했다. 공개 API·DB·ADR·SSOT도 바꾸지 않았다.

- **현재 규칙의 위험 근거:** `security/risk_evaluator.py`의 `classify_ssh_risk_basis`가 SSH 관측을 단발·횟수와 빈도 모두 충족·횟수만 충족·빈도만 충족·둘 다 미충족으로 나누고, `_evaluate_ssh_bruteforce`는 같은 분류에서 기존과 같은 등급·사유 코드를 낸다. Dispatcher는 저장된 관측에 현재 규칙을 다시 적용해 등급·사유 코드가 저장된 초기 판정과 같을 때만 `SecOpsGraphInput.current_rule_risk_basis`를 붙이고, 다르면 생략한다. 이 값은 저장된 관측의 현재 규칙 해석이며 접수 당시의 판정 근거를 보존한 값이 아니다. 초기 등급·사유·대응 모드는 저장값 그대로이고 타이머도 건드리지 않는다. 값은 내부 enum `SshRiskBasis`이며 모델에는 "현재 규칙 기준 …" 형태의 한국어 라벨만 보낸다. 동결 입력의 값은 C01–C03·C08·C09 횟수와 빈도 모두 충족, C04 횟수만 충족, C05 빈도만 충족, C06 둘 다 미충족, C07 단발이다.
- **선행 격리 뒤 NACL 목적:** `ai/capabilities.py`의 `build_secops_capabilities`가 선행 실행 기록을 받는다. 기록이 이 EC2를 영향 대상으로 한 `RUNBOOK_EC2_ISOLATE` SUCCESS일 때만 목적 문구를 "격리 실행이 성공으로 기록된 EC2와 별개로, 같은 서브넷의 다른 호스트를 보호하기 위해 출발지 CIDR 유입을 NACL 거부 규칙으로 차단"으로 바꾼다. 실패·진행 중·미확인 기록, 다른 대상, 다른 런북이면 기존 문구다. 동결 입력에서는 C08만 바뀐다. 이 문구는 기록된 상태를 옮길 뿐 현재 격리 상태나 차단 효과를 확인하지 않는다.
- **후보 등록(11라운드 전):** `candidate`에 v2.0.5 그대로의 프롬프트 지문과 새 입력 지문 `2f7135424546fa81bdab0aeba885620adc60147ddf43310d0a4d9fbba0294167`·요청 지문 `9d387e7e67cd604d4c20c754d1f8700fc41edc73628989ca9909af29ad624b30`을 `quality_status` PENDING으로 기록했다. 10라운드 FAIL(81/90 — C05 5/10·C08 7/10·C09 9/10)은 이전 입력·요청 지문과 함께 `history`에 남는다.
- **사례별 비율 지표:** 보고서에 `case_acceptance`를 더했다. C01–C09 × 정확히 10회일 때 사례마다 PASS 8회 이상인지 내며 오류·누락도 분모에 남는다. 산술 판정(`threshold_met`), 관측 완전성(`measurement.fully_observed`), 기준선 후보 여부(`baseline_candidate`)는 따로 낸다. 기존 `quality_pass`·최상위 `baseline_candidate`와 `--report` 종료 코드(전원 PASS일 때만 0)는 그대로다([품질 기준](../baseline.md)).

## 배경

2단계 재측정 중 동결 입력 7건 모두 `isolation_execution`이 비어 있어, 서비스 HIGH 경로에서 가장 흔한 "자동 선차단(EC2 격리)이 이미 실행된 뒤 분석" 분기가 한 번도 측정되지 않은 것을 확인했다. C01에서 파생한 C08(선행 격리 SUCCESS, 영향 대상 = 해당 EC2)·C09(선행 격리 FAILED, 영향 대상 없음)를 추가하고 로더가 선행 실행 기록을 받도록 바꿨다. 두 케이스의 허용 결과는 후보 또는 무제안(`EITHER`)이며 의미 조건은 `answers.json`의 `action_basis`에 있다.

## 변경

`[rationale]` 절에 선행 실행 기록이 있을 때의 지시를 추가했다: ①에 기록의 런북·상태·영향 대상을 밝히고 결정과 연결한다. 성공이면 제시한 조치가 그 영향 대상과 어떻게 구별되는지를 ②에 쓰고 구별되는 범위가 없으면 조치를 제시하지 않는다. 실패·진행 중이면 대상의 보호가 확인되지 않은 상태임을 ①에 명시하고 제시한 조치가 남은 통제라는 점을 연결한다. 실패 기록을 적용된 것으로 쓰거나 실패가 변경 없음을 증명한다고 쓰지 않는다. 대비책(`CANDIDATE_FIRST`) 프롬프트와 rubric·입력·정답지는 바꾸지 않는다.
