## 결정

9케이스 셋에서 비율 기준을 충족한 판은 없다. `approved`는 v2.0.2로 두며 7케이스 셋(3라운드 21/21)에서만 유효하다. 배포 프롬프트는 v2.0.5이고 `prompt_snapshot.json`에 `candidate`, `quality_status` FAIL로 기록했다.

프롬프트 수정은 멈춘다. 서버 위험 규칙(`security/risk_evaluator.py`의 `_evaluate_ssh_bruteforce`)은 횟수 ≥ 10과 분당 ≥ 20 중 정확히 하나만 충족하면 MEDIUM이고 두 경우 모두 사유 코드 `RISK_SSH_BRUTEFORCE`를 낸다. 입력에 어느 임계값을 충족했는지가 없어 C04(횟수만 충족)와 C05(빈도만 충족)는 v2.0.5와 v2.0.6 사이에서 자리를 바꿨다(C04 10/10↔4/10, C05 5/10↔10/10). C08은 두 판 모두 7/10이다 — `ai/capabilities.py`의 `build_secops_capabilities`가 선행 실행 상태를 받지 않아 NACL 목적 문구가 선행 격리 성공을 모른다. C09는 두 판 모두 기준 안(8/10, 9/10)이다. v2.0.5를 택한 이유는 그 C05 결함이 횟수·창은 맞게 쓴 누락인 반면 v2.0.6의 C04 결함은 잘못된 서술이고, v2.0.6이 더한 문장이 C09의 격리 부재 단정도 유발했기 때문이다.

다음 작업(계획, 미수행): #583 2단계의 후속 작업에서 코드가 위험 근거(횟수 충족·빈도 충족)와, 선행 격리가 성공한 경우 NACL 조치의 구별되는 목적을 모델 입력에 공급하고 10라운드 수치를 기준으로 재측정한다. 사례별 비율의 코드 지표화도 같은 PR에서 한다.

## 배경

2단계 재측정 중 동결 입력 7건 모두 `isolation_execution`이 비어 있어, 서비스 HIGH 경로에서 가장 흔한 "자동 선차단(EC2 격리)이 이미 실행된 뒤 분석" 분기가 한 번도 측정되지 않은 것을 확인했다. C01에서 파생한 C08(선행 격리 SUCCESS, 영향 대상 = 해당 EC2)·C09(선행 격리 FAILED, 영향 대상 없음)를 추가하고 로더가 선행 실행 기록을 받도록 바꿨다. 두 케이스의 허용 결과는 후보 또는 무제안(`EITHER`)이며 의미 조건은 `answers.json`의 `action_basis`에 있다.

## 변경

`[rationale]` 절에 선행 실행 기록이 있을 때의 지시를 추가했다: ①에 기록의 런북·상태·영향 대상을 밝히고 결정과 연결한다. 성공이면 제시한 조치가 그 영향 대상과 어떻게 구별되는지를 ②에 쓰고 구별되는 범위가 없으면 조치를 제시하지 않는다. 실패·진행 중이면 대상의 보호가 확인되지 않은 상태임을 ①에 명시하고 제시한 조치가 남은 통제라는 점을 연결한다. 실패 기록을 적용된 것으로 쓰거나 실패가 변경 없음을 증명한다고 쓰지 않는다. 대비책(`CANDIDATE_FIRST`) 프롬프트와 rubric·입력·정답지는 바꾸지 않는다.
