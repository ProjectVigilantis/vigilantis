# SecOps 재측정 계획 — v2.0.2 (근거 선행 1회 호출)

프롬프트 **v2.0.2**의 재측정 계획이다. 상태: **측정 PASS (2026-11-09)** — 3라운드에서 구조화 21/21·의미 189/189·식별자 21/21·decision 뒤집힘 0/7을 기록해 공개 기준선이 v2.0.2로 재고정됐다. 이 승인은 C01~C07 7사례 세트에서만 유효했고, 2026-11-10 20차에서 9사례 세트의 비율 기준을 충족한 입력 보강 v2.0.5로 대체됐다(`prompt_snapshot.json`의 `history`에 `SUPERSEDED`, [v2.0.3 이후 계획](v2.0.3-prior-execution.md)). 결과·비용 추정·한계는 [실험 요약 12차](../results/README.md#12차--v202-3라운드)에 있다. 이전 기준선 v1.0.0과 1–9차 결과는 이력으로 남는다([품질 기준](../baseline.md)). 아래 본문은 측정 전 계획이며 "미실행"·"PENDING" 표기는 계획 시점의 상태다. 측정 전이던 후보 v1.1.0([계획](v1.1.0-reassess-removal.md))은 v2.0.0으로 대체됐다. v1.1.0은 의미 측정을 받은 적이 없으며(아래 1라운드의 구조화·내부 식별자 비교 측정만 있다) `CANDIDATE_FIRST` 대비책 그래프의 프롬프트로 남는다.

## v2.0.0 1라운드 결과와 v2.0.1

2026-11-09 1라운드(C01~C07 × 3회, `EVIDENCE_FIRST` 21회 + `CANDIDATE_FIRST` 비교 21회·42호출)에서 v2.0.0은 구조화 21/21 PASS, decision 뒤집힘 C07 1/3(후보↔무제안, `EITHER` 허용)이었으나 **내부 식별자 검사 15/21 FAIL**이었다. diagnosis가 서버 초기 판정의 사유 코드(`RISK_SSH_BRUTEFORCE`·`RISK_SSH_LOW_SIGNAL`)를 원문으로 인용했다. 원인은 1단계(v1.1.0)가 넣은 "initial_risk의 사유 코드가 가리키는 사실을 등급에 연결한다" 문장이며, 같은 문장을 가진 대비책 v1.1.0도 19/21 FAIL로 같은 결함을 보였다(1단계는 유료 측정 없이 머지돼 그때 드러나지 않았다). 제안된 상대 비교(근거 선행이 대비책보다 나쁘지 않음)로 보면 근거 선행이 앞섰지만, 절대 합격선은 두 변종 모두 미달이다.

v2.0.1은 v2.0.0에서 그 문장을 "사유가 뜻하는 사실을 … 연결한다. 사유는 그 뜻을 한국어로 풀어 쓰고 사유 코드 식별자를 그대로 옮기지 않는다"로 바꾸고 [표현]에 코드 식별자 금지를 명시했다. 그래프·스키마·메뉴 입력은 v2.0.0과 같다. 대비책 프롬프트는 "1단계 그래프 유지" 원칙대로 고치지 않으며 1라운드 비교 측정값을 그대로 쓴다. 1라운드 원자료는 작성자가 Git 밖에 보관하며 요청하면 공유한다.

## v2.0.1 2라운드 결과와 v2.0.2

같은 날 2라운드(`EVIDENCE_FIRST` 21회)에서 v2.0.1은 구조화 21/21 PASS, 내부 식별자 0 FAIL, decision 뒤집힘 0/7(C07은 3회 모두 무제안)이었다. 의미 검토는 Claude Opus 5.5·GPT 6.1 sol 이중 대조로 수행했고 189행 중 176행이 일치했다. 두 검토자가 일치한 FAIL은 **`rationale_supports_decision` 13건** — 후보를 낸 18건 중 13건의 rationale이 실제 범위와 승인 전 확인만 쓰고, 어떤 관측 강도가 왜 차단 제시로 이어지는지를 빠뜨렸다. 갈린 13행은 같은 기록의 `action_reason`(Opus PASS·GPT FAIL)이며 작성자 판정 대상이다. 원인은 "조치를 제시하면 … 실제 범위를 먼저 설명하고" 지시가 한 문장 안에서 결정 이유를 밀어낸 것이다. 원자료는 작성자가 Git 밖에 보관하며 요청하면 공유한다.

v2.0.2는 rationale 지시를 "① 결정을 가른 관측 강도와 그것이 제시 또는 보류로 이어지는 이유 → ② 실제 범위 → ③ 현재 적용 판단과 다음 확인" 순서로 명시하고 NACL 범위 문장을 ②에 두었다. 그 밖의 문장·그래프·스키마는 v2.0.1과 같다.

## 변경 내용 (#583 2단계)

- 순서: 근거 선행 1회 호출(`summarize_evidence`) → 코드 실행 계획 조립(`assemble_plan`) → 출력 검증(`validate_output_contract`). 후보 생성 호출은 없다.
- 모델 호출은 건당 1회다. 응답(`SecOpsEvidenceDecisionOutput`)은 observation → diagnosis → rationale → `decision` 순서이며, `decision`은 `available_actions`(조치 목적 문구만, 1부터 `action_id`)에서 사람에게 제시할 조치의 목록이다. SecOps는 0개 또는 1개다.
- 실행 계획은 코드가 조립한다: 연결된 NACL 하나(`PROTECTED_BY`), `cidr_block=<출발지 IP>/32`, `protocol=tcp`, 서버가 정한 `rule_number`, 단일 THREAT evidence ID. 모델은 파라미터·ARN·evidence ID를 내지 않으며 파라미터 제약도 받지 않는다.
- decision이 메뉴와 맞지 않으면(범위 밖·중복·SecOps 한도 초과) `AnalysisFailureReason.DECISION_MISMATCH`로 출력 전체가 FAILED다.
- 프롬프트 지문은 근거 프롬프트와 `SecOpsEvidenceDecisionOutput` 스키마다. 요청 지문은 후보 있음·없음 두 경로를 1회 호출로 재구성하며, 후보 있음 경로는 조립된 후보가 [answers.json](../answers.json)과 같은지(runbook·대상·CIDR·protocol·evidence ID·규칙 번호 범위) 모델 호출 없이 확인한다.
- rubric에 필수 항목 `rationale_supports_decision`을 추가했고 `risk_reason`을 서버 초기 판정 기준으로 고쳤다. 의미 항목은 9개다.
- 보고에 `decision_flip`(결정 뒤집힘 비율)을 추가했다.

## 재측정 계획 (미실행)

- 시점: 별도 승인 후 수행한다. 이 계획은 측정 준비만 담는다. 기준선 재고정은 측정·검토·최종 회귀 뒤에 한다.
- 규모: C01~C07 × 3회 = 그래프 21회 = 논리 모델 호출 21회. 전송 재시도(`OPENAI_MAX_ATTEMPTS` 3)를 포함한 HTTP 시도는 최대 63회다.
- 비교 라운드: 같은 조건에서 `--variant CANDIDATE_FIRST`로 21회 = 모델 호출 42회(HTTP 시도 최대 126회). 비교용이며 요청 지문이 달라 `current_service`는 false로 남는다. 2026-11-09 1라운드에서 이미 수행했고 v2.0.1 재측정에는 반복하지 않는다(대비책 프롬프트가 바뀌지 않았다).
- 조건: 동결 입력·답지·rubric과 측정 시점의 후보 프롬프트. 모델 설정은 승인 요청 시점의 현재 서비스 설정을 쓴다.
- 사전 승인: 측정 라운드마다 실행 전에 열 수·호출 수·추정 비용·소요 시간·원자료 저장 경로를 보고하고 별도 승인을 받는다.
- 원자료: 작성자가 Git 밖에 보관하며 요청하면 공유한다. 임시 폴더에 저장하지 않는다.
- 판정 점검: 정답지·채점·프롬프트 감사처럼 판단이 들어가는 점검은 같은 브리프를 Claude Opus 5.5(effort high)와 GPT 6.1 sol(effort high)에 각각 주고 결과를 행 단위로 대조한다. 판단이 갈린 행만 작성자가 판정한다.

## 합격 조건

- 구조화 21/21 PASS.
- 의미 항목 9개 × 21건 = 189/189 PASS (`rationale_supports_decision` 포함).
- 내부 식별자 검사 21/21 PASS. `decision`·`action_id` 등 신규 필드명 노출도 잡는다.
- decision 뒤집힘 비율을 사례별과 전체(`cases_with_flip / cases_measured`)로 보고한다. 구조화 PASS(`EITHER` 허용)와 분리해 둘 다 보고한다.
- 근거 선행과 대비책(`CANDIDATE_FIRST`) 사이의 전환 기준은 미정이다. 같은 라운드의 대비책보다 나쁘지 않아야 한다는 상대 비교는 제안이며 합격 조건이 아니다.

## 결과 처리

새 회차로 [실험 요약](../results/README.md)에 추가하고 기존 기록을 덮어쓰지 않는다. PASS면 최종 회귀와 공개판 확정을 거쳐 승인판으로 옮기고 기준선을 재고정한다. FAIL이면 후보 상태를 `FAIL`로 바꾸고 결과 기록을 연결한다.

## 후속 (이 계획의 범위 밖)

- 메뉴가 있으면서 모델이 조치를 제시하지 않는 것이 정답인 무제안 케이스(메뉴 있는 무제안 케이스)는 현재 동결 7건에 없다. 새 동결 입력과 새 측정이 필요하다.
- FinOps 재측정(3단계), 실제 공격 탐지율, 실제 AWS 실행과 통신 효과.
