# #347 단가 추정 개선 후보 설계

작성: 2026-09-16. 상태: **설계 제안, 후보 구현·모델 실행 전**.
이 문서의 작성으로 실행 승인이 생기지 않는다. 이번 설계의 유료 모델 호출은 0회다.

## 1. 결정할 것

**첫 후보 A는 모델 출력에서 서버가 이미 정한 식별자 네 개를 빼고, AI 설명과 두 단가는 유지한다.**
후보 B는 A에서 설명 생성까지 제거하는 별도 안이다. A가 충분성 기준을 통과하면 B를 비교하지 않는다.
최고 점수의 프롬프트를 찾는 것이 아니라, 기존 절감액·산출률 기준을 만족하는 후보를 찾는다.

| 구분 | 모델 출력 — 실제 스키마의 필드 순서 | 변경의 의미 |
| --- | --- | --- |
| 현재 v0.9.1 | status → target_arn → region → current_instance_type → target_instance_type → explanation → current_hourly_rate → target_hourly_rate | 비교용 과거 증거를 보존한다. 현재 버전을 합격 기준선으로 부르지 않는다. |
| **A: 식별자 재출력 제거** | status → explanation → current_hourly_rate → target_hourly_rate | 대상·리전·사양은 요청에 그대로 제공하고, 결과의 연결과 저장은 서버가 담당한다. 공개 설명은 계속 AI가 작성한다. |
| **B: 설명 생성 제거** | status → current_hourly_rate → target_hourly_rate | 숫자 추정만 AI에 맡기고 비교 조건·계산법·한계 설명을 서버가 작성한다. 설명의 생성 주체가 바뀌는 별도 계약 제안이다. |

두 후보 모두 모델 지식에서 가격을 떠올리는 방식을 유지한다. 출력 축소가 정확도를 높인다는 증거는 아직 없다.
목표는 출력 책임을 좁혔을 때 기존 가격 기준을 충족하는지 확인하는 것이다.

## 2. 관찰 근거와 가설

[최근 동시 비교](../results/20260916-rate-prompt-comparison-1/report.md)에서 v0.9.0과 v0.9.1은 각각 29/30이었다.
이탈한 출력도 서버 산술은 맞았고, 공개 설명에서 리전·과금 조건의 모순은 발견하지 못했다.
v0.9.0의 한 출력은 두 단가가 함께 20% 높았고, v0.9.1의 한 출력은 두 단가의 오차가 달라 절감액이 27.18% 낮았다.
따라서 비율 검사나 서버 계산만으로 단가 문제를 해결할 수 없다.

- **A의 가설:** 이미 입력에 있는 식별자를 생성하는 일을 없애면 두 단가와 설명을 생성하는 출력이 안정될 수 있다.
  반대로 식별자 재출력이 가격 조건을 유지하는 데 도움이 됐을 가능성도 있으므로, 개선 방향은 미정이다.
- **B의 가설:** 설명문 생성도 제거하면 숫자 출력의 변동이 줄 수 있다.
  설명이 먼저 나오는 현재 순서가 유리했을 가능성도 있으며, 설명 제거 자체는 가격 지식을 보충하지 않는다.

기존 실험은 설명 지시 추가·단가 식별 지시·가격표 출력만으로 충분성이 확보되지 않았음을 보여 준다.
[과거 회고](../results/20260916-retrospective/report.md)의 호출 위치 설명은 과거 상태다.
현재 호출 위치와 무료 검증 상태는 [후속 보고](../results/20260916-post-guardrail-free-validation/report.md)를 따른다.

## 3. 공통 고정 조건

- 모델 `gpt-5.6-luna`, reasoning `low`, temperature 미지정. 다른 모델·추론 설정을 같은 실험에 섞지 않는다.
- 가드레일 PASS 후 독립 단가 호출 1회, 서버 계산, 저장본 조회라는 현재 구조를 유지한다.
- `savings_context`의 내용과 전송 전 마스킹은 현재와 같다. ARN·리전·현재/목표 사양도 입력에 남긴다.
- 서버가 정한 목표 사양, USD, 월 730시간, Linux·Shared·OnDemand·컴퓨팅 비용만 비교하는 가정을 유지한다.
- 두 단가의 숫자 문자열 pattern·범위·소수 6자리 제한, Decimal 계산·센트 HALF_UP을 유지한다.
- [평가 명세 v0.2.0](../spec.json), Golden 입력, AWS 참조 스냅샷, 기존 채점기와 과거 결과를 변경하지 않는다.
- 평가용 참조 단가나 정답에서 얻은 배율을 요청에 넣지 않는다. 출력 보정·허용폭 완화·성공 표본 교체도 하지 않는다.

첫 실험에서는 입력 축소·리전명 추가·가격표 생성·자기 검토 호출·다수결을 함께 넣지 않는다.
서버는 가격을 조회하지 않으며, 실행 가드레일·형식 수용·산술 성공을 가격 정확성으로 표시하지 않는다.

## 4. 후보 A의 정확한 변경

### 모델 요청

[현재 요청](../../../savings.py)의 시스템 프롬프트에서 다음 한 문장만 바꾼다.

```text
변경 전: 목표 타입은 서버가 결정한 값을 복사한다.
변경 후: 목표 타입은 서버가 결정한 값을 사용한다.
```

나머지 단가 식별·한국어 설명·UNAVAILABLE 지시는 유지한다.
출력 스키마에서 `target_arn`, `region`, `current_instance_type`, `target_instance_type` 네 필드를 제거한다.
남은 필드는 다음 순서·타입으로 고정한다.

```text
status: ESTIMATED | UNAVAILABLE
explanation: string | null
current_hourly_rate: 기존 HourlyRateText | null
target_hourly_rate: 기존 HourlyRateText | null
```

SDK의 strict schema 변환 후에도 필드 순서와 required/nullable 처리를 지문에 포함한다.
ESTIMATED는 두 단가와 저장 가능한 비어 있지 않은 설명을 요구한다.
UNAVAILABLE는 두 단가가 모두 null이어야 하며, 기존처럼 저장 계약에는 미산출 사유만 남긴다.
SDK 스키마뿐 아니라 서버 수용 단계에서도 이 조건을 검증한다.

### 결과 연결과 보장 범위

서버는 호출 전에 후보의 런북·대상·목표 사양을 자산 문맥과 대조한다.
호출에 사용한 문맥을 해당 응답과 결속하고, 그 문맥에서 대상·리전·사양·가정을 가져와 저장 근거를 구성한다.
모델 응답이나 배열 위치로 다른 후보의 식별자를 선택하지 않는다.

**응답의 식별자 일치 검사는 A에서 사라진다.** 서버가 문맥을 채웠다는 이유로 모델이 그 문맥을 맞게 해석했다고 판정하지 않는다.
실험 어댑터가 식별자를 합성해 기존 검사에 넣은 뒤 `CONTEXT_MISMATCH=0`을 개선 근거로 보고하는 방식은 쓰지 않는다.
가격이 다른 조건에서 나온 듯해도 두 숫자만으로 그 원인을 증명할 수 없다. 고정 참조와의 절감액 편차로 판정한다.

공개 `AISavingsEstimate`의 필드·DB·API 형식은 그대로 유지할 수 있다.
두 단가와 설명은 AI 생성값, 대상·사양은 서버 문맥, 금액은 서버 계산 결과라는 출처를 유지한다.

## 5. 후보 B의 정확한 변경과 보류 조건

B는 A를 기준으로 `explanation` 출력 필드를 제거한다.
프롬프트의 역할에서 “추정 근거”를 빼고, explanation 작성 지시·한국어 공개 코드 표현 지시·UNAVAILABLE 설명 지시를 제거한다.
단가 식별·비교 범위·숫자 형식·ESTIMATED/UNAVAILABLE 조건은 A와 같다.

공개 근거는 서버 문맥과 AI 단가로 다음 의미의 문장을 작성한다.

> {리전}의 {현재 사양}에서 {목표 사양}으로 변경하는 비교입니다. Linux·공유형·온디맨드 컴퓨팅 요금만 포함합니다.
> 두 시간당 단가는 모델 지식 기반 추정값이며 실제 요금 조회 결과가 아닙니다.
> 서버가 두 단가의 차이에 월 730시간을 곱했습니다. 스토리지·네트워크·세금·할인·크레딧은 제외합니다.

이 문장은 **서버가 적용한 비교 조건의 설명**이다. 모델이 해당 조건의 가격을 정확히 기억했다는 증거나 AI가 작성한 설명으로 표시하지 않는다.
UNAVAILABLE의 개별 자유 서술 이유도 생성하지 않으므로, 서비스에는 일반적인 모델 산출 불가 사유만 남는다.

현재 [공유 저장 계약](../../../../../../packages/schemas/savings.py)과
[SSOT](../../../../../../docs/PROJECT_STATUS.md)는 AI 근거를 전제로 한 표현을 포함한다.
B는 JSON 모양을 유지할 수 있어도 설명의 생성 주체와 의미가 바뀐다.
서비스 적용 전 이 의미 변경을 결정하고 공유 계약 설명·PM의 SSOT 갱신 범위를 정해야 한다.
단순히 서버 문장을 기존 AI explanation 자리에 넣고 동일 계약이라고 처리하지 않는다.

따라서 B는 이번 첫 라운드의 실행 대상이 아니다. A가 통과하면 B는 실행하지 않는다.
A가 실패해도 B를 자동 실행하거나 남은 호출을 넘기지 않는다.

## 6. 무료 준비 범위

아직 이 준비 코드를 작성하거나 실행하지 않았다. 후속 구현 시 서비스 요청을 바로 교체하지 않고 평가 경로에서 A를 만든다.

1. 평가용 요청·출력 모델·수용 어댑터를 추가한다. 기존 production 요청과 과거 실험 파일은 보존한다.
2. 설치된 SDK의 MockTransport로 실제 전송 요청을 확인한다. 입력 문맥 동일, 출력 네 식별자 제거,
   나머지 필드 순서·nullable·숫자 pattern·모델 설정을 확인한다. 이는 모델 품질 확인과 분리한다.
3. 좁은 경계만 검증한다: 후보/문맥 오연결, ESTIMATED 필수값, UNAVAILABLE의 잔여 단가,
   저장 불가 설명, 음수 절감액, 모델 호출 실패 시 기존 PASS 후보 보존.
   기존 산술·DB/API 테스트를 복제하지 않고 재사용한다.
4. 기존 실패 단가 쌍을 재생해 채점 결과가 계속 실패인지 확인한다. 어댑터가 가격 실패를 숨기거나 수정하지 않아야 한다.
5. 입력·전송 요청·출력 스키마의 순서·프롬프트·채점 명세·구현·전체 호출 순서를 실행 전 지문으로 고정한다.

후속 예상 변경은 `ai/evaluation/savings/`와 해당 AI 테스트 범위다.
후보 채택 전에는 `ai/savings.py`의 서비스 요청, Workflow, 공유 스키마, FE, migration을 변경하지 않는다.
서비스 채택 시에는 별도로 요청 지문·수용 경계·회귀 범위를 갱신한다.

## 7. 첫 유료 라운드 제안: A의 충분성 평가

| 항목 | 고정 계획 |
| --- | --- |
| 실행 열 | A 한 개 |
| 사례 | A1, A7, A11, A12, A14, A16 |
| 반복 | 사례당 10회 |
| 최대 요청 | **60회** — 각 회차는 독립 단가 호출 1회 |
| 실행 순서 | 반복 1~10을 바깥 순서로 두고, 홀수 반복은 위 사례 순서, 짝수는 역순 |
| 제외 호출 | 요약·추천·모델 판정자 호출 0회 |
| 재시도 | SDK 0, 래퍼 1회 시도, 요청 timeout 30초 |

현재 버전은 최근 라운드에서 이미 기준을 충족하지 못했다. 첫 라운드는 A의 충분성 판정이므로 대조군을 다시 호출하지 않는다.
과거와 실행 시점이 다른 결과만으로 A의 인과적 우월성이나 실패율 감소를 주장하지 않는다.
60개는 서로 다른 가격 조건 60개가 아니다. 고정 6사례에는 **가격 조건 두 종류**만 있으며 결론도 그 범위에 한정한다.

### 합격·중단 기준

[기존 명세](../spec.json)의 절감액 과대 +10%·과소 −20%, 최소 절대 허용폭 1 USD와 센트 경계를 유지한다.

- 예정된 60회가 완료되어야 충분성 통과를 판정한다.
- ESTIMATED 최소 57/60. UNAVAILABLE는 최대 3건이다.
- 허용 밖 절감액과 모델 출력의 계약 오류는 각각 0건이어야 한다.
- **가격 이탈 또는 모델 출력의 계약 오류 첫 1건에서 중단한다.** 기존의 0건 기준을 더 이상 충족할 수 없기 때문이다.
- **UNAVAILABLE 네 번째 발생에서 중단한다.** 남은 회차가 모두 성공해도 95% 산출률을 충족할 수 없다.
- 인증·네트워크·timeout·공급자 오류·실행기 결함은 라운드를 중단하고 미완료로 분류한다.
  모델 품질 결함과 혼동하지 않으며, 불확실한 호출의 재시작·자동 대체를 하지 않는다.

시도 수·응답 수·ESTIMATED·UNAVAILABLE·INVALID·미실행을 따로 기록한다.
중단 전 성공분만으로 통과율을 제시하거나 미산출·실패를 분모에서 제거하지 않는다.
형식 오류가 모델 출력 때문인지 실행기 때문인지 불명확하면 원인 미확정으로 남기고 승패를 내지 않는다.

개별 단가 ±10% 이탈, 과소 허용 하한 일치, 설명의 조건 모순·정보 누락, usage·시간은 별도 진단이다.
기존 가격 합격선을 사후 변경하지 않는다. 설명에 입력과 모순되는 조건이나 실제 요금 조회 주장이 있으면
가격 점수와 분리해 서비스 채택의 미해결 결함으로 남긴다. 설명은 구조화 근거와 합쳐 정보 충족을 확인한다.

### 비용과 승인

최대 60회는 이 문서의 제안 한도이며 실행 승인이 아니다.
무료 준비 후 실제 요청 크기와 과거 usage, 실행 직전의 공식 모델 단가로 비용·시간을 산정한다.
열 수 1·최대 호출 수 60·추정 비용·예상 시간을 함께 제시하고 해당 라운드 승인을 받는다.
이전 라운드의 미사용 한도는 재사용하지 않는다. B의 추가 호출도 포함하지 않는다.

## 8. 결과별 다음 작업

| 결과 | 다음 작업 |
| --- | --- |
| A 충분성 통과, 설명의 서비스 결함 없음 | A를 서비스 적용 후보로 삼는다. B나 동점 해소 실험은 진행하지 않는다. |
| A 가격 이탈·산출률·출력 계약 기준 미달 | 해당 결과와 중단 이유를 보존한다. 같은 후보를 통과할 때까지 반복하지 않는다. B를 포함한 다음 선택은 관찰 근거로 다시 결정한다. |
| A 가격 통과, 설명 결함 있음 | 가격 통과와 공개 근거 미해결을 함께 보고한다. 단가 요청 변경이 필요한 후속 수정은 새로운 버전으로 다룬다. |
| 인프라·실행기 문제로 미완료 | 수행·과금 여부와 품질 판정 불가 범위를 정리한다. 수정 후에도 새 실행은 별도 라운드로 승인받는다. |

채택 후보의 서비스 검증은 독립 가격 평가와 별도다.
대표 가격 조건 두 종류에서 각각 요약 → 추천 → 가드레일 → 단가 → PostgreSQL 저장 → 새 앱 조회를 확인한다.
제안 예산은 **최대 6회 모델 호출**이며, 별도 실행 승인 대상이다.
추천 부재·가드레일 거절로 후속 가격 호출이 없으면 경로 검증 미완료로 보고하고 성공할 때까지 추가 생성하지 않는다.
LocalStack 검증은 실제 AWS 성공이나 조치 후 청구 절감을 입증하지 않는다.

## 9. 산출물과 종료점

이 설계의 산출물은 문서 한 개다. 개선 후보의 가격 품질은 아직 미검증이다.
후속 실행에서는 고정 계획·요청 지문·시도 장부·허용된 구조화 결과·필드/규칙 진단·usage·모델 식별자·시간·오프라인 채점 결과를 남긴다.
비밀키·거부 원문·모델 원본 응답·내부 추론은 보존하지 않는다. 공개 설명을 내부 추론으로 해석하지 않는다.

서비스 적용 여부는 가격 충분성, 공개 근거, 실제 저장·조회 경로의 결과를 각각 보고한 뒤 결정한다.
한 번의 무실패 표본을 다른 리전·사양·현재 AWS 가격에 대한 보증으로 확대하지 않는다.
