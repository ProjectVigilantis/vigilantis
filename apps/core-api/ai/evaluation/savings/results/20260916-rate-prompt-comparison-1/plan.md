# v0.9.0·v0.9.1 단가 프롬프트 비교

## 목적

직전 서비스 후보 v0.9.1의 월 절감 예상 60건 중 2건이 과대 허용폭을 넘었다.
이전 v0.9.0의 60건 통과와 실행 시점이 달라, 추가 설명 지시의 영향인지 출력 변동인지
현재 결과만으로 구분할 수 없다. 같은 라운드에서 두 단가 프롬프트를 비교한다.

이번 범위는 A1·A7·A11의 **단가 호출 진단**이다. 서비스 3호출 구조를 유지하며,
AI는 시간당 단가를 추정하고 서버는 `(현재 단가 - 목표 단가) × 730`을 계산한다.
전체 6개 사례의 서비스 품질, 요약 품질, 온라인 생성→저장→조회는 후속 검증이다.

## 두 열과 호출 순서

| 열 | 사용하는 요청 | 사례·반복 | 호출 수 |
|---|---|---|---:|
| v0.9.0 | `rate_only_request`의 기존 단가 지시 | A1·A7·A11 각 10회 | 30 |
| v0.9.1 | `savings_request`의 현재 서비스 단가 지시 | A1·A7·A11 각 10회 | 30 |
| 합계 | 요약·추천·판정자 추가 호출 없음 | 3 × 10 × 2 | **60** |

두 요청의 차이는 공개 근거의 필드명·상태 코드를 한국어로 풀어 쓰라는 v0.9.1의 마지막
지시뿐이다. 기존 프롬프트를 수정하거나 새 버전을 만들지 않는다.

- 같은 사례·반복 안에서 두 열을 연이어 호출한다. 홀수 반복은 v0.9.0→v0.9.1,
  짝수 반복은 역순이다. 사례 순서도 홀수 A1→A7→A11, 짝수 역순이다.
  사례별로 각 열이 먼저 호출되는 횟수는 5회씩이다.
- Luna/low, temperature 미지정. `ProposedHourlyRates` 출력 계약과 서버 수용 함수를 공유한다.
- Golden 입력·외부 전송 직전 마스킹 결과·출력 스키마·프롬프트·채점 명세·소스와
  60개 호출 순서를 [preflight.json](preflight.json)에 고정한다.
- 평가용 AWS 참조 단가는 요청에 넣지 않는다. 단가 보정이나 표본 교체를 하지 않는다.

## 판정과 다음 단계

[기존 명세 v0.2.0](../../spec.json)을 그대로 사용한다. 서버 계산 후 월 절감 예상의
과대 +10%·과소 −20%, 최소 절대 허용폭 1 USD, 센트 반올림 경계를 적용한다.
단가 각각의 ±10%는 진단 항목이며 월 절감 예상의 통과 조건과 분리한다.

각 열의 30건을 모두 관찰한 뒤 산출률 95% 이상, 가격 이탈·계약 오류 0건인지 확인한다.
30건에서 `UNAVAILABLE`는 최대 1건이다. 미산출·실패·미실행을 분모에서 빼지 않는다.
부분 실행의 관찰값은 보존하지만 비교 완료나 통과로 판정하지 않는다.

과대/과소 이탈 수, 최대 과대 오차, 사례별 상태, 생성된 두 단가·서버 금액을 보고한다.
모든 결과를 보존하며, 반복 중 일부만 골라 이전 결과와 합산하지 않는다.

| 관찰 결과 | 후속 판단 |
|---|---|
| 한 열만 진단 기준 충족 | 그 열을 전체 서비스 검증 후보로 제안한다. 아직 채택하지 않는다. |
| 두 열 모두 충족 | 순위 결정을 위한 재실험 없이 현재 v0.9.1을 전체 검증 후보로 유지한다. |
| 두 열 모두 이탈/미충족 | 관찰한 단가 쌍·사례로 후속 수정 범위를 정한다. 반복 실행을 자동 확대하지 않는다. |
| 호출·파싱·실행기 오류로 중단 | 부분 결과와 실패 단계만 보고한다. 열 간 승패를 내지 않는다. |

표본이 작아 이탈 횟수 차이만으로 추가 지시의 인과 효과나 모델의 내부 추론을 증명하지 않는다.
기존 실패 이력도 유지한다. 설명문은 모델 내부 사고 과정의 증거로 해석하지 않는다.

## 실행 경계와 기록

- 최대 60호출. SDK `max_retries=0`, 래퍼 `max_attempts=1`, 호출 제한시간 30초.
- 가격 이탈·서버 계약 거절·UNAVAILABLE는 기록하고 계획된 비교를 계속한다.
  요청·전송·응답 파싱·실행기 오류는 즉시 중단한다. 재시도·표본 대체·잔여 호출 재배정은 없다.
- 각 호출 직전에 STARTED를 저장하고, 완료 후 수용된 구조화 예상값·검증 규칙/필드·usage·
  모델 식별자·시간을 기록한다. 거절 원문·모델 원본 응답·내부 추론·키는 보존하지 않는다.
- 중단된 실행의 호출 여부가 불명확해도 같은 라운드에서 재시작하지 않는다.
  [metadata.json](metadata.json)은 실행 후 생성되는 호출 기록이며
  [analysis.json](analysis.json)은 오프라인 재채점으로 생성한다.
- 승인 파일과 고정 지문이 맞아야 시작한다. 기본 실행은 키를 읽지 않는 오프라인 확인이다.
  사용자가 이전에 승인한 **기본 체크아웃 `.env`의 키**와 Golden 외부 전송 범위를 사용한다.

## 예상 비용·시간과 승인

**이번 2열·60호출 실행 승인은 아직 받지 않았다.** 이전 540호출 라운드의 남은 한도는
이 라운드로 옮기지 않는다. 로컬 준비와 실행 전 검증 후 별도로 승인받는다.

예상 **0.03~0.06 USD, 약 4~6분**. 직전 서비스 라운드의 단가 호출 60건은
입력 56,420·출력 20,360토큰, 캐시 입력 0, 합계 237.566초였다.
같은 사용량에 현재 공개 단가를 곱하면 0.035716 USD이며, 출력 변동 여유를 둔 추산이다.
비용·시간 범위는 보장 상한이 아니며 실행 상한은 60호출이다.

[공식 Luna 가격](https://developers.openai.com/api/docs/models/gpt-5.6-luna)을 2026-09-16 확인했다.
100만 토큰당 입력 0.20 / 캐시 입력 0.02 / 출력 1.20 USD다.
실행 후 비용도 제공된 usage 기반 추정으로 기록하고 실제 청구와 구분한다.
공급자가 별도 보고하지 않은 캐시 쓰기 비용·실패 usage는 대사할 수 없다.

## 실행 방법

worktree 루트의 `.venv/Scripts/python.exe -X utf8`로 이 디렉터리의
`run_comparison.py`를 실행한다.

- 인자 없음: 현재 파일과 고정 계획 대조, 모델 호출 0회.
- `--freeze`: 승인 전에 계획을 고정한다. 승인·착수 후 재고정을 거부한다.
- `--execute-approved`: 이 계획에 대한 실제 사용자 승인을 `approval.json`으로 기록한 뒤 실행한다.
- `--analyze`: 저장된 기록을 새 모델 호출 없이 재채점한다.
