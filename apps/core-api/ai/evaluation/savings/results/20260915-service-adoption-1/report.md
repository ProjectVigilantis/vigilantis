# v0.9.1 서비스 편입 검증 — 최종 채택 보류

## 결론

서비스 3호출 연결과 저장·조회는 구현했다. 새 후보는 **60회 중 58회 가격 통과, 과대 추정 2회**로 사전 합격선에 미달했다. 승인 스냅샷은 v2로 유지하며 v1.0.0으로 올리지 않았다.

최대 540호출 승인 중 실제 **300호출**을 실행했다. 계획의 가격 중단 조건에 따라 기존·새 요약 판정 **240호출은 미실행**이다. 남은 예산을 다른 실험에 배정하거나 재시도하지 않았다.

## 현재 구현

1. 요약을 생성한다.
2. 조치 후보를 생성하고 기존 후보 계약을 검사한다.
3. 유효한 RIGHTSIZING 후보에만 세 번째 호출로 시간당 단가 두 개와 근거를 받는다.
4. 서버가 `(현재 단가 − 목표 단가) × 730`을 Decimal로 계산하고 센트 단위로 반올림한다.
5. Dispatcher의 저장 전 검사, Workflow, PostgreSQL, 상세 API가 예상값을 전달한다.

목표 인스턴스 타입은 기존 서버 규칙으로 정한다. AI가 추정하는 값은 단가이며, 서버가 계산한 금액도 단가에 의존하는 **예상값**이다. 서비스에 평가용 가격표나 AWS 요금 API를 연결하지 않았다.

요약·추천 실패는 기존 FAILED 경로다. 단가 호출만 실패하면 실행 후보를 보존하고 예상값을 `INVALID / MISSING_ESTIMATE`로 둔다. `UNAVAILABLE`, 계약·문맥 오류, 기존 후보의 null은 서로 구분한다.

## 가격 결과

사전 명세 `spec.json v0.2.0`을 유지했다. 절감액 과대 +10%·과소 −20%, 최소 허용폭 $1, 센트 단위 비교, 산출률 95% 이상이 기준이다. 이번 60회는 모두 산출됐고 산술·사양·리전·과금 가정 검사를 통과했다. 가격 오차 2건 때문에 전체는 실패다.

### 잡아야 할 과대 추정

두 건 모두 `t3.xlarge → t3.medium`이며 평가 참조 월 절감액은 **$113.88**, 허용 상한은 **$125.27**이다.

| 회차 | AI 현재/목표 단가(USD/h) | 서버 계산 월 절감액 | 참조 대비 | 허용 상한 초과 |
| --- | --- | ---: | ---: | ---: |
| A7/6 | 0.230400 / 0.057600 | $126.14 | +$12.26 · **+10.77%** | $0.87 |
| A1/6 | 0.230400 / 0.052800 | $129.65 | +$15.77 · **+13.85%** | $4.38 |

참조 현재/목표 단가는 0.208000 / 0.052000이다. 두 건의 현재 단가는 참조보다 10.77% 높다. A7은 목표 단가도 같은 비율로 높고, A1은 목표 단가가 1.54% 높아 단가 차이의 오차가 더 커졌다. 서버 산술 오류가 아니라 **입력 단가의 오차가 절감액에 반영된 것**이다.

이는 고정된 가격 참조와의 비교다. 실제 고객 청구서나 변경 후 실측 비용과 비교한 결과는 아니다.

### 허용한 낮은 추정과 별도 진단

- 절감액 방향: 일치 4회, 높음 26회, 낮음 30회. 높은 26회 중 위 2회만 한도를 넘었다.
- 22회는 과소 추정 허용 하한에 걸렸다. 하한을 센트로 반올림하므로 원비율로는 약 −20.0035%가 될 수 있으나, 사전 명세의 $91.10 / $45.55 경계에 맞아 통과한다.
- 개별 단가 ±10% 진단은 **30/60회 이탈**이다. 이 중 상방 이탈 2회, 하방 이탈 28회이며, 단가 진단 30회를 가격 실패 30회로 해석하지 않는다.
- 가격 허용폭을 넓히거나 결과 금액을 보정하지 않았다.

전량 결과와 원자료 재채점은 [candidate-scored.json](candidate-scored.json), [analysis.json](analysis.json)에 있다.

## 무엇을 확인했고 무엇이 남았나

| 항목 | 기존 v2 생성 | 새 v0.9.1 생성 |
| --- | ---: | ---: |
| SUCCEEDED | 60/60 | 60/60 |
| 계약·요청·전송 실패 | 0 | 0 |
| 빈 후보 | 0 | 0 |
| 입력 사실 자동 검사 실패 | 0/60 | 0/60 |
| 실행 필드 안정도 | 36/36 | 36/36 |
| 요약 복원·결함 판정 | 미실행 | 미실행 |

요약·후보 생성의 성공은 요약 의미 품질 승인과 다르다. 가격 중단 조건에 따라 짝 비교 판정을 생략했으므로 기존 요약 기준선 재통과를 주장하지 않는다.

60개 가격 근거 원문과 가격 실패 2건의 전체 출력을 확인했다. 서울·Linux·공유·온디맨드·컴퓨팅 비용 범위 및 모델 지식 추정이라는 설명과 모순되는 문장은 발견하지 못했다. 단가를 어떻게 선택했는지는 이 공개 설명으로 알 수 없으며 내부 CoT는 수집하지 않았다.

공개 용어 정리도 완결되지 않았다. 새 요약 **44/60회**에 `COST_CANDIDATE`가 남았고, 가격 근거 **A11/2**에는 `pricing_source`와 `MODEL_KNOWLEDGE`가 남았다. 이는 진단 기록이며 사전에 정하지 않은 가격 실패 조건으로 추가하지 않았다. [문장 확인 기록](public-text-review.json)

v0.9.0 가격 요청과 비교하면 입력·출력 스키마는 같고, v0.9.1에는 공개 코드명을 한국어로 쓰라는 지시가 추가됐다. 이번 결과만으로 그 지시가 과대 추정의 원인인지, 모델 출력 변동인지 구분할 수 없다. 이전 60/60 결과만으로 원래 문구의 안정성이 충분하다고 확정하지 않는다.

## 저장·조회와 회귀 검증

- **대표 생성 내용 6건 저장·조회 통과.** 고정 세트의 비 UUID 식별자만 DB UUID로 일대일 대응하고, 요약·조치·대상·파라미터·단가·금액은 보존했다. 실제 출력과 대응 후 출력 모두 Dispatcher 검사에 통과했다. Workflow의 가드레일 1~3, PostgreSQL commit, 새 앱 두 개의 상세 조회를 확인했다. 추가 모델 호출 0회. [결과·응답 예시·식별자 대응](saved-output-verification.json)
- 이 재생 검증은 온라인 모델 생성부터 DB 저장까지 한 번에 실행한 검증과 다르다. Intake를 다시 실행하지 않았고 실제 AWS 사전검사(가드레일 4)는 대역이다.
- **Docker 빌드·API 기동·health·OpenAPI 통과.** 자동 분석·AWS 스캔·위협 inbox를 끄고 단일 worker로 기동했다. 검증용 API 컨테이너는 정리했다. [Docker 검증](docker-verification.json)
- **로컬 전체 pytest: 2,140 통과 / 1 실패 / 2 skip.** CI와 같은 테스트 경로, PostgreSQL·LocalStack 사용. 실패는 승인 v2와 미채택 v0.9.1의 스냅샷 불일치다. 두 skip은 기존 E2E 무조건 보류다. CI 통과 상태가 아니다.
- 사용자 요청으로 서비스 흐름과 DB·API 계약의 독립 코드 리뷰를 1회 진행했다. 두 리뷰 모두 검토 범위에서 추가 기능 결함을 찾지 못했다. 테스트·가격 품질 판정을 대신하지 않는다.
- 변경 Python 파일 40개 Ruff 비교에서 HEAD 대비 추가 진단은 0건이다. 기존 진단 196건이 남아 있으므로 전체 lint 무결점 통과를 뜻하지 않는다. `git diff --check`는 통과했다. [lint 기록](lint-final.json)

초기 저장 검증 스크립트의 enum 참조·합성 ID 처리와 분석 스크립트의 import 경로 오류는 수정 후 재검증했다. 모델 출력·서비스 코드를 그 오류에 맞춰 바꾸지 않았다.

## 보관과 재검증

```powershell
# 네트워크 없는 전량 원자료·채점·호출 기록 대조.
# 가격 미달을 재현하므로 종료 코드 1이 현재 정상적인 판정 결과다.
.venv\Scripts\python.exe -X utf8 apps/core-api/ai/evaluation/savings/results/20260915-service-adoption-1/analyze.py

# 모델 호출 없이 로컬 PostgreSQL 저장·새 앱 조회 재생 검증.
.venv\Scripts\python.exe -X utf8 apps/core-api/ai/evaluation/savings/results/20260915-service-adoption-1/verify_saved_outputs.py

# 현재 서비스의 호출 규모 안내. 6건 × 10회 = 최대 180호출.
.venv\Scripts\python.exe -X utf8 scripts/finops_eval.py --repeats 10 --estimate
```

`run_validation.py`의 완료된 단계를 다시 실행하지 않는다. 계측 뒤 `finops_eval.py --estimate`의 기존 2호출 안내만 3호출로 수정했다. 계측 당시 소스 지문은 보존하며 [변경 기록](post-measurement-edits.json)을 역적용하면 당시 바이트 지문과 같음을 분석 스크립트가 확인한다.

## 후속 조건

1. 가격 프롬프트 선택과 공개 용어 처리 방식을 정한 뒤 새 라운드를 별도로 설계한다. 평가 단가 주입·사후 보정·허용폭 변경으로 이번 실패를 없애지 않는다.
2. 새 최종 후보의 가격 기준을 통과하면 이번 v2 원자료를 재사용해 기존·새 요약을 같은 판정 패스에서 비교한다.
3. 대표 입력을 실제 DB에서 만들어 온라인 생성→저장→조회도 확인한다. 합성 ID 대응 재생 검증의 한계를 닫는 단계다.
4. 모든 채택 조건 충족 후 v1.0.0·승인 스냅샷·최종 PR 본문을 확정한다. [현재 PR 초안](pr-draft.md)은 게시 전 보류 상태다.

공개 PR #344가 `db/models.py`와 별도 Alembic migration을 변경 중이다. 게시 전 병합 순서와 migration head를 조율해야 한다. #347 초기 이슈의 “추천 호출에서 AI가 금액 생성” 문구는 이후 사용자 결정인 “AI 단가 추정·서버 계산·3호출”에 맞춰 갱신할 대상이다. 이번 검증에서 GitHub·SSOT를 수정하거나 팀원에게 메시지를 보내지 않았다.
