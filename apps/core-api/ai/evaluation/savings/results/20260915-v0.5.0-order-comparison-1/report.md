## 변경과 비교 범위

내부 모델 출력 `ProposedSavingsEstimate`에서 공개 근거 `explanation`을 단가·금액보다 먼저 생성하도록 순서만 옮겼다.
근거를 먼저 작성하면 입력 조건에 맞는 단가 선택이 안정되는지 보는 실험이다.

| 버전 | 대상 식별자 이후의 필드 순서 |
| --- | --- |
| v0.4.0 | 현재 단가 → 목표 단가 → 월 금액 → 근거 |
| v0.5.0 | 근거 → 현재 단가 → 목표 단가 → 월 금액 |

시스템 프롬프트 문구, 필드 의미와 파싱 계약, 모델 설정, 입력 세트, `spec.json` v1의 가격 참조·허용 오차는 고정했다.
A1·A11의 요약은 [이전 v0.4.0 원자료](../20260915-v0.4.0-probe-1/raw.json)에서 가져와 모든 반복에 동일하게 전달했다.
`replay_recommendation`으로 기존 추천·출력 검증 노드만 실행했다. 평가 참조 단가는 모델 입력에 포함하지 않았다.

사전 계획은 두 버전 × 두 케이스 × 3회, 최대 12호출이었다. 버전 호출 순서를 교대하고 **v0.5.0의 첫 기준 미달에서 즉시 중단**하도록 정했다.
대조군 v0.4.0의 실패는 중단 조건에 포함하지 않았다. 전체 계획과 실제 순서는 metadata에 보존했다.

## 판정과 한계

v0.5.0은 관측 3건 중 2건 PASS, 1건 PRICE_DEVIATION이다. v0.4.0 대조군은 2건 중 각각 1건이다.
조기 중단으로 반복 수가 부족하고 버전별 횟수도 다르므로 개선 효과·우열·실패율 차이를 확정하지 않는다.
다만 사전에 정한 가격 기준을 넘는 오류가 재현됐으므로 **생성 순서 변경만으로 기준을 충족했다는 가설은 지지되지 않는다.**

두 채점 파일의 `complete=false`는 전체 6건 × 10회가 아닌 부분 실행이라는 뜻이다.
`PRICE_DEVIATION`은 반복 수 부족과 별개의 실제 가격 오류이며 두 파일 모두 `passed=false`다.
실행기 `exit_code=0`은 계획한 중단과 기록이 정상 종료됐다는 뜻이다.

이번 원자료의 `invocation_status`는 추천 재생과 출력 계약 검증의 결과다. 서비스 전체 그래프를 실행한 결과로 읽지 않는다.
저장된 요약을 사용했으므로 새 요약의 품질·요약 회귀를 판정하지 않았다. DB·조회 API 실환경 검증과 전체 6건 × 10회 실행도 이번 범위 밖이다.
v0.5.0은 미공개 개선안으로 남기고 품질 기준선과 승인 스냅샷의 갱신은 보류한다.

## 재현과 무료 검증

- 실제 OpenAI SDK와 `httpx.MockTransport`로 두 스키마를 각각 1회 직렬화했다(실호출 0회). 메시지·응답 이름·스키마 의미가 같고 `properties` 및 SDK가 만든 `required`의 필드 순서만 달랐다.
- 기존 프롬프트 지문은 JSON 키를 정렬해 선택 필드의 순서 변경을 놓쳤다. 출력 스키마의 순서를 보존하도록 고치고 순서 변경을 감지하는 회귀 검증을 추가했다. v0.4.0 지문은 과거 정렬 형식으로 보존하며 같은 형식으로 재구성하면 기존 지문과 일치한다.
- v0.4.0: `68eb744564bf2b7ec7906a01e3a9cc45333e88e55b4d1f6bcfe81478ed1a1840` (`schema_keys_sorted_legacy`).
- v0.5.0: `b2564546a4e2984973aae75a73543266e75bae883a2740f6e85aeb7ad31612da` (`schema_order_preserved`).
- 관련 pytest: **83 통과·1 실패·1,991 deselected·0 skip**. 실패는 `test_prompt_fingerprint_matches_approved_snapshot`의 승인 판 v2와 현재 v0.5.0 불일치다. 테스트를 통과시키기 위한 스냅샷 갱신은 하지 않았다.
