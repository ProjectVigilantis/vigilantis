가장 큰 기록 공백마지막 계약 거부의 구체적 필드와 규칙을 저장하지 못했다.

계측 실행기가 서버 검증 후의 INVALID / INVALID_ESTIMATE만 기록했다. 원래 구조화 값과 검증 위치가 없으므로 산술 오류인지, 필드 형식 오류인지 현재 자료로는 확정할 수 없다. 이 누락은 내가 만든 계측 경로의 문제다.

  • 어떤 과정을 거쳤나 →사용자 피드백과 실행한 변경의 시간순 기록

  • 왜 개선이 멈췄나 →관찰된 가격 오류와 계측의 빈틈
  • 코드는 어디까지 했나 →서비스 변경 파일과 실험 도구의 경계

수치는 저장된 JSON에서 다시 집계했다. 초기 논의는 이 대화에 남은 사용자 지시와 작업 기록을 요약했다. 모든 대화의 정확한 시각이나 당시 전체 코드 스냅샷을 보유한 것은 아니다. 이번 HTML 작성 중 새 유료 모델 호출은 하지 않았다.

금액을 AI가 추정하는 이유

이 작업에서 AI 추정은 3줄 요약에 금액을 넣기 위한 편의 기능으로 선택한 것이 아니다. 금액과 산출 근거의 생성 주체를 AI로 정한 SSOT 결정이 출발점이다. 따라서 런타임에 사람이 관리하는 단가표나 요금 API를 붙여 생성 주체를 바꾸는 선택은 별도 설계 변경이 된다.

다만 “AI가 만든다”는 계약은 “그 숫자를 검증 없이 정확하다고 취급한다”는 뜻이 아니다. 현재 사양·리전·목표 사양은 서버 문맥과 대조하고, 단가와 금액의 실제 정확도는 별도 실험으로 측정한다. 그 실험이 아직 기준을 충족하지 못했다.

절감 예상의 의미 검증만 실패하면 조치 후보를 보존한다. 이미 파싱된 추천 안에서 추정 부분을 거부하는 동작이다. 모델의 전체 응답 자체가 구조화 출력으로 파싱되지 않으면 기존 그래프 실패 경로를 따르므로, 모든 종류의 AI 오류에서 후보를 보존한다고 확대할 수 없다.

평가 입력과 가격 참조를 먼저 고정

기존 FinOps 고정 세트의 A1·A7·A11·A12·A14·A16을 명세에 등록했다. 기준선 계획은 6건 각각 10회다. 실제 예비 계측은 두 가격 조합을 대표하는 A1과 A11만 선택했다. 나머지 4개 사례의 값이나 품질을 관측한 것으로 쓰지 않는다.

참조는 spec.json v1에 저장한 AWS 공개 EC2 요금 파일이다. 2026-09-15 조회 기록이며 파일 판은 20260910195514, 게시일은 9월 10일, 해당 요금 적용일은 9월 1일이다. 리전은 서울 ap-northeast-2, Linux / Shared / OnDemand, 사전 설치 소프트웨어 NA, CapacityStatus Used, USD/Hrs 조건이다.

이 단가는 채점에서만 사용했다. 모델에는 ARN·리전·사양·730시간과 과금 가정을 제공했다. 평가 정답 단가나 월 참조 절감액은 모델 입력에 넣지 않았다. 런타임이 평가 가격표를 참조하도록 연결하지도 않았다.

월 예상 절감액 = (현재 시간당 단가 − 목표 시간당 단가) × 730

730시간은 비교용 고정 가정이다. 실제 가동 시간이나 실제 청구액을 측정한 값이 아니다. 인스턴스 컴퓨팅 요금만 포함하고, 스토리지·네트워크·세금·할인·CPU 크레딧은 제외한다.

후보가 정한 기준을 한 번이라도 벗어나면 중단하는 방식은 이번 후보가 무오류 조건을 충족하지 못했음을 빠르게 확인했다. 대신 표본 수와 노출이 불균등해져 두 조건의 실패율이나 개선 효과를 안정적으로 추정하지 못한다. “후보가 이번 기준에서 탈락했다”와 “이 방향이 일반적으로 더 나쁘다”는 서로 다른 결론이다.

가격 전용의 첫 두 A1 결과는 후속 진단을 생각할 단서다. 마지막 계약 거부의 세부 원인을 놓쳤다고 앞선 신호가 사라지는 것도, 앞선 신호가 있다고 실패를 지워도 되는 것도 아니다. 지금은 두 사실을 함께 유지해야 한다.
