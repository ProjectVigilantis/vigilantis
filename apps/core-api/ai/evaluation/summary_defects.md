# CoT 요약 3줄 — 결함 체크리스트

관제자에게 나가는 요약 3줄(`AgentGraphOutput.summary_lines`)을 판정할 때 쓰는 목록이다. **Issue #237 산출물이며, #243이 요약 프롬프트 v1의 지시문 기준으로 썼다 — 항목 1개 = `ai/agent.py` 지시문 1줄.** 3줄의 역할은 근거(`observation`) / 진단(`diagnosis`) / 결론 근거(`rationale`)다.

## 이 문서가 "좋은 요약"의 정의가 아닌 이유

요약 문장에는 정답지가 없고 만들 수도 없다 — 같은 뜻을 여러 문장으로 쓸 수 있어서다. 그래서 좋은 쪽을 정의하지 않고, **관제자의 결정을 막는 결함**만 목록으로 쌓는다. 목록은 유한하고 누적된다: 새 결함을 발견하면 한 줄 추가하고, 이미 있는 항목은 지우지 않는다.

## 통과 기준선 — 하나뿐이다

> **관제자가 이 3줄만 보고 승인 또는 차단을 고를 수 있는가.**

이 선을 넘으면 통과다. 그 위(문장이 더 매끄럽다, 더 짧다)는 통과 조건이 아니라 개선이며, 개선을 통과 조건으로 올리면 판정이 사람마다 갈린다.

## 결함 목록

| # | 결함 | 왜 결정을 막는가 | 예 |
| --- | --- | --- | --- |
| 1 | **근거 사실이 없다** | 판단만 있고 왜 그렇게 봤는지가 없어, 관제자가 그 판단을 검증할 수 없다. 국가·공공기관 AI보안 가이드북 v2.0(2025.12) M22·A-M14 "설명 가능한 AI 구성"이 요구하는 판단 근거가 이 줄이다 | "이 인스턴스는 낭비입니다." — 무엇을 보고 그렇게 봤는지가 없다 |
| 2 | **단정과 추정이 안 갈린다** | 확실한 것과 추정한 것이 같은 어조로 나오면 관제자가 위험을 잘못 잡는다 | "유휴입니다" vs "14일 평균 3%로 유휴로 보인다" |
| 3 | **진단과 조치가 안 이어진다** | 왜 그 조치인지가 비어 승인 판단이 근거 없이 남는다 | 1–2줄은 CPU 이야기인데 3줄이 다른 축의 조치를 권한다 · 제안 카드는 다운사이징인데 3줄이 "중지·종료 검토"를 권한다(v0 실측) |
| 4 | **3줄이 같은 말이라 실질 정보가 1줄** | 화면 세 줄을 차지하고 정보는 한 줄어치다. 읽을 것이 없는 승인 요청이 쌓이면 습관적 승인이 된다(같은 가이드북 A09 "승인 피로") | "CPU가 낮다 / 사용률이 저조하다 / 이용이 적다" |
| 5 | **구조화 필드로 이미 나가는 값을 문장에서 반복한다** | 문장 자리를 값 낭독에 쓰면 문장만 줄 수 있는 것(맥락·인과)이 밀려난다 | "health_score는 5이고 판정은 COST_CANDIDATE입니다" |

### 5번의 판정 기준은 화면이 아니라 계약이다

"화면에 이미 보이는 값"이 아니라 **"구조화 필드로 이미 나가는 값"** 을 기준으로 본다. 필드가 있으면 FE는 언제든 그릴 수 있고, 안 그리는 것은 FE의 결정이다. 화면 기준으로 잡으면 화면이 개편될 때마다 이 항목이 무효가 된다.

대상 필드:

- `AssetItem`(`packages/schemas/api/assets.py`) — `health_score` · `verdict` · `skip_reason_code`
- `RecommendationItem`(`packages/schemas/api/incidents.py:101`) — `runbook_id` · `target_arn` · `display_parameters`

값을 **인용해 근거로 삼는 것**은 결함이 아니다("평균 CPU 4.9%라 다운사이징 후보로 잡혔다"). 값을 **되읽는 것**이 결함이다.

## 지시문 대응 (v1)

| # | `ai/agent.py` `_SUMMARY_SYSTEM_PROMPT`의 줄 |
| --- | --- |
| 1 | `observation:` — 근거가 된 입력 사실을 쓰고 판정의 문턱이 된 값을 포함한다 |
| 2 | `diagnosis:` — 입력이 확정한 것은 단정으로, 추론한 것은 추정으로 구분한다 |
| 3 | `rationale:` — `available_actions` 중 근거·진단이 뒷받침하는 조치 **하나**에 대해 그 조치가 이 자산에 맞는 이유. 다른 조치는 다루지 않고, 판정이 후보가 아니면 왜 조치가 없는지 |
| 4 | "세 줄은 각각 새 정보를 싣는다 — 같은 사실은 한 줄에만 둔다" |
| 5 | "구조화 필드로 이미 화면에 나간다. 그 값은 근거로 인용할 때만 쓴다" |

### 실측이 더한 규칙 (v1 세우는 동안)

결함 목록 항목이 아니라 **산출에서 드러난 도피·과잉을 막는 규칙**이다. 항목을 늘리는 법 그대로 — 결함이 나오면 규칙 한 줄로 반영했다.

| 실측 | 규칙 | 자리 |
| --- | --- | --- |
| A7(관측 48개)에서 요약이 판정을 유보하고 후보를 비움(NO_PROPOSAL 4/60) | "verdict는 규칙 엔진이 이미 내린 판정이다 … 판정을 다시 내리는 자리는 승인 단계의 관제자다" | `_SUMMARY_SYSTEM_PROMPT` 둘째 문단 |
| 3줄이 메뉴에 없는 조치(중지·종료·삭제)를 권함(31/60) | 요약 호출에 가능한 조치의 **목적 문구만**(`available_actions`) 싣는다 — 이름을 주면 되읽고 열거한다 | `agent._summary_payload` |
| 3줄이 메뉴를 열거하자 후보 노드가 언급된 런북을 다 담음(후보 2건 35/60, `min_size=max_size=1`) | rationale은 뒷받침하는 조치 하나만 · 후보는 "rationale이 뒷받침한 조치를, 한 대상에 하나" | 요약·후보 프롬프트 |

## 누가 판정하나 — 세 층

| 층 | 무엇을 보나 | 어디서 |
| --- | --- | --- |
| 코드 | 재현성·`FAILED` 건수 / 사실 정합성(인용한 값이 입력에 실재하는가) / 되읽기·근거 인용 — 5번·1번의 어휘 근사 | `reproducibility.py` · `factcheck.py` · `readback.py` |
| LLM 판정자 | **복원 대조** — 3줄과 제안 카드만 보고 `verdict`·`skip_reason_code`·판정을 가른 값을 복원해 골든과 대조(정답지가 판정자 품질을 판정한다) / 2·3·4번 판정(라벨 + 이유, 처방 없음) | `judge.py` · `scripts/finops_judge.py` |
| 사람 | **지금은 없다.** 팀에 관제 도메인 전문가가 없어 비전문가 라벨은 판정자 검증이 되지 않는다 — 2·3·4번 라벨은 진단값으로만 쓴다. 팀이 관제자 역할을 실제로 해 본 뒤 판정자 지적의 정밀도(지적한 표현이 문장에 실재하는가) 확인부터 붙인다 | `docs/AI_SUMMARY_BASELINE.md` |

사람이 산출을 직접 판정하지 않는 이유: 순진한 판정자는 첫 판 뒤에 케이스를 기억해 글이 아니라 기억으로 답하므로 1회용이고, LLM은 기억하지 않아 매 판 다시 쓸 수 있다. 복원 대조는 정답지가 있어 판정자 품질이 저절로 검증된다. 2·3·4번은 정답지가 없어 판정자 라벨이 미검증 진단값으로 남는다 — 합격선에는 걸리지 않고, 판을 바꿨을 때 방향(v0 대비)만 본다.

`NO_PROPOSAL` 비율도 자동 집계다(`ai/evaluation/report.py`). 제약이 쌓일수록 빈 후보가 가장 안전한 답이 되어 모델이 아무것도 제안하지 않는 쪽으로 기우는데, **개선했는데 조용히 제안이 사라지는 것을 그것 말고는 잡을 수단이 없다.**

## 항목을 늘리는 법

판정하다 막힌 자리가 생기면 그것이 새 항목이다. 두 가지만 지킨다.

- **결함으로 쓴다.** "~하면 좋다"가 아니라 "~가 없으면 결정을 못 한다"로 적는다. 전자는 통과 기준선을 올려 판정을 흐린다.
- **판정 근거를 계약이나 입력에 건다.** 화면 구성·문체 취향에 걸면 그쪽이 바뀔 때 항목이 무효가 된다.
- **지시문 1줄을 함께 단다.** 항목과 `ai/agent.py` 지시문은 1:1이다. 코드로 근사할 수 있으면 `readback.py`에, 아니면 `judge.py`의 결함 판정 프롬프트에 항목을 넣는다.
